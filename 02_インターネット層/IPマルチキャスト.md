# IPマルチキャスト まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

令和5年春 午後Ⅰ 問2「IP（Internet Protocol）マルチキャストによる映像配信の導入」で大問として出ている。

## 1. マルチキャストの基本（○）

- **1つの送信元から、特定のグループに参加した複数の受信者へ同時に送る**通信
- 送信元は**1つのパケットを送るだけ**で、ネットワークの分岐点（ルータ、スイッチ）で必要な数だけ複製される

| 方式 | 送り先 | 映像を100台に送る場合 |
|---|---|---|
| ユニキャスト | 1台 | 送信元が**100本**送る → 送信元と回線の負荷が大きい |
| ブロードキャスト | 同じネットワークの全台 | 見ない端末にも届く。ルータを越えられない |
| **マルチキャスト** | **参加したグループの端末だけ** | 送信元は**1本**。必要な所だけで複製 |

- 用途：映像・音声の配信（社内放送、IPテレビ）、ソフトウェアの一斉配布、ルーティングプロトコル（OSPF（Open Shortest Path First）の224.0.0.5など）
- **UDP**（User Datagram Protocol）で送る → **再送がない**（失われたパケットは戻らない）

## 2. マルチキャストアドレス（○）

| 範囲 | 用途 |
|---|---|
| **224.0.0.0/4**（224.0.0.0〜239.255.255.255） | IPv4マルチキャスト（旧クラスD） |
| 224.0.0.0/24 | **同じリンク内だけ**（ルータは転送しない）：224.0.0.1（全ホスト）、224.0.0.2（全ルータ）、224.0.0.5／6（OSPF）、224.0.0.18（VRRP（Virtual Router Redundancy Protocol）） |
| **239.0.0.0/8** | **組織内だけで使う**（プライベートアドレスのようなもの）→ 社内の映像配信で使う |
| ff00::/8 | IPv6マルチキャスト |

- **マルチキャストのMACアドレス**：**01-00-5E** ＋ IPアドレスの**下位23ビット**
  - 28ビットのうち5ビットは使われないので、**32個のIPアドレスが同じMAC（Media Access Control）アドレスになる**（△）

## 3. IGMP：受信者とルータの間（◎）

- **IGMP（Internet Group Management Protocol）**：端末が「このグループを受信したい」とルータに知らせるプロトコル
  - **参加（レポート／Join）**：受信したい端末がルータに知らせる
  - **クエリ**：ルータが定期的に「まだ受信したい端末はいるか」と確認する
  - **離脱（Leave）**：IGMPv2から。受信をやめたことをすぐに知らせる → 不要な配信を早く止められる
  - **IGMPv3**：「この送信元からのグループだけ」と**送信元を指定**できる（SSM（Source-Specific Multicast）で使う）
- IPv6では **MLD**（Multicast Listener Discovery）が同じ役割（△）

### IGMPスヌーピング（◎）

- 通常のL2スイッチは、マルチキャストのフレームを**ブロードキャストと同じように全ポートへ転送**（フラッディング）する → 受信しない端末にも映像が流れ、帯域を圧迫する
- **IGMPスヌーピング**：L2スイッチがIGMPのやり取りを**盗み見て**、**参加した端末がいるポートにだけ**転送する
- 記述の型：「L2スイッチがIGMPメッセージを監視し、マルチキャストグループに参加している端末が接続されたポートにだけフレームを転送するため」

## 4. PIM：ルータ同士（○）

- **PIM（Protocol Independent Multicast）**：ルータ同士で、マルチキャストを**どの経路で配信するか**（配信ツリー）を作るプロトコル
  - 既存のユニキャストのルーティングテーブルを使うので「Protocol Independent」

| 方式 | 動き | 向く場面 |
|---|---|---|
| **PIM-DM**（Dense Mode） | まず**全体にフラッディング**し、不要な所から**プルーン（刈り込み）** | 受信者が多く、密集している |
| **PIM-SM**（Sparse Mode） | 受信者からの**Join**で必要な所だけにツリーを作る。**RP**（Rendezvous Point：集合場所のルータ）を使う | **受信者がまばら**。企業ネットワークの主流 |

- PIM-SMの流れ：受信者側のルータがRPに向けてJoin → 送信元はRPに送る → RPから受信者へ（共有ツリー）→ 必要なら送信元から直接の最短経路（最短経路ツリー）に切り替える（△）
- **RPF（Reverse Path Forwarding）チェック**：マルチキャストを受けたインタフェースが、**送信元へのユニキャストの経路の向き**と一致しなければ破棄する → ループを防ぐ（○）
  - ユニキャストの経路と合わない構成（非対称な経路など）では、マルチキャストが届かない原因になる

## 5. 午後で問われるテーマと記述の型

### ◎ 映像配信の導入

- ユニキャストで配信すると、**送信元のサーバとWAN（Wide Area Network）回線の帯域が受信者の数に比例して必要**になる → マルチキャストにする理由
  - 記述の型：「受信者が増えても送信元が送るパケットは1つで済み、サーバと回線の負荷が増えないから」
- 帯域の計算：1ストリームの帯域 × チャネル数（受信者数ではない）
- L2スイッチにIGMPスヌーピングを設定し、受信しないポートに流さない
- ルータにPIMを設定し、拠点間でマルチキャストを中継する

### ○ マルチキャストが届かない原因

- **TTL**（Time To Live）が小さすぎてルータを越えられない（送信元の設定）
- **RPFチェック**で破棄される（ユニキャストの経路とずれている）
- IGMPスヌーピングで、**クエリを送る機器**（IGMPクエリア）がいないと、参加の情報が更新されずに配信が止まる
- FW（Firewall）、VPN（Virtual Private Network）がマルチキャストを通さない → GRE（Generic Routing Encapsulation）でカプセル化する（→ [[IPsec]]）

### ○ 再送がないことへの対応

- UDPで再送がないので、**FEC**（Forward Error Correction：前方誤り訂正）で冗長なデータを付けて、多少の損失を受信側で補う（△）
- 一斉配布（ファイル）では、失われた部分だけを後でユニキャストで取りに行く

## 6. 覚え方

- **マルチキャストは「ラジオ放送」**：送信は1回、聴きたい人だけ周波数（グループ）を合わせる
- **IGMPは「端末とルータの間の受信希望」、PIMは「ルータ同士の配信経路づくり」**
- **IGMPスヌーピングは「スイッチが聞き耳を立てて、希望者のポートだけに流す」**
- **DMは「まず全部に流して、いらない所を切る」、SMは「希望があった所だけ、集合場所（RP）経由で」**
- **社内用は239.0.0.0/8、224.0.0.x はリンク内だけ**
- **MACは「01-00-5E＋下位23ビット」**

## 7. 勉強の優先順位

1. マルチキャストを使う理由（送信元・回線の負荷）を30〜40字で書けるようにする
2. IGMPの役割と、IGMPスヌーピングの目的
3. PIM-SMとPIM-DMの違い、RPの役割
4. 届かない原因（TTL、RPFチェック、クエリア）
5. マルチキャストアドレスの範囲とMACアドレスの対応（午前）
6. FEC、SSMは名前を知っている程度でよい

> [!tip] 得点につながる覚え方
> マルチキャストの問題では、**受信者 ⇔ L2スイッチ ⇔ ルータ ⇔ ルータ ⇔ 送信元**の区間ごとに、どのプロトコル（IGMP、IGMPスヌーピング、PIM）が働くかを構成図に書き込んでから設問を読む。
