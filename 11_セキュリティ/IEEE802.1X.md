# IEEE802.1X まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

## 1. IEEE802.1Xの基本（◎）

- **LAN（Local Area Network、有線・無線）に接続する時点で利用者・端末を認証し、認証に成功するまでネットワークを使わせない**仕組み
- 単位は**ポート**（有線ならスイッチのポート、無線ならAP（Access Point）への接続）→ ポートベース認証
- 認証前は**EAPOL（認証用のフレーム）だけ**通し、それ以外の通信は遮断する
- 登場人物は3者

| 役割 | 正体 | 仕事 |
|---|---|---|
| **サプリカント** | 端末（PCのOS（Operating System）に組み込まれたソフト） | 認証を要求する |
| **オーセンティケータ** | **L2スイッチ、無線AP**（またはWLC（Wireless LAN Controller）） | 認証の中継役。結果に従ってポートを開閉する |
| **認証サーバ** | **RADIUS（Remote Authentication Dial In User Service）サーバ** | 認証の可否を判断する |

- 区間ごとのプロトコル

```
[サプリカント] ──EAPOL── [オーセンティケータ] ──RADIUS── [認証サーバ] ──LDAP── [LDAPサーバ（AD）]
    端末          （EAP over LAN）  L2SW／AP     （EAPをRADIUSで運ぶ）  RADIUS       （必要なら）   利用者情報
```

- **EAP**（Extensible Authentication Protocol）：認証のやり取りを運ぶための枠組み。中身の認証方式（EAP-TLS（EAP-Transport Layer Security）など）を選べる
  - 端末〜オーセンティケータ間は**EAPOL**（L2のフレーム。IP（Internet Protocol）アドレスがなくても認証できる）
  - オーセンティケータ〜認証サーバ間は、EAPを**RADIUSのパケットに入れて**運ぶ
- オーセンティケータは**認証方式の中身を理解しなくてよい**（中継するだけ）
- 午前の定番：「IEEE802.1Xが定めているもの」→ ポートベースのネットワークアクセス制御

## 2. 認証の流れ（○）

1. 端末がつながる → EAPOL-Start（端末から）またはEAP-Request/Identity（スイッチ・APから）
2. 端末がユーザIDを返す（EAP-Response/Identity）
3. オーセンティケータがRADIUSサーバへ **Access-Request** で中継する
4. 選んだEAP方式でやり取りする（RADIUSサーバからは **Access-Challenge**）
5. 結果
   - 成功：**Access-Accept**（接続先のVLAN（Virtual LAN）などを指定できる）→ 端末にEAP-Success → **ポートが開く**
   - 失敗：**Access-Reject** → ポートは閉じたまま
6. 無線LANの場合は、EAPで作られた鍵をもとに、続けて**4ウェイハンドシェイク**で暗号鍵を作る → [[WPA]]

## 3. EAPの認証方式（◎）

| 方式 | サーバの認証 | クライアントの認証 | ポイント |
|---|---|---|---|
| **EAP-TLS** | サーバ証明書 | **クライアント証明書** | **最も安全**。パスワード不要。全端末に**クライアント証明書の配布・管理が必要** |
| **PEAP**（Protected EAP） | サーバ証明書 | **ID・パスワード** | サーバ証明書でTLS（Transport Layer Security）のトンネルを作り、その中でID・パスワード（MS-CHAPv2）を送る |
| **EAP-TTLS**（EAP-Tunneled TLS） | サーバ証明書 | **ID・パスワード** | PEAPと同じくトンネルの中でID・パスワードを送る。中の方式を選べる |
| EAP-MD5 | なし | パスワード | サーバを認証しない、暗号鍵を作れない → **無線LANでは使えない**（△） |

- EAP-MD5が無線LANで使えない理由：無線LANでは認証の途中で電波を暗号化する鍵の元を作る必要があるが、EAP-MD5は**暗号鍵を生成できず、サーバの認証もできない**から（TLSを使う方式は、相互認証と鍵の生成ができる）
- **どの方式もサーバ証明書でRADIUSサーバを確認する**（EAP-MD5以外）
  - 端末がサーバ証明書を検証しないと、**偽のAP・偽のRADIUSサーバ**にID・パスワードを盗まれる
  - 端末には、サーバ証明書を発行した**CA（Certificate Authority）の証明書**（ルート証明書）を入れておく必要がある
- 問われ方：「EAP-TLSとPEAPの違い」「クライアント証明書を配布しない方式を選ぶ理由」「端末に必要な証明書」
- 記述の型（EAP-TLS）：「クライアント証明書で端末を認証するため、パスワードの漏えいによるなりすましを防げる」
- 記述の型（サーバ証明書の検証）：「偽のアクセスポイントに接続して、認証情報を窃取されることを防ぐため」

## 4. RADIUS（◎）

- 認証（Authentication）・認可（Authorization）・アカウンティング（Accounting）を行う **AAA**（Authentication, Authorization, Accounting） のプロトコル
  - 具体例：**認証**でID・パスワードや証明書から本人か確かめ、**認可**でその利用者を所属部署のVLANに入れ、**アカウンティング**で誰が・いつ・どれだけ接続したかを記録する
- ポート：**UDP（User Datagram Protocol） 1812（認証・認可）／1813（アカウンティング）**（古い実装は1645／1646）
  - RADIUSでは、認証と認可は**同じやり取り**で行う（Access-Acceptで認証の成功を返すとき、VLAN番号などの認可の情報も一緒に返す）ので、どちらも1812番
- **RADIUSクライアント＝オーセンティケータ（スイッチ・AP）**。RADIUSサーバ側に、IPアドレスと**共有シークレット**（事前共有の鍵）を登録しておく
  - 登録されていない機器からの要求は受け付けない
  - パスワード属性は共有シークレットで隠されるが、**それ以外の属性は平文**（△）
- メッセージ：Access-Request／Access-Challenge／Access-Accept／Access-Reject
- **ダイナミックVLAN**：Access-Acceptに**VLAN番号の属性**を入れて返す → スイッチ・APがその端末をそのVLANに所属させる
- ISP（Internet Service Provider）のPPP（Point-to-Point Protocol）接続の認証にも使われている → [[PPP]]

## 5. LDAPとの関係（○）

- RADIUSサーバ自身に利用者を登録せず、**LDAP（Lightweight Directory Access Protocol）サーバ（AD：Active Directory）の利用者情報を使って**認証・認可することが多い
  - 「RADIUSが窓口、LDAPが名簿」
- 使い方は方式によって違う
  - **EAP-TLS**：認証は証明書で行う。LDAPは**アカウントが有効か、所属グループは何か**の確認（認可）に使う
  - **EAP-TTLS（中身がPAP（Password Authentication Protocol））**：RADIUSサーバが受け取ったパスワードで、LDAPに**Bind**して確認できる
  - **PEAP（MS-CHAPv2）**：パスワードそのものが届かないため、LDAPのシンプル認証では確認できない → RADIUSサーバをADと連携させる（△）
- **所属グループ（LDAPの属性）→ ダイナミックVLAN**：部署ごとに接続先VLANを分ける、が定番の組合せ
- → [[LDAP]]

## 6. 午後で問われるテーマと記述の型

### ◎ 構成要素の役割と通信区間

- 構成図の機器を「サプリカント／オーセンティケータ／認証サーバ」に当てはめる
- 区間ごとのプロトコル（EAPOL／RADIUS／LDAP）と、FW（Firewall）で許可すべき通信
  - オーセンティケータ（スイッチ、AP、WLC）→ RADIUSサーバ：**UDP 1812／1813**
  - RADIUSサーバ → LDAPサーバ：TCP（Transmission Control Protocol） 389／636
- 問われ方：「表の空欄に入る機器名・プロトコル名」「RADIUSサーバに登録すべき情報」→ オーセンティケータのIPアドレスと共有シークレット

### ◎ ダイナミックVLAN

- 同じスイッチ・同じSSID（Service Set Identifier）でも、**認証結果（利用者の所属）に応じて接続先VLANを変える**
- 席を移動しても、自分の部署のVLANにつながる（フリーアドレス）
- 記述の型：「RADIUSサーバが認証結果とともにVLAN IDを通知し、スイッチがそのVLANにポートを割り当てる」
- → [[VLAN]]

### ○ 認証に対応しない機器・複数の端末

- プリンタ、IP電話などサプリカントを持たない機器 → **MAC（Media Access Control）認証**（MACアドレスで認証。偽装に弱い）や、ポートの認証を外す
- 1つのポートの先にハブで複数の端末がつながる場合
  - 1台が認証されるとポート全体が開く設定だと、**未認証の端末も通信できてしまう**
  - 対策：**端末（MACアドレス）ごとに認証する**モードにする
- Web認証：ブラウザでID・パスワードを入れる方式（ゲスト向け）

### ○ 無線LANでのローミング

- APを移動するたびに802.1X認証をやり直すと時間がかかり、音声通話などが途切れる
- 対策：**PMK（Pairwise Master Key）キャッシュ**、**事前認証**、**802.11r（高速BSS（Basic Service Set）遷移）**
- → [[IEEE802.11]]

### ○ 認証サーバの冗長化

- RADIUSサーバが止まると、**新しく接続する端末が誰も認証できない**
- 対策：RADIUSサーバを2台にし、オーセンティケータに**両方を登録**する（プライマリが応答しなければセカンダリへ）
- LDAPサーバも同様に冗長化する

### △ 検疫ネットワーク

- 認証時に端末のOSの更新状況やウイルス対策ソフトの状態を確認し、基準を満たさない端末を**隔離用のVLAN**に入れる

## 7. 攻撃者の観点：どこを突くか

| 狙う所 | 攻撃のしかた | 成り立つ条件 |
|---|---|---|
| **端末がサーバ証明書を検証しない** | 正規と同じSSIDの**偽AP・偽RADIUSサーバ**を立て、PEAP／EAP-TTLSのID・パスワードを盗む | 端末側で「サーバ証明書を検証する」「信頼するCAを指定する」設定がない |
| **ポート単位の認証** | 認証済みの端末のポートにハブを挟み、**未認証の端末を便乗させる** | 1台が認証されるとポート全体が開く設定 |
| **MAC認証の機器** | プリンタ・IP電話などのMACアドレスを調べて**偽装**し、そのポートやVLANに入り込む | MACアドレスだけで認証している、その機器のVLANから社内の重要な所に行ける |
| **認証をかけていないポート** | 会議室や空き席のポート、認証を外したポートにつなぐ | 未使用のポートが有効なまま |
| **ID・パスワード** | 推測、使い回し、退職者のアカウントを使う | パスワード方式（PEAP）、アカウントの削除漏れ |
| **証明書の入った端末** | 紛失・盗難した端末でそのまま接続する（EAP-TLS） | 証明書を失効させる運用がない |
| **認証サーバ** | RADIUSサーバ・LDAPサーバを止めて、誰も接続できなくする（可用性への攻撃） | 認証サーバが1台だけ |

- 午後では「どの設定が欠けていると、どの攻撃が成り立つか」を問う形が多い

## 8. 防御側に必要な対策

| 立場・機器 | 対策 | 防げる攻撃 |
|---|---|---|
| **端末（サプリカント）** | **サーバ証明書の検証を必須にし、信頼するCA（とサーバ名）を指定する**。設定は管理者が一括で配布し、利用者に変えさせない | 偽AP・偽RADIUSによる認証情報の窃取 |
| **認証方式の選択** | **EAP-TLS**（クライアント証明書）にする | パスワードの推測・漏えいによるなりすまし |
| **スイッチ（オーセンティケータ）** | **端末（MACアドレス）ごとに認証する**モードにする。**未使用ポートは無効化**する | ハブによる便乗、空きポートからの接続 |
| **MAC認証の機器** | MAC認証は必要な機器だけにし、**専用のVLANに入れて通信先を絞る**（プリンタならプリントサーバとの通信だけ許可） | MACアドレスの偽装による侵入の被害を小さくする |
| **RADIUS／LDAP（アカウント管理）** | 退職・異動をLDAPに即時反映する。紛失した端末の**証明書を失効**させる（CRL（Certificate Revocation List）／OCSP（Online Certificate Status Protocol）） | 退職者・盗難端末による接続 |
| **RADIUSサーバ** | 2台で冗長化する。オーセンティケータごとに推測されにくい共有シークレットを設定する | 認証サーバの停止、不正なRADIUSクライアント |
| **運用** | RADIUSのアカウンティングで**誰がいつどこに接続したか記録**する | 不正接続の追跡 |

- 記述の型（サーバ証明書の検証）：「端末がRADIUSサーバの証明書を検証することで、偽のアクセスポイントに認証情報を送ることを防ぐ」
- 記述の型（MAC認証の機器）：「MACアドレスは偽装できるため、MAC認証の機器は専用VLANに収容し、通信先を限定する」

## 9. 覚え方

- **3者は「客（サプリカント）・受付（オーセンティケータ）・審査部門（認証サーバ）」**。名簿（LDAP）は審査部門の奥にある
  - 受付は書類（EAP）の中身を読まずに奥へ回すだけ
- **区間は「EAPOLで受付まで、RADIUSで奥まで、LDAPで名簿まで」**
- **EAP-TLSは「両方が身分証（証明書）」、PEAP・TTLSは「サーバだけ身分証、客は合言葉（パスワード）」**
- **RADIUSは「1812（いち・はち・いち・に）で認証、1813で記録」**
- **ダイナミックVLANは「名簿の部署を見て、案内する部屋を変える」**

## 10. 勉強の優先順位

1. 3者の役割と、区間ごとのプロトコル（EAPOL／RADIUS）を構成図に書き込めるようにする
2. EAP-TLSとPEAP（EAP-TTLS）の違い、サーバ証明書を検証する理由を30〜40字で書けるようにする
3. ダイナミックVLANの仕組み
4. RADIUSのポート番号、RADIUSサーバに登録する情報（IPアドレス、共有シークレット）
5. LDAPとの役割分担（RADIUSが窓口、LDAPが名簿）
6. MAC認証、ハブ配下の複数端末、ローミング、冗長化
7. EAPの細かいメッセージ名、検疫ネットワークは名前を知っている程度でよい

> [!tip] 得点につながる覚え方
> 802.1Xは**無線LAN、社内LANの更改、テレワークの問題の中で**繰り返し出る定番。構成図を見たら、まず「どれがサプリカント／オーセンティケータ／認証サーバか」に印を付け、**証明書がどこに必要か**（RADIUSサーバ、端末、CA証明書）を確認する。
