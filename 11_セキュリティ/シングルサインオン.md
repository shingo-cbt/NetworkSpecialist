# シングルサインオン まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

SSOの**実現方式の比較**をまとめる入口のノート。仕組みの詳細は [[SAML]]（組織をまたぐSSO）、[[Kerberos]]（社内のSSO）を参照。

## 1. SSOの基本（○）

- **SSO（Single Sign-On）**：**1回の認証で、複数のシステム・サービスを使えるようにする**仕組み
- 利点
  - 利用者が覚えるパスワードが1つで済む（使い回しや、メモ書きが減る）
  - **認証を1か所に集める**ので、多要素認証の導入や、退職者のアカウント停止を**まとめて**行える
  - 各システムがパスワードを持たなくてよい方式もある（漏えいの範囲が小さくなる）
- 欠点・注意点
  - **認証情報が1つ漏れると、すべてのシステムに入られる**
  - **認証の仕組み（認証サーバ、プロキシ）が止まると、すべてのシステムを使えない**（単一障害点）

## 2. 実現方式の比較（◎：午前で頻出、午後でも構成として出る）

| 方式 | 仕組み | 利点 | 欠点 |
|---|---|---|---|
| **リバースプロキシ型** | 利用者とWebサーバの間に**認証用のリバースプロキシ**を置き、**すべてのアクセスをそこに通す**。プロキシで1回認証し、各サーバへは認証済みとして中継する | **各サーバに手を加えなくてよい** | **全通信がプロキシを通る** → **ボトルネック・単一障害点**になる。プロキシを経由しない経路をふさぐ必要がある |
| **エージェント型** | 各Webサーバに**エージェント（ソフト）を組み込む**。エージェントが、認証サーバが発行した**認証済みの証明**（Cookieなど）を確認する | 通信が1か所に集中しない | **各サーバにエージェントを導入**する必要がある（対応していないサーバには入れられない） |
| 代理認証型 | 端末のソフトなどが、利用者の代わりに**各システムのID・パスワードを自動で入力**する | 既存のシステムを変えなくてよい | 各システムのID・パスワードを代理認証の仕組みに登録・管理する必要がある |
| **フェデレーション型（SAML（Security Assertion Markup Language）など）** | **IdP**（Identity Provider）が発行した**署名付きの証明**（アサーション）を、各サービス（SP（Service Provider））が検証する | **組織・ドメインをまたげる**。クラウドサービスで主流 | IdPとSPの間で、事前に信頼関係（証明書の登録など）を結ぶ必要がある → [[SAML]] |
| **Kerberos** | KDC（Key Distribution Center）が発行した**チケット**を、各サーバに提示する | Windowsの社内環境で標準。パスワードがネットワークに流れない | 基本は**同じ組織（ドメイン）の中**。時刻同期が必要 → [[Kerberos]] |

### リバースプロキシ型とエージェント型の構成（◎）

```
【リバースプロキシ型】                         【エージェント型】
利用者 → [認証リバースプロキシ] → Webサーバ1     利用者 → Webサーバ1（エージェント）
                         └→ Webサーバ2             └→ Webサーバ2（エージェント）
         ↑ 全部ここを通る                                   ↕ 認証の確認
                                                     [認証サーバ]
```

- 午前の定番：「各サーバにソフトを導入しなくてよい方式」→ **リバースプロキシ型**、「通信が認証サーバに集中しない方式」→ **エージェント型**
- 記述の型（リバースプロキシ型の注意点）：「すべてのアクセスがリバースプロキシを経由するため、処理が集中し、停止すると全システムが利用できなくなるから」

## 3. シングルドメインSSOとマルチドメインSSO（メモ）

- 背景：エージェント型などは、**認証済みの証明をCookieでブラウザに持たせる**ことが多い。ところが**Cookieは、発行したドメイン（とそのサブドメイン）にしか送られない**
- **シングルドメインSSO**
  - 対象のシステムが**同じドメインの中**にある（例：`app1.example.co.jp` と `app2.example.co.jp`）
  - ドメイン全体（`.example.co.jp`）に有効なCookieを発行すれば、**どのサーバにも同じCookieが送られる** → Cookieを共有するだけでSSOできる
- **マルチドメインSSO（クロスドメインSSO）**
  - 対象が**別々のドメイン**にある（例：`example.co.jp` と `example-shop.jp`、自社と**クラウドサービス**）
  - **Cookieを共有できない** → 認証サーバ（IdP）にいったん**リダイレクト**し、認証済みの証明（トークン、アサーション）を**URL（Uniform Resource Locator）やフォームで相手のドメインに渡す**仕組みが必要
  - 代表が **SAML**（やOpenID Connect）のフェデレーション型
- 押さえどころ：「**同じドメインならCookieの共有で済む、ドメインが違えばリダイレクトで証明を受け渡す（SAMLなど）**」

## 4. 午後で問われるテーマと記述の型

### ◎ 方式の選択

- 既存の社内Webシステムを変更したくない → リバースプロキシ型
- 通信の集中を避けたい、サーバにソフトを入れられる → エージェント型
- **クラウドサービス（別ドメイン・別組織）を含めたい** → **SAML（フェデレーション型）**
- Windowsのファイルサーバや社内システム → Kerberos

### ○ リバースプロキシ型の構成での注意

- **プロキシを経由しない直接のアクセスを禁止**する（FW（Firewall）でWebサーバへの直接の通信を拒否する）→ そうしないと認証を迂回される
- プロキシの冗長化（負荷分散装置で複数台に振り分ける）→ [[負荷分散装置]]
- プロキシでTLS（Transport Layer Security）を終端する場合、サーバ証明書と秘密鍵をプロキシに置く → [[TLS]]

### ○ 認証基盤の統合

- SSOの認証サーバ・IdPは、利用者情報を**LDAP（Lightweight Directory Access Protocol）サーバ**（Active Directory）から参照することが多い → [[LDAP]]

## 5. 攻撃者の観点：どこを突くか

| 狙う所 | 攻撃のしかた | 成り立つ条件 |
|---|---|---|
| **SSOのID・パスワード** | フィッシングで盗み、**すべてのシステムに一度に入る** | 多要素認証がない |
| **認証済みの証明（Cookie、トークン）** | 盗んだCookieで、認証を飛ばしてアクセスする（セッションの乗っ取り） | 平文の通信、有効期間が長い、端末の感染 |
| **認証を迂回する経路** | リバースプロキシを通らずに、**Webサーバへ直接アクセス**する | Webサーバへの直接の通信を許可している |
| **各システムに残ったローカルログイン** | SSOを経由しないID・パスワードでログインする | ローカルアカウントを無効にしていない |
| **認証の仕組みの停止** | 認証サーバ・プロキシを攻撃して止め、全システムを使えなくする | 冗長化していない |

## 6. 防御側に必要な対策

| 対策 | 内容 | 防げる攻撃 |
|---|---|---|
| **多要素認証** | SSOの入口（認証サーバ、IdP）で必須にする | 盗んだパスワードでのログイン |
| **通信の暗号化とセッション管理** | TLSで暗号化し、CookieにSecure属性を付ける。有効期間を短くする | 証明の盗聴・乗っ取り |
| **迂回経路の遮断** | FWで、リバースプロキシ以外からWebサーバへの通信を拒否する | 認証の迂回 |
| **ローカルログインの無効化** | 各システムのSSO以外のログインを止める | SSOを経由しないログイン |
| **冗長化** | 認証サーバ・プロキシ・IdPを複数台にする | 単一障害点の停止 |

## 7. 覚え方

- **リバースプロキシ型は「全員が通る関所で1回だけ検問」**：サーバはそのまま、ただし関所が混む・止まると全滅
- **エージェント型は「各部屋に受付係を置く」**：混まないが、全部屋に係を配置する手間がかかる
- **代理認証型は「秘書が代わりにパスワードを打つ」**
- **フェデレーション（SAML）は「他社発行の通行証を、署名で信用する」**：ドメイン・組織をまたげる
- **同じドメインなら「Cookieの共有」、別のドメインなら「リダイレクトで証明を渡す」**

## 8. 勉強の優先順位

1. リバースプロキシ型とエージェント型の違い（利点と欠点）を説明できるようにする
2. 方式の選択（既存のサーバを変えない、クラウドを含める、など）
3. シングルドメインとマルチドメインの違い（Cookieの届く範囲）
4. リバースプロキシ型で直接のアクセスを禁止する理由を30〜40字で書けるようにする
5. 代理認証型は名前と仕組みを知っている程度でよい

> [!tip] 得点につながる覚え方
> SSOの問題では、まず「**どこで認証し、認証済みの証明を誰がどうやって確かめるか**」を構成図で追う。リバースプロキシならプロキシ、エージェントなら各サーバ、SAMLならSP、Kerberosなら各サーバがチケットを確認する。
