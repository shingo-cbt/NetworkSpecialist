# Kerberos まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

令和4年春 午後Ⅰ 問3「シングルサインオンの導入」で、ポート88を使う通信の選択、チケットを盗聴されても使えない理由、時刻同期、DNS（Domain Name System）のSRVレコードが問われている。

## 1. Kerberosの基本（○）

- **Kerberos（ケルベロス）**：**チケット**を使って、社内のサーバへの**シングルサインオン（SSO（Single Sign-On））**を実現する認証の仕組み
  - 一度ログオンすれば、ファイルサーバ・業務サーバなどを**パスワードを入れ直さずに**使える
  - **パスワードそのものはネットワークに流れない**
- **Active Directory**（Windowsの認証基盤）の中心的な仕組み。ADのドメインコントローラがKDCの役割を持つ → [[LDAP]]
- ポート：**TCP（Transmission Control Protocol）／UDP（User Datagram Protocol） 88**

| 用語 | 内容 |
|---|---|
| **KDC（Key Distribution Center）** | 認証とチケットの発行を行うサーバ。**AS（Authentication Server）**と**TGS（Ticket Granting Server）**の2つの役割を持つ |
| **TGT（Ticket Granting Ticket）** | 「認証済みの利用者である」ことを示すチケット。**STをもらうための引換券** |
| **ST（Service Ticket）** | **特定のサーバを使うためのチケット**。サーバごとに発行される |

## 2. 認証の流れ（◎）

```
PC（利用者）                     KDC（AS・TGS）                 業務サーバ
   │── ① 認証の要求 ─────────→│ AS
   │←─ ② TGT ───────────────│        （ここまでがログオン時）
   │── ③ TGTを見せて、STを要求 ──→│ TGS
   │←─ ④ ST ────────────────│
   │── ⑤ STを提示 ───────────────────────────────→│
   │←─ ⑥ 利用許可 ─────────────────────────────────│
```

- ①〜④は**KDCとの通信（ポート88）**、⑤⑥は**業務サーバとの通信**（業務サーバのプロトコルの中でSTを渡す）
- 2台目のサーバを使うときは、**③④をくり返してそのサーバ用のSTをもらう**だけ（パスワードは不要）
- 問われ方：「図の通信のうち、ポート88を使うものはどれか」→ **KDCとの通信（①②③④）**

## 3. なぜ安全か・前提条件（◎）

### チケットは暗号化されている

- STは、**業務サーバとKDCだけが知っている鍵**で暗号化されている → 利用者も、盗聴した第三者も**中身を読めず、書き換えられない**
- TGTは**KDCだけが知っている鍵**で暗号化されている
- 記述の型（盗聴しても使えない理由）：「STは暗号化されているため、通信を盗聴してもSTを取り出せず、なりすましに使えないから」

### 時刻の同期が必須

- チケットには**有効期限**があり、要求には**時刻（タイムスタンプ）**が入っている → **再送攻撃（盗聴した通信の使い回し）を防ぐ**
- PCとサーバ・KDCの**時刻のずれが大きい（初期値5分）と認証に失敗**する
- 記述の型（令和4年春 午後Ⅰ 問3の解答）：「PCとサーバの間で時刻同期を行う」
- → [[NTP]]

### KDCの場所をDNSで知る

- PCはKDCのアドレスを、DNSの**SRVレコード**（`_kerberos._tcp.ドメイン` など）で調べる
  - SRVレコードには、**優先度・重み・ポート番号・ホスト名**が書かれていて、複数のKDCへ振り分けられる
  - SRVレコードを使わない場合は、PCにKDCのFQDN（Fully Qualified Domain Name）を設定する必要がある
- → [[DNS]]

## 4. 午後で問われるテーマ

### ◎ 社内システムのSSOの導入

- ログオン時にTGTをもらい、各サーバへのアクセスでSTを使う流れ
- FW（Firewall）のルール：PC → KDC：TCP／UDP 88
- KDC（ドメインコントローラ）が止まると、**新しくチケットをもらえず**、ログオン・新しいサーバの利用ができない → **KDCを冗長化**する（SRVレコードで複数を指定）

### ○ プロキシの統合認証

- プロキシがKerberosに対応していれば、利用者がPCにログオンした情報で、**プロキシの認証を自動で通過**できる → [[プロキシ]]

### ○ SAMLとの違い

| | Kerberos | SAML（Security Assertion Markup Language） |
|---|---|---|
| 主な範囲 | **社内**（同じドメインのサーバ） | **組織をまたぐ**（クラウドサービスなど） |
| 証明に使うもの | **チケット**（共通鍵で暗号化） | **アサーション**（公開鍵で署名） |
| 通信 | PC ⇔ KDC、PC ⇔ サーバ | ブラウザのリダイレクトでIdP（Identity Provider）とSP（Service Provider）の間を運ぶ |

- → [[SAML]]

## 5. 攻撃者の観点：どこを突くか

| 狙う所 | 攻撃のしかた | 成り立つ条件 |
|---|---|---|
| **利用者のパスワード** | 推測・フィッシングで盗み、正規の利用者としてTGTをもらう | 弱いパスワード、多要素認証がない |
| **盗んだチケット** | 感染したPCのメモリからチケットを盗み、**そのまま使う**（パスザチケット） | 端末がマルウェアに感染している |
| **KDC（ドメインコントローラ）** | 乗っ取ってKDCの鍵を盗めば、**任意の利用者のTGTを偽造**できる（ゴールデンチケット。△） | KDCの防御が弱い |
| サービス用のアカウント | 弱いパスワードのサービス用アカウントのSTを取り、オフラインで解析する（△） | サービス用アカウントのパスワードが弱い |
| 時刻 | 時刻をずらして認証を失敗させる（可用性への攻撃） | 時刻の情報源が信頼できない |

## 6. 防御側に必要な対策

| 対策 | 内容 | 防げる攻撃 |
|---|---|---|
| パスワードの強化・多要素認証 | 利用者・サービス用アカウントのパスワードを強くする | パスワードの推測、STの解析 |
| **KDCの厳重な保護** | ドメインコントローラへの管理者のアクセスを限定し、更新・監視する | チケットの偽造 |
| 端末の保護 | EDR（Endpoint Detection and Response）などで感染を防ぎ・見つける、チケットの有効期限を適切にする | チケットの盗難 |
| **信頼できる時刻同期** | 社内のNTP（Network Time Protocol）サーバに同期させる | 時刻のずれによる認証失敗 |
| KDCの冗長化 | 複数のKDCをSRVレコードで指定する | KDCの停止による認証不能 |

## 7. 覚え方

- **Kerberosは「遊園地の入場券（TGT）と、アトラクションごとの乗車券（ST）」**：入口（KDC）で入場券をもらい、それを見せて乗車券に引き換える
- **KDCは「AS（入場券の窓口）＋TGS（乗車券の窓口）」、ポートは88**
- **チケットは「中身の読めない封筒」**：盗聴しても取り出せない
- **時計が5分ずれると入れない** → NTP
- **KDCの場所は「DNSのSRVレコード」で探す**
- **社内はKerberos（チケット）、組織をまたぐならSAML（署名付きアサーション）**

## 8. 勉強の優先順位

1. TGTとSTの流れと、KDCとの通信（ポート88）を図で区別できるようにする
2. 盗聴されてもSTを使えない理由、時刻同期が必要な理由を30〜40字で書けるようにする
3. SRVレコードでKDCを探す仕組み
4. SAMLとの違い
5. KDCの冗長化、プロキシの統合認証
6. ゴールデンチケットなどの攻撃名は概要を知っている程度でよい

> [!tip] 得点につながる覚え方
> Kerberosの問題では、**PC・KDC・サーバの3者の通信に番号を振り**、どれがKDCとの通信（88番）かを区別する。「認証に失敗する原因」を問われたら、まず**時刻のずれ**と**KDC・DNSに届くか**を疑う。
