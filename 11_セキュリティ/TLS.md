# TLS まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

## 1. TLSの基本（○）

- **TCP（Transmission Control Protocol）とアプリケーションの間**で、通信を安全にするプロトコル
- TLS（Transport Layer Security）が提供するもの
  - **機密性**：通信を暗号化する（盗聴の防止）
  - **完全性**：改ざんを検知する
  - **認証**：**サーバ証明書でサーバが本物か確認**する（必要ならクライアント証明書でクライアントも）
- バージョン：SSL3.0、TLS1.0、1.1は脆弱なので使わない。**TLS1.2／1.3**を使う
- TLSを使う主なプロトコルとポート

| プロトコル | ポート | 関連ノート |
|---|---|---|
| **HTTPS**（HTTP Secure） | **TCP 443** | |
| **wss**（WebSocket） | TCP 443 | [[WebSocket]] |
| **LDAPS**（LDAP over SSL/TLS） | TCP 636 | [[LDAP]] |
| **FTPS**（FTP over SSL/TLS、FTP：File Transfer Protocol） | TCP 990（暗黙的）／21＋AUTH TLS | [[FTP]] |
| **DoT**（DNS over TLS、DNS：Domain Name System） | TCP 853 | [[DNS]] |
| SMTPS（SMTP over SSL/TLS）／IMAPS（IMAP over SSL/TLS）／POP3S（POP3 over SSL/TLS） | 465／993／995 | |
| メール送信のSTARTTLS | 587 | |

- **STARTTLS**：平文で接続した後、途中からTLSに切り替える方式（SMTP（Simple Mail Transfer Protocol）、LDAP（Lightweight Directory Access Protocol）など）

## 2. ハンドシェイク（○）

### TLS1.3の流れ（概要）

```
クライアント                                   サーバ
   │── ClientHello（対応する暗号、鍵交換の値、SNI） ──→│
   │←─ ServerHello（選んだ暗号、鍵交換の値）           │
   │←─ 証明書、Finished（ここから暗号化）  ─────────│
   │── Finished ──────────────────────→│
   │════════ 暗号化されたアプリケーションデータ ════════│
```

- **鍵交換で共通鍵を作り、データはその共通鍵で暗号化する**（公開鍵暗号は鍵交換と署名に使う）
- TLS1.3は**1往復**（1-RTT）でハンドシェイクが終わる（1.2は2往復）
- TLS1.3は鍵交換を(**EC)DHE**だけにした → **前方秘匿性（PFS：Perfect Forward Secrecy）**：サーバの秘密鍵が後で漏れても、過去の通信は復号できない
- TLS1.2でRSAで鍵交換すると、秘密鍵が漏れたとき過去の通信まで復号される（△）

### SNI（○）

- ClientHelloに**接続先のホスト名**（SNI：Server Name Indication）を入れる → 1つのIP（Internet Protocol）アドレスで複数のHTTPSサイトを運用できる（サーバが証明書を選べる）
- **SNIは暗号化されない** → FW（Firewall）・SWG（Secure Web Gateway）は、復号しなくてもSNIでアクセス先を判定できる（URL（Uniform Resource Locator）フィルタリング）

## 3. サーバ証明書（◎）

- 中身：**サーバの公開鍵**、**ドメイン名（コモン名CN（Common Name）、SAN（Subject Alternative Name））**、有効期限、発行した認証局（CA：Certificate Authority）の**署名**
- クライアントが確認すること
  1. **接続先のホスト名と、証明書のCN／SANが一致するか**
  2. 有効期限内か
  3. **信頼できるルートCAまで、署名をたどって検証できるか**（証明書チェーン）
  4. 失効していないか（CRL（Certificate Revocation List）、**OCSP**（Online Certificate Status Protocol））
- **証明書チェーン**：サーバ証明書 → **中間CA証明書** → ルートCA証明書（端末・ブラウザに最初から入っている）
  - **サーバは、自分の証明書と一緒に中間CA証明書も送る**必要がある → 設定漏れで一部の端末だけエラーになる
- **ワイルドカード証明書**（`*.example.jp`）：1階層下の複数のホスト名で使える（`a.b.example.jp` には使えない）
- **失効確認**
  - **CRL**：失効した証明書の一覧をダウンロードする
  - **OCSP**：個々の証明書の状態を**OCSPレスポンダ**に問い合わせる → **クライアントからOCSPレスポンダへの通信をFWで許可**する必要がある
  - OCSPステープリング：サーバがOCSPの応答を代わりに取得して、ハンドシェイクで渡す（△）

## 4. 午後で問われるテーマと記述の型

### ◎ 証明書のホスト名の不一致

- 例：証明書は `www.example.jp` で発行されているのに、社内から**内部用のホスト名やIPアドレス**でアクセスする → 証明書エラー
- 対策：アクセスに使う名前を証明書のCN／SANに含める、**内部DNSで同じホスト名を内部のアドレスに解決させる**（スプリットDNS）
- 記述の型：「アクセスしたURLのホスト名と、サーバ証明書のコモン名が一致しないから」
- → [[DNS]]

### ◎ 負荷分散装置・リバースプロキシでのTLS終端

- **TLSの処理を負荷分散装置（LB：Load Balancer）で行う**（SSL（Secure Sockets Layer）オフロード）
  - サーバの負荷を減らせる
  - LBが**復号したHTTP（Hypertext Transfer Protocol）の中身（URL、Cookie）を見て振り分け・セッション維持**ができる
- 必要な作業：**サーバ証明書と秘密鍵をLBに導入する**（サーバから移す）
- LBとサーバの間は平文にするか、もう一度暗号化する
- 記述の型：「LBでTLSを終端することで、HTTPのCookieを参照してセッションを維持できるから」
- → [[負荷分散装置]]

### ◎ TLSインスペクション（プロキシ・SWGでの復号）

- HTTPSの中身（マルウェア、情報漏えい）を検査するため、プロキシ・SWGが**通信の途中でいったん復号**する
  - プロキシが端末に対して、**自分のCAで署名した証明書をその場で発行**して見せる（中間者として動く）
  - そのため、**端末にプロキシ・SWGのルート証明書をインストール**しておく必要がある。ないと証明書エラーになる
- 復号しない例外を設定することもある（金融機関、証明書を固定しているアプリなど）
- 記述の型：「端末がSWGの発行したサーバ証明書を検証できるよう、SWGのルート証明書を信頼済みとして登録する」

### ○ TLS-VPN（SSL-VPN）

- ブラウザや専用ソフトでTLSを使い、社外から社内にアクセスするリモートアクセスVPN（Virtual Private Network）
- **TCP 443**を使うので、出先のFW・プロキシを通りやすい（IPsec（Security Architecture for Internet Protocol）はUDP（User Datagram Protocol） 500／4500やESP（Encapsulating Security Payload）が必要）
- 方式：リバースプロキシ（Webアプリだけ）、ポートフォワーディング、L2フォワーディング（専用ソフトで全通信）
- クライアント証明書で端末を認証することもある
- → [[IPsec]]

### ○ クライアント証明書（相互認証）

- クライアントも証明書を提示し、サーバが検証する
- 会社が許可した端末だけを接続させる（ID・パスワードが漏れても、証明書のない端末からは接続できない）
- **EAP-TLS**（EAP-Transport Layer Security）も同じ考え方 → [[IEEE802.1X]]

### △ その他

- **HTTP/2**は実質TLSが前提。使うプロトコルはTLSのハンドシェイク中に決める（ALPN：Application-Layer Protocol Negotiation）
- **QUIC**（Quick UDP Internet Connections、HTTP/3）はUDP上でTLS1.3を使う → UDP 443をFWで許可するかが論点になる

## 5. 攻撃者の観点：どこを突くか

| 狙う所 | 攻撃のしかた | 成り立つ条件 |
|---|---|---|
| **証明書の検証** | 偽のサーバ証明書で**中間者攻撃**を行う | 利用者が証明書の警告を無視する、端末に**不正なルート証明書を入れさせる** |
| **TLSを終端した先の平文区間** | LBやSWGで復号された後の通信を盗聴する | LB〜サーバ間などが平文のまま、その区間に侵入できる |
| **秘密鍵** | サーバやLBの秘密鍵、SWGのCAの秘密鍵を盗む → なりすまし、通信の復号 | 秘密鍵の保管が甘い。PFSのない鍵交換なら**過去の通信まで復号**される |
| **古いバージョン・弱い暗号** | SSL3.0／TLS1.0などに**ダウングレード**させ、既知の脆弱性を突く | 古いバージョンや弱い暗号を無効にしていない |
| **失効確認** | 失効した（盗まれた）証明書を使い続ける | OCSPに届かないとき「失効していない」とみなして通す設定 |
| **暗号化そのもの** | マルウェアの通信や情報の持ち出しを**TLSの中に隠し**、FW・プロキシの検査をすり抜ける | 通信の中身を検査していない |

- 最後の項目は、**防御側がTLSインスペクションを行う理由**として午後で問われる

## 6. 防御側に必要な対策

| 立場・機器 | 対策 | 防げる攻撃 |
|---|---|---|
| **利用者・端末** | 証明書の警告が出たら接続しない。**信頼するルート証明書は管理者が配布**し、利用者に勝手に追加させない | 中間者攻撃 |
| **Webサーバ** | 応答に**HSTS**（HTTP Strict Transport Security）のヘッダを付け、ブラウザに常にHTTPSで接続させる（証明書の警告も無視できなくなる）→ [[HTTP]] | SSLストリッピング（HTTPへのダウングレード）、警告を無視した中間者攻撃 |
| **サーバ・LB** | **TLS1.2／1.3だけを許可**し、弱い暗号を無効にする。**PFSのある鍵交換**（ECDHE）を使う | ダウングレード、過去の通信の復号 |
| **サーバ・LB** | **秘密鍵を厳重に管理**する（アクセス権を絞る、専用の機器で保管）。LB〜サーバ間も必要なら再暗号化する | 秘密鍵の盗難、平文区間の盗聴 |
| **SWG・プロキシ** | **TLSインスペクション**で中身を検査する。端末にSWGのルート証明書を配布し、金融機関などは例外にする | TLSに隠れたマルウェア・情報漏えい |
| **FW** | 端末から**OCSPレスポンダへの通信を許可**し、失効確認ができるようにする | 失効した証明書の悪用 |
| **アクセス制御** | 社外からの接続（TLS-VPNなど）は**クライアント証明書**で端末を限定する | ID・パスワード漏えい時のなりすまし |

- 記述の型（ルート証明書の管理）：「利用者が任意のルート証明書を追加できると、不正な証明書を信頼して中間者攻撃を受けるおそれがあるから」
- 記述の型（TLSインスペクション）：「TLSで暗号化された通信に含まれるマルウェアを検知するため、SWGで復号して検査する」

## 7. 覚え方

- **TLSは「封筒（暗号化）＋封印（改ざん検知）＋身分証（証明書）」**
- **証明書のチェックは「名前・期限・発行元・失効」の4つ**
- **中間CA証明書は「紹介状」**：サーバは自分の身分証と一緒に紹介状も出す。忘れると一部の端末が信用しない
- **TLS終端は「LBに鍵を預ける」**：証明書と秘密鍵をLBに入れる
- **TLSインスペクションは「会社公認の中間者」**：だから会社のルート証明書を端末に入れる
- **1.3は「1往復、PFS必須」**
- **SNIは「封筒の宛名」**：中身は見えなくても宛名（ホスト名）は見える

## 8. 勉強の優先順位

1. 証明書のホスト名不一致によるエラーと対策を30〜40字で書けるようにする
2. LBでのTLS終端（証明書と秘密鍵の移設、Cookieでのセッション維持）
3. TLSインスペクションで端末にルート証明書が必要な理由
4. 証明書チェーンと中間CA証明書、OCSPの通信許可
5. TLSを使うプロトコルとポート番号（443、636、853など）
6. TLS-VPN、クライアント証明書
7. ハンドシェイクの詳細、PFS、QUICは概要を知っている程度でよい

> [!tip] 得点につながる覚え方
> TLSは**Webシステム、プロキシ・SWG、テレワーク（VPN）の問題で必ずと言っていいほど絡む**。午後では暗号の仕組みより、「**証明書と秘密鍵がどの機器にあるか」「端末にどのルート証明書が必要か**」を構成図で追いかける問題が多い。
