# TLS まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

## 1. TLSの基本（○）

- **TCP（Transmission Control Protocol）とアプリケーションの間**で、通信を安全にするプロトコル
- TLS（Transport Layer Security）が提供するもの
  - **機密性**：通信を暗号化する（盗聴の防止）
  - **完全性**：改ざんを検知する
  - **認証**：**サーバ証明書でサーバが本物か確認**する（必要ならクライアント証明書でクライアントも）
- バージョン：SSL3.0、TLS1.0、1.1は脆弱なので使わない。**TLS1.2／1.3**を使う
- TLSを使う主なプロトコルとポート

| プロトコル | ポート | 関連ノート |
|---|---|---|
| **HTTPS**（HTTP Secure、HTTP：Hypertext Transfer Protocol） | **TCP 443** | |
| **wss**（WebSocket） | TCP 443 | [[WebSocket]] |
| **LDAPS**（LDAP over SSL/TLS） | TCP 636 | [[LDAP]] |
| **FTPS**（FTP over SSL/TLS、FTP：File Transfer Protocol） | TCP 990（暗黙的）／21＋AUTH TLS | [[FTP]] |
| **DoT**（DNS over TLS、DNS：Domain Name System） | TCP 853 | [[DNS]] |
| SMTPS（SMTP over SSL/TLS）／IMAPS（IMAP over SSL/TLS）／POP3S（POP3 over SSL/TLS） | 465／993／995 | |
| メール送信のSTARTTLS | 587 | |

- **STARTTLS**：平文で接続した後、途中からTLSに切り替える方式（SMTP（Simple Mail Transfer Protocol）、LDAP（Lightweight Directory Access Protocol）など）

### TLSの層とIPsecとの違い（◎）

```
アプリケーション層   HTTP、SMTP、LDAP など
        ↕
     【TLS】        ← アプリのデータを暗号化してから、TCPに渡す
        ↕
トランスポート層     TCP
インターネット層     IP
```

- TCP/IPの4階層では、**トランスポート層（TCP）とアプリケーション層の間**。TLS専用の層はないので、本によって「アプリケーション層」「トランスポート層の上」と書き方が分かれる
- OSI（Open Systems Interconnection）の7階層では、セッション層〜プレゼンテーション層あたりとされることが多い。試験では「TCPとアプリケーションの間」と覚えれば十分
- 名前は「Transport Layer Security」だが、「トランスポート層の**上で**通信を守る」という意味で、トランスポート層そのものではない
- 層の位置の違いが、そのまま[[IPsec]]との特徴の違いになる

| | IPsec（Security Architecture for Internet Protocol） | TLS |
|---|---|---|
| 層 | **インターネット層（IP：Internet Protocol）** | **TCPとアプリケーションの間** |
| 守る範囲 | IPで運ぶ**すべての通信**をまとめて守る。アプリの対応は不要 | **TLSに対応したアプリの通信だけ**（HTTPS、LDAPSなど）。アプリごとに使う |
| 使うポート | UDP（User Datagram Protocol） 500／4500、ESP（Encapsulating Security Payload）（プロトコル番号50） | アプリごとのポート（HTTPSならTCP 443） |
| FW（Firewall）・プロキシの通りやすさ | 止められることがある | **TCP 443なので通りやすい** |

- 午後で「TLS-VPN（VPN：Virtual Private Network）を選んだ理由」を問われたら、表の下の2行（TCP 443で、出先のFW・プロキシを通りやすい）が答えになる
- TLSは基本的にTCPの上で動く。UDPで使う場合は、DTLS（Datagram Transport Layer Security）やQUIC（Quick UDP Internet Connections、HTTP/3、UDP 443）がある（△）
- 覚え方：**「IPsecは道路ごと守る（全部まとめて）、TLSは車ごと守る（アプリごと）」**

## 2. ハンドシェイク（○）

### TLS1.3の流れ（概要）

```
クライアント                                   サーバ
   │── ClientHello（対応する暗号、鍵交換の値、SNI） ──→│
   │←─ ServerHello（選んだ暗号、鍵交換の値）           │
   │←─ 証明書、Finished（ここから暗号化）  ─────────│
   │── Finished ──────────────────────→│
   │════════ 暗号化されたアプリケーションデータ ════════│
```

- **鍵交換で共通鍵を作り、データはその共通鍵で暗号化する**（公開鍵暗号は鍵交換と署名に使う）
- TLS1.3は**1往復**（1-RTT）でハンドシェイクが終わる（1.2は2往復）
- TLS1.3は鍵交換を(**EC)DHE**だけにした → **前方秘匿性（PFS：Perfect Forward Secrecy）**：サーバの秘密鍵が後で漏れても、過去の通信は復号できない
- TLS1.2でRSAで鍵交換すると、秘密鍵が漏れたとき過去の通信まで復号される（△）

### SNI（○）

- **SNI（Server Name Indication）**：ClientHelloの中に、**接続先のホスト名を平文で入れる**仕組み
- **必要な理由**：HTTPSでは、サーバはTLSハンドシェイクの時点で証明書を出す必要がある。しかし、どのサイトへのアクセスかを示すHTTPの**Hostヘッダ**は、ハンドシェイクの**後に**暗号化されて届く
  - SNIがないと、サーバはどのサイトの証明書を出せばよいかわからない → 昔は「1つのIPアドレスに1つのHTTPSサイト」しか置けなかった
  - SNIを見れば、サーバが証明書を選べる → **1つのIPアドレスで複数のHTTPSサイトを運用できる**

```
① TCP接続
② TLSハンドシェイク ← ClientHelloのSNIを見て、証明書を選ぶ
③ HTTPのリクエスト（Hostヘッダ） ← 暗号化されて、②の後に届く
```

**1つのアドレスで複数のHTTPSサイトを運用できるメリット**

| メリット        | 内容                                                                                                                              |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------- |
| IPv4アドレスの節約 | グローバルアドレスは数が少なく、費用もかかる。サイトごとに用意しなくて済む                                                                                           |
| 機器・費用の集約    | 1台の**負荷分散装置・リバースプロキシ**で、多数のドメインのTLS終端ができる。**CDN（Content Delivery Network）・クラウドのLB**（Load Balancer）は、この仕組みで多数の顧客サイトを同じアドレスで受けている |
| 復号せずに振り分け   | LBが**SNIを見るだけで**宛先サーバを選べる（TLSを終端しないパススルー方式）。秘密鍵をLBに置かなくてよい                                                                      |

**SNIが暗号化されないことの、実運用での利点**：通信を復号しなくても、**どのサイトに行こうとしているか**がわかる

| 場面 | 内容 |
|---|---|
| FW・SWG（Secure Web Gateway）・プロキシでのフィルタリング | TLSインスペクションをしなくても、SNIのホスト名で接続を禁止できる。**端末へのルート証明書の配布が不要**で、復号の処理負荷もかからない |
| TLSインスペクションの例外判定 | 「金融機関・医療のサイトは復号しない」という判定も、SNIを見て行う |
| アクセスログ | どのサイトにアクセスしたかを、復号せずに記録できる |
| LBでの振り分け | 上の表の「復号せずに振り分け」と同じ |

**注意点（試験で狙われる）**

- **SNIでわかるのは「ホスト名」だけ**。URL（Uniform Resource Locator）のパス（`/admin/` など）や中身は暗号化されている → SNIでできるのは**ホスト名単位**のフィルタリング。パス単位の制御やマルウェアの検査には、**TLSインスペクション**が必要
- プライバシー上は弱点：経路上の第三者に、アクセス先のホスト名が見える → SNIを暗号化する**ECH**（Encrypted Client Hello）が普及しつつある。ECHを使われると、SNIによるフィルタリングができなくなる（△）
- SNIに対応していない古い端末は、正しい証明書を受け取れず、証明書エラーになる（△）
- 覚え方：**「SNIは封筒の宛名。中身（パス・データ）は見えないが、宛名（ホスト名）だけで仕分けと検問ができる」**

## 3. サーバ証明書（◎）

- 中身：**サーバの公開鍵**、**ドメイン名（コモン名CN（Common Name）、SAN（Subject Alternative Name））**、有効期限、発行した認証局（CA：Certificate Authority）の**署名**

```
サーバ証明書
├─ サブジェクト（持ち主）
│    CN（コモン名）  = www.example.jp      ← 1つだけ
│    O（組織名）     = Example株式会社
├─ SAN（サブジェクト代替名）              ← 拡張領域。複数書ける
│    DNS名 = www.example.jp
│    DNS名 = example.jp
│    DNS名 = shop.example.jp
│    （IPアドレス = 192.0.2.10 も書ける）
├─ 公開鍵、有効期限
└─ 認証局（CA）の署名
```

- **CNからSANへの歴史**
  1. もとは、**CNにホスト名を書き**、ブラウザがそれと照合していた
  2. CNには1つしか書けないので、`www.example.jp` と `example.jp` の両方で使いたい、といった需要に応えられない
  3. そこで、複数の名前（ホスト名、IPアドレス、ワイルドカード）を書ける**SAN**が追加された
  4. 現在の主要なブラウザは**SANだけを照合**し、CNは見ない → CNと同じ名前もSANに必ず入れる
  - 過去問では「コモン名」で出ることが多く、記述の型「ホスト名とコモン名が一致しない」は今も使える。新しめの問題では「SANに登録する」形で問われる
- クライアントが確認すること
  1. **接続先のホスト名と、証明書のCN／SANが一致するか**
  2. 有効期限内か
  3. **信頼できるルートCAまで、署名をたどって検証できるか**（証明書チェーン）
  4. 失効していないか（CRL（Certificate Revocation List）、**OCSP**（Online Certificate Status Protocol））
- **証明書チェーン**：サーバ証明書 → **中間CA証明書** → ルートCA証明書（端末・ブラウザに最初から入っている）
  - **サーバは、自分の証明書と一緒に中間CA証明書も送る**必要がある → 設定漏れで一部の端末だけエラーになる
  - ルートCAは大事な鍵を守るため、サーバ証明書に直接は署名せず、間に中間CAをはさむ。**端末に最初から入っているのはルートCA証明書だけ**で、中間CA証明書は入っていない → サーバが送らないと「サーバ証明書 → ？」でたどれなくなる
  - **なぜ「一部の端末だけ」エラーになるのか**：PCの主要なブラウザは、以前ほかのサイトで受け取った中間CA証明書を覚えていたり、自動でダウンロードしたりして、足りない分を**自分で補える**ことがある。一部のスマートフォンや業務用の端末（組み込み機器など）は補う機能がなく、サーバから送られたものだけでたどろうとして失敗する（補う仕組みの詳細は△）
  - 証明書を**更新したとき**に起きやすい（中間CAが変わったのに古い中間CA証明書のまま、または入れ忘れた）
  - 午後で「一部の端末だけ証明書エラー」と出たら、まず**中間CA証明書の設定漏れ**を疑う
  - 記述の型：「PCのブラウザは中間CA証明書を保持・自動取得して検証できるが、一部の端末はその機能がなく、証明書チェーンをたどれないから」
- **ワイルドカード証明書**（`*.example.jp`）：1階層下の複数のホスト名で使える（`a.b.example.jp` には使えない）
- **失効確認**
  - **CRL**：失効した証明書の一覧をダウンロードする
  - **OCSP**：個々の証明書の状態を**OCSPレスポンダ**に問い合わせる → **クライアントからOCSPレスポンダへの通信をFWで許可**する必要がある
  - OCSPステープリング：サーバがOCSPの応答を代わりに取得して、ハンドシェイクで渡す（△）

## 4. 午後で問われるテーマと記述の型

### ◎ 証明書のホスト名の不一致

- 例：証明書は `www.example.jp` で発行されているのに、社内から**内部用のホスト名やIPアドレス**でアクセスする → 証明書エラー
- 対策：アクセスに使う名前を証明書のCN／SANに含める、**内部DNSで同じホスト名を内部のアドレスに解決させる**（スプリットDNS）
- 記述の型：「アクセスしたURLのホスト名と、サーバ証明書のコモン名が一致しないから」
- 「ドメイン名」より「**ホスト名（FQDN：Fully Qualified Domain Name）**」と書く（証明書に書くのは1台のサーバの名前）
- → [[DNS]]（スプリットDNSが必要な理由と記述の型）

### ◎ 負荷分散装置・リバースプロキシでのTLS終端（SSLオフロード）

- **SSL（Secure Sockets Layer）オフロード**：Webサーバが行っていたTLSの暗号化・復号を、**負荷分散装置（LB）やリバースプロキシが肩代わりする**こと。「オフロード」は「荷を降ろす」の意味。名前のSSLは昔の呼び方の名残で、中身はTLS。**TLS終端**とも呼ぶ

```
                 HTTPS（暗号化）           HTTP（平文）
利用者 ════════════════════→ [LB] ──────────→ Webサーバ1
                              ↑     ──────────→ Webサーバ2
                  ここでTLSを終端（復号）する
                  → 証明書と秘密鍵はLBに置く
```

| メリット | 内容 |
|---|---|
| ① サーバの負荷を減らす | ハンドシェイクや暗号の重い処理を、LB（専用のハードウェアを持つものもある）にまとめて任せる |
| **② HTTPの中身を見て処理できる（◎）** | 復号した後のHTTPを見て、**Cookieでのセッション維持**、**URLのパスによる振り分け**（`/api/` はAPI（Application Programming Interface）サーバへ、など）、WAF（Web Application Firewall）での検査ができる |
| ③ 証明書の管理を1か所にまとめる | サーバが何台あっても、証明書の更新はLBの1か所だけで済む |

- 一番問われるのは②。TLSのまま通すと、LBには中身が見えないので、Cookieでのセッション維持ができず、IPアドレスでしか振り分けられない
- 必要な作業：**サーバ証明書と秘密鍵をLBに導入する**（サーバから移す）。証明書のSANには、利用者がアクセスする名前（LBで受ける名前）を入れる
- 記述の型：「LBでTLSを終端することで、HTTPのCookieを参照してセッションを維持できるから」

| 注意点 | 内容と対策 |
|---|---|
| **LB〜サーバ間が平文になる** | その区間で盗聴されるおそれがある。必要なら、LBでもう一度暗号化してサーバに送る（再暗号化） |
| 秘密鍵がLBに集まる | LBが乗っ取られると影響が大きい。LBの管理・保護を厳重にする |
| サーバから利用者のIPアドレスが見えない | サーバに届く通信の送信元はLBのアドレスになる。LBがHTTPヘッダ（**X-Forwarded-For**）に、元の利用者のIPアドレスを入れて渡す（△） |

| 方式 | LBでの復号 | LBで見えるもの |
|---|---|---|
| **SSLオフロード（TLS終端）** | **する** | HTTPの中身（Cookie、URL） |
| 再暗号化 | して、もう一度暗号化する | HTTPの中身。サーバまで暗号化される |
| パススルー | **しない** | **SNIのホスト名**だけ |

- 覚え方：**「SSLオフロードは、LBに鍵を預けて、封筒を開けてもらう。開けるから中身（Cookie）で仕分けできる」**
- → [[負荷分散装置]]

### ◎ TLSインスペクション（プロキシ・SWGでの復号）

- HTTPSの中身（マルウェア、情報漏えい）を検査するため、プロキシ・SWGが**通信の途中でいったん復号**する
  - SWGは、相手サイト（Googleや銀行など）の秘密鍵を持っていない（持てない）
  - そこで、端末に対して**自分のCAで署名した証明書をその場で発行**して見せる（中間者として動く）
  - そのため、**端末にプロキシ・SWGのルート証明書をインストール**しておく必要がある。ないと証明書エラーになる
- **流れの整理**（身分証のたとえ：ブラウザは「名前」と「発行元」の両方を確認する受付係）
  1. ブラウザが信用するのは、**名前が一致し**、かつ**信用しているルートCAまでたどれる**証明書だけ。正規のCAが発行した本物でも、名前が違えば（例：evil.com）エラーになる
  2. SWGは、相手サイト（www.google.com）の本物の証明書と秘密鍵を持てない。公的なCAも、ドメインの持ち主でない会社には発行しない
  3. そこでSWGは、**会社専用の認証局（プライベートCA）として**、名前に「www.google.com」と書いた証明書を、その場で発行する。「ふり」をしているのは認証局の部分ではなく、**Googleの部分**（Googleになりすます）
  4. その証明書の発行元（会社のCA）は、端末の信頼済みの一覧（トラストストア）にないので、そのままでは証明書エラーになる
  5. そのため、**管理者が会社のCAのルート証明書を、全端末に配布**しておく（AD（Active Directory）のグループポリシーやMDM（Mobile Device Management）で一括配布）。利用者には追加させない（攻撃者のルート証明書を入れられるおそれがあるため）
  - 覚え方：**「端末は、名前の合った、知っている印鑑の身分証しか信用しない。インスペクションは、会社の印鑑で名前の正しい身分証を作るので、先に印鑑登録（ルート証明書の配布）が要る」**
  - 詳しい説明 → 10章「補足：TLSインスペクションで端末にルート証明書が必要な理由」
- 検査した後は、**必ず再暗号化**して本物のサイトへ送る。端末〜SWGと、SWG〜サイトの**TLSが2本**になる
- 復号しない例外を設定することもある（金融機関、証明書を固定しているアプリなど）。例外の判定にはSNIを使う
- 記述の型：「端末がSWGの発行したサーバ証明書を検証できるよう、SWGのルート証明書を信頼済みとして登録する」
- → [[ゼロトラスト・SASE]]（SWG）

### ◎ SSLオフロードとTLSインスペクションの違い

- どちらも「途中の機器で、TLSをいったん復号する」点は同じ。違いは、**誰のサーバの通信を、誰の鍵で復号するか**

```
【SSLオフロード】 自社のサーバを守る（外 → 内）
利用者 ══HTTPS══→ [LB] ──HTTP──→ 自社のWebサーバ
                   ↑ 自社サイトの本物の証明書と秘密鍵を持っている

【TLSインスペクション】 社員の通信を検査する（内 → 外）
社員の端末 ══TLS①══→ [SWG・プロキシ] ══TLS②══→ インターネット上の任意のサイト
                       ↑ 相手サイトの秘密鍵は持っていない
                         → 自分のCAで署名した証明書を、その場で作って端末に見せる
```

| | SSLオフロード | TLSインスペクション |
|---|---|---|
| 置く場所 | **サーバ側**（DMZ（DeMilitarized Zone）、データセンタ） | **利用者側**（社内からインターネットへの出口） |
| 復号する通信 | **自社のサイト**宛て（外 → 内） | インターネット上の**任意のサイト**宛て（内 → 外） |
| 使う証明書 | **自社サイトの本物の証明書と秘密鍵**（サーバから移す） | **SWGが自分のCAで、その場で作った証明書** |
| 立場 | 正規の**通信の終点**（サイトの持ち主が置いた） | **中間者**（会社公認） |
| 端末に必要なもの | **何もいらない**（本物の証明書なので、普通に検証が通る） | **SWGのルート証明書のインストール** |
| 目的 | サーバの負荷軽減、Cookieでのセッション維持、URLでの振り分け | マルウェアや情報漏えいの検査、URLのパス単位のフィルタリング |
| 復号後 | サーバまで平文、または再暗号化 | 検査したら**必ず再暗号化**（TLSが2本） |

- **一番大事な違い**：SSLオフロードのLBは、サイトの持ち主から**本物の秘密鍵**を預かっているので、端末から見ると本物のサーバと同じ。TLSインスペクションのSWGは相手サイトの秘密鍵を持てないので、自分で作った証明書を端末に信用させる必要がある → **インスペクションだけ、端末にルート証明書が必要**
- 覚え方
  - **SSLオフロード**：家の主人から**合鍵を預かった執事**。お客さんから見て、本物の家の人
  - **TLSインスペクション**：会社公認の**検問所**。相手の鍵は持っていないので、自分の印鑑（ルート証明書）を社員に信用してもらう

### ○ TLS-VPN（SSL-VPN）

- ブラウザや専用ソフトでTLSを使い、社外から社内にアクセスするリモートアクセスVPN
- **TCP 443**を使うので、出先のFW・プロキシを通りやすい（IPsecはUDP 500／4500やESPが必要）
- 方式：リバースプロキシ（Webアプリだけ）、ポートフォワーディング、L2フォワーディング（専用ソフトで全通信）
- クライアント証明書で端末を認証することもある
- → [[IPsec]]

### ○ クライアント証明書（相互認証）

- クライアントも証明書を提示し、サーバが検証する
- 会社が許可した端末だけを接続させる（ID・パスワードが漏れても、証明書のない端末からは接続できない）
- **EAP-TLS**（EAP-Transport Layer Security）も同じ考え方 → [[IEEE802.1X]]

### △ その他

- **HTTP/2**は実質TLSが前提。使うプロトコルはTLSのハンドシェイク中に決める（ALPN：Application-Layer Protocol Negotiation）
- **QUIC**（HTTP/3）はUDP上でTLS1.3を使う → UDP 443をFWで許可するかが論点になる

## 5. 攻撃者の観点：どこを突くか

| 狙う所 | 攻撃のしかた | 成り立つ条件 |
|---|---|---|
| **証明書の検証** | 偽のサーバ証明書で**中間者攻撃**を行う | 利用者が証明書の警告を無視する、端末に**不正なルート証明書を入れさせる** |
| **TLSを終端した先の平文区間** | LBやSWGで復号された後の通信を盗聴する | LB〜サーバ間などが平文のまま、その区間に侵入できる |
| **秘密鍵** | サーバやLBの秘密鍵、SWGのCAの秘密鍵を盗む → なりすまし、通信の復号 | 秘密鍵の保管が甘い。PFSのない鍵交換なら**過去の通信まで復号**される |
| **古いバージョン・弱い暗号** | SSL3.0／TLS1.0などに**ダウングレード**させ、既知の脆弱性を突く | 古いバージョンや弱い暗号を無効にしていない |
| **失効確認** | 失効した（盗まれた）証明書を使い続ける | OCSPに届かないとき「失効していない」とみなして通す設定 |
| **暗号化そのもの** | マルウェアの通信や情報の持ち出しを**TLSの中に隠し**、FW・プロキシの検査をすり抜ける | 通信の中身を検査していない |

- 最後の項目は、**防御側がTLSインスペクションを行う理由**として午後で問われる

## 6. 防御側に必要な対策

| 立場・機器 | 対策 | 防げる攻撃 |
|---|---|---|
| **利用者・端末** | 証明書の警告が出たら接続しない。**信頼するルート証明書は管理者が配布**し、利用者に勝手に追加させない | 中間者攻撃 |
| **Webサーバ** | 応答に**HSTS**（HTTP Strict Transport Security）のヘッダを付け、ブラウザに常にHTTPSで接続させる（証明書の警告も無視できなくなる）→ [[HTTP]] | SSLストリッピング（HTTPへのダウングレード）、警告を無視した中間者攻撃 |
| **サーバ・LB** | **TLS1.2／1.3だけを許可**し、弱い暗号を無効にする。**PFSのある鍵交換**（ECDHE）を使う | ダウングレード、過去の通信の復号 |
| **サーバ・LB** | **秘密鍵を厳重に管理**する（アクセス権を絞る、専用の機器で保管）。LB〜サーバ間も必要なら再暗号化する | 秘密鍵の盗難、平文区間の盗聴 |
| **SWG・プロキシ** | **TLSインスペクション**で中身を検査する。端末にSWGのルート証明書を配布し、金融機関などは例外にする | TLSに隠れたマルウェア・情報漏えい |
| **FW** | 端末から**OCSPレスポンダへの通信を許可**し、失効確認ができるようにする | 失効した証明書の悪用 |
| **アクセス制御** | 社外からの接続（TLS-VPNなど）は**クライアント証明書**で端末を限定する | ID・パスワード漏えい時のなりすまし |

- 記述の型（ルート証明書の管理）：「利用者が任意のルート証明書を追加できると、不正な証明書を信頼して中間者攻撃を受けるおそれがあるから」
- 記述の型（TLSインスペクション）：「TLSで暗号化された通信に含まれるマルウェアを検知するため、SWGで復号して検査する」

## 7. 覚え方

- **TLSは「封筒（暗号化）＋封印（改ざん検知）＋身分証（証明書）」**
- **証明書のチェックは「名前・期限・発行元・失効」の4つ**
- **中間CA証明書は「紹介状」**：サーバは自分の身分証と一緒に紹介状も出す。忘れると一部の端末が信用しない
- **TLS終端は「LBに鍵を預ける」**：証明書と秘密鍵をLBに入れる
- **TLSインスペクションは「会社公認の中間者」**：だから会社のルート証明書を端末に入れる
- **1.3は「1往復、PFS必須」**
- **SNIは「封筒の宛名」**：中身は見えなくても宛名（ホスト名）は見える

## 8. 勉強の優先順位

1. 証明書のホスト名不一致によるエラーと対策を30〜40字で書けるようにする
2. LBでのTLS終端（証明書と秘密鍵の移設、Cookieでのセッション維持）
3. TLSインスペクションで端末にルート証明書が必要な理由
4. 証明書チェーンと中間CA証明書、OCSPの通信許可
5. TLSを使うプロトコルとポート番号（443、636、853など）
6. TLS-VPN、クライアント証明書
7. ハンドシェイクの詳細、PFS、QUICは概要を知っている程度でよい

> [!tip] 得点につながる覚え方
> TLSは**Webシステム、プロキシ・SWG、テレワーク（VPN）の問題で必ずと言っていいほど絡む**。午後では暗号の仕組みより、「**証明書と秘密鍵がどの機器にあるか」「端末にどのルート証明書が必要か**」を構成図で追いかける問題が多い。

## 10. 補足：TLSインスペクションで端末にルート証明書が必要な理由（詳しい説明）

4章「TLSインスペクション」の「流れの整理」を、具体的に説明したもの。

### 前提：端末は「信用する認証局の一覧」を持っている

- Windows、macOS、スマホ、ブラウザには、最初から**信頼できるルートCAの証明書**が数十〜百数十個入っている（**トラストストア**）。DigiCert、GlobalSign などの公的な認証局
- ブラウザは、サーバから受け取った証明書の署名をたどり、**この一覧にあるルートCAに行き着けば**「本物」と判断する

```
サーバ証明書 → 中間CA証明書 → ルートCA証明書（端末の一覧にある？）
                                     ある → OK ／ ない → 証明書エラー
```

- 身分証のたとえ
  - **ブラウザ**：相手の身分証を確認する受付係
  - **証明書**：サーバの身分証
  - **ルートCA**：身分証を発行する役所。受付係は「国が発行した身分証だけ信用する」と決めている

### ブラウザは「名前」と「発行元」の両方を確認する

| 確認すること | 身分証のたとえ |
|---|---|
| **① 名前**：アクセスしたホスト名と、証明書のSANが一致するか | 身分証の名前が、会いに来た相手の名前と同じか |
| ② 期限：有効期限内か | 期限切れでないか |
| **③ 発行元**：信用するルートCAまでたどれるか | 国が発行したものか |
| ④ 失効：取り消されていないか | 紛失届が出ていないか |

- **全部OKのときだけ**接続を許す
- 例：攻撃者が自分のドメイン（evil.com）の証明書を、正規の認証局から正式にもらっても、社員がアクセスしたのが www.google.com なら、①の名前が一致しないので**証明書エラー**になる（「田中さんに会いに来たのに、身分証が鈴木さんのもの」と同じ）

### SSLオフロード：端末に何もいらない

```
LBが見せる証明書：「www.example.jp」  発行元：公的な認証局（DigiCert など）
                                         ↓ たどる
                                端末の一覧に最初から入っている → OK
```

- 自社サイトの証明書は、もともと**公的な認証局から正式に発行してもらったもの**。それをサーバからLBに移しただけ
- たとえ：窓口に立っているのはLBだが、**自社が国から正式にもらった身分証**を預かっている。受付係は「国が発行した、www.example.jp の身分証だ」と判断する → 準備は不要

### TLSインスペクション：他人のふりをするので、身分証を自作する

```
SWGが見せる証明書：「www.google.com」  発行元：SWGの認証局（会社のCA）
                                         ↓ たどる
                                端末の一覧に入っていない → 証明書エラー ✕
```

1. SWGは通信を復号するために、**端末に対して「www.google.com」の証明書を見せる**必要がある（Googleになりすます）
2. 本物のGoogleの証明書と秘密鍵は、Googleしか持っていない。公的な認証局も、ドメインの持ち主でない会社には発行しない
3. そこでSWGは、**会社専用の認証局（プライベートCA）として**、名前に「www.google.com」と書いた証明書を、その場で発行する
   - SWGは認証局の「ふり」をしているのではなく、本当に認証局の役割を持っている（会社のCAの秘密鍵で署名する）。「ふり」をしているのは**Googleの部分**
4. 端末から見ると、知らない認証局が署名した証明書なので、③の発行元の確認で**証明書エラー**になる
5. そこで、**会社のCAのルート証明書を端末の一覧に追加**する。たとえると、受付係に「うちの会社の印鑑が押してある身分証も、信用してOK」と登録しておく
   - 配布は**管理者が全端末に一括で行う**（ADのグループポリシー、MDMなど）。利用者に追加させない
6. これで、SWGが作った証明書は①名前も③発行元も満たすので、エラーが出なくなる

| | 見せる証明書の発行元 | 端末の一覧にあるか | 端末の設定 |
|---|---|---|---|
| SSLオフロード | **公的な認証局**（正式に発行された本物） | 最初からある | **不要** |
| TLSインスペクション | **SWGのCA**（その場で作ったもの） | ない | **SWGのルート証明書を追加する** |

### 裏返すと：本当に危ない場面（攻撃者の観点）

①名前と③発行元の両方を満たす偽の証明書が作れてしまうと、端末は素通りさせる。そうなるのは次の2つの場面

- **攻撃者が、端末に自分のルート証明書を入れてしまう** → どんなサイトの偽証明書も信用させられ、中間者攻撃ができる。だから、ルート証明書の追加は管理者だけが行う（5章・6章）
- **信用されている認証局が、間違って（または乗っ取られて）他人の名前で発行してしまう**。認証局は発行前にドメインの持ち主かを確認するが、過去には認証局が乗っ取られ、偽のGoogleの証明書が出回った事件もある（△）

- 覚え方：**「身分証は『名前』と『発行元』の両方を見る。オフロードは本物の身分証を預かるだけ。インスペクションは会社の印鑑で名前の正しい身分証を自作するので、先に印鑑登録（ルート証明書の配布）が要る」**
