# DNSリフレクタ攻撃 まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

## 1. 攻撃の基本（◎）

- **送信元IP（Internet Protocol）アドレスを被害者のアドレスに詐称**したDNS（Domain Name System）問い合わせを、多数のDNSサーバに送る
- DNSサーバは**被害者に応答を返してしまう** → 大量の応答で被害者の回線・サーバを埋め尽くす **DDoS（Distributed Denial of Service）攻撃**
- 別名：**DNSアンプ（amplification）攻撃**。小さな問い合わせで大きな応答を返させる＝**増幅**するため
- 登場人物

| 役割 | 正体 | 何が起きるか |
|---|---|---|
| 攻撃者 | ボットネット（乗っ取った多数の端末） | 送信元を詐称した問い合わせを送る |
| **踏み台**（リフレクタ） | **オープンリゾルバ**、権威DNSサーバ | 自分は悪くないのに攻撃に加担する |
| **被害者** | 詐称された送信元IPの持ち主 | 頼んでいない大量の応答が届く |

## 2. 攻撃者の観点：どこを突くか（◎）

| 狙う所 | 攻撃者のねらい |
|---|---|
| **UDP（User Datagram Protocol）であること** | ハンドシェイクがないので、送信元IPを被害者に詐称した問い合わせがそのまま成立する |
| **踏み台になるDNSサーバ** | 誰からの再帰問い合わせにも答える**オープンリゾルバ**、応答の大きいレコードを持つ**権威DNS**（DNSSEC（DNS Security Extensions）署名付き、ANY応答） |
| **増幅率** | 小さい問い合わせで大きい応答を返すタイプ（ANY、EDNS0（Extension Mechanisms for DNS version 0）、DNSSEC）を選び、少ない攻撃量で大きな被害を出す |
| **被害者の回線帯域** | 被害者のFW（Firewall）より**手前の回線**を埋める → 被害者は自組織の機器だけでは防げない |
| **自分の隠蔽** | 被害者に届くのは正規DNSサーバからの応答なので、攻撃者（ボットネット）を特定しにくい |
| **送信元詐称を許すネットワーク** | イングレスフィルタリングをしていない組織・ISP（Internet Service Provider）のボットを使う |

### 成り立つ理由

1. **DNSはUDP（53番）** → TCP（Transmission Control Protocol）のような3ウェイハンドシェイクがないので、**送信元IPを詐称しても問い合わせが成立する**
2. **応答が問い合わせよりずっと大きい**
   - ANYタイプの問い合わせ、EDNS0で大きな応答を許す、DNSSECの署名付きレコード
   - 数十バイトの問い合わせで数千バイトの応答 → **数十倍に増幅**
3. **誰からの再帰問い合わせにも答えるDNSサーバ（オープンリゾルバ）**がインターネット上に多数ある
4. 被害者から見ると、送ってくるのは**正規のDNSサーバ** → 攻撃者を特定しにくい

- 記述の型（詐称できる理由）：「DNSはUDPを用いるため、コネクションを確立せずに送信元IPアドレスを詐称した問い合わせを送れるから」
- 記述の型（増幅の仕組み）：「サイズの小さい問い合わせに対して、サイズの大きい応答を被害者に送らせるから」

## 3. 防御側に必要な対策（◎）：立場ごとに整理する

### 踏み台にならない（DNSサーバを運用する側）

| 対策 | 内容 |
|---|---|
| **オープンリゾルバにしない** | キャッシュDNSサーバは**社内（自組織）からの再帰問い合わせだけ**受け付ける（ACL（Access Control List）で送信元を制限） |
| **権威DNSとキャッシュDNSを分ける** | 外部公開する権威DNSは再帰問い合わせを受け付けない。社内用のキャッシュDNSは外部から問い合わせできない場所に置く |
| **RRL（Response Rate Limiting、応答レート制限）** | 権威DNSで、同じ宛先への同じ応答の回数を制限する（権威DNSはオープンリゾルバ対策だけでは踏み台を防げないため） |
| ANYへの応答を制限 | 大きな応答を返さない |

- 記述の型：「キャッシュDNSサーバが、社内からの再帰問い合わせだけに応答するよう設定する」
- 記述の型（分離する理由）：「外部からの問い合わせを受け付ける権威DNSサーバで再帰問い合わせに応答すると、踏み台に悪用されるから」

### 送信元の詐称をさせない（ネットワークを運用する側）

- **イングレスフィルタリング（BCP38）**：自組織から外へ出るパケットのうち、**送信元IPが自組織のアドレスでないもの**を、境界ルータ・FWで破棄する
- **uRPF**：受信したパケットの送信元IPへの経路が、受信したインタフェースを向いていなければ破棄する
- 自組織の端末がボットにされても、**詐称パケットを外に出さない** → 攻撃に加担しない
- 記述の型：「自組織のアドレス以外を送信元とするパケットを、外部へ送信しないようにする」

### 被害者として守る

- **自組織のFWで応答を遮断しても、回線自体はすでに埋まっている** → 自組織だけでは防げない（◎）
- 対策は**上流（ISP）**で行う
  - ISPやクラウドの **DDoS対策サービス**（攻撃通信を除去する、スクラビング）
  - 問い合わせていないDNS応答（宛先が送信元ポート53）を、ISP側でフィルタする
  - CDN（Content Delivery Network）で負荷を分散する
- 記述の型：「攻撃通信によりインターネット接続回線の帯域が埋まるため、自組織のFWより手前で遮断する必要があるから」

## 4. 午後で問われるテーマ

### ◎ DNSサーバの構成見直し

- 構成図に「外部向けDNSサーバが、社内の名前解決（再帰問い合わせ）も兼ねている」と書かれていたら、この攻撃の踏み台になる問題と考える
- 解答の流れ：**権威とキャッシュを分離** → 権威は再帰問い合わせを拒否 → キャッシュは社内からのみ許可、DMZ（DeMilitarized Zone）ではなく内部に置くか、FWで外からの問い合わせを遮断する
- → [[DNS]]

### ○ 似た攻撃との区別

| 攻撃 | 目的 | ポイント |
|---|---|---|
| **DNSリフレクタ攻撃** | **DDoS**（帯域を埋める） | 送信元詐称＋応答の増幅 |
| **DNSキャッシュポイズニング** | **偽の応答をキャッシュさせ、偽サイトへ誘導** | 対策は送信元ポートのランダム化、DNSSEC |
| DNS水責め攻撃 | 権威DNSの負荷を上げる | ランダムなサブドメインを大量に問い合わせる |

- 午前で取り違えさせる選択肢が出る → **「増幅・DDoS」ならリフレクタ、「偽の情報・誘導」ならポイズニング**

### ○ 同じ仕組みのリフレクション攻撃

- **UDPで、小さい要求に大きい応答を返すサービス**はどれも踏み台になる
  - **NTP**（Network Time Protocol、monlistコマンド）、SNMP（Simple Network Management Protocol）、SSDP（Simple Service Discovery Protocol）、memcached など
- 対策の考え方は同じ：外部からの要求に答えない、不要なサービスを止める、イングレスフィルタリング
- → [[NTP]]

## 5. 覚え方

- **「宛名を被害者に書いた、往復はがきの大量発送」**：小さいはがき（問い合わせ）を出すと、大きな返信（応答）が被害者に届く
- **成立条件は3つ：「UDP」「増幅」「オープンリゾルバ」** → 対策はそれぞれをつぶす（イングレスフィルタリング／ANY制限・RRL／再帰問い合わせの制限）
- **踏み台は「誰にでも答える」から使われる**：キャッシュDNSは身内にだけ答える
- **被害者は自分のFWでは守れない**：水道管（回線）が詰まってから蛇口（FW）を閉めても遅い

## 6. 勉強の優先順位

1. 攻撃の仕組み（送信元詐称、UDP、増幅）を30〜40字で書けるようにする
2. 踏み台にならない対策（オープンリゾルバ禁止、権威とキャッシュの分離）を構成図の上で説明できるようにする
3. 被害者の自組織FWで防げない理由と、ISP側の対策
4. イングレスフィルタリングの定義
5. キャッシュポイズニングとの区別
6. RRL、NTPなど他のリフレクション攻撃は名前を知っている程度でよい

> [!tip] 得点につながる覚え方
> この攻撃は**DNSサーバの設計問題（権威とキャッシュの分離、DMZへの配置）の理由づけ**として出ることが多い。「どのサーバが」「誰からの」「どの種類の問い合わせに」答えるべきかを、構成図に書き込んで考える。
