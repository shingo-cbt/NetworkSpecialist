# FW まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

## 1. FWの基本（◎）

- **FW（Firewall：ファイアウォール）**：ネットワークの境界で、**許可した通信だけを通し、それ以外を遮断する**装置
- 種類

| 種類 | 判断に使う情報 | ポイント | 出題度 |
|---|---|---|---|
| パケットフィルタリング（静的） | IP（Internet Protocol）アドレス、プロトコル、ポート番号 | 戻りの通信も**ルールで個別に許可**する必要がある | ○ |
| **ステートフルインスペクション** | 上記＋**通信の状態（セッション）** | 行きの通信を記録し、**その戻りを自動で許可**する。現在の主流 | ◎ |
| アプリケーションゲートウェイ | アプリケーション層の中身 | プロキシとして中継する | △ |
| **次世代FW（NGFW：Next Generation Firewall）**／UTM（Unified Threat Management） | **アプリケーションの種類**、利用者、URL（Uniform Resource Locator） | IPS（Intrusion Prevention System）、URLフィルタリング、ウイルス対策などを1台で行う | ○ |

- **WAF**（Web Application Firewall）との違い：WAFは**Webアプリケーションへの攻撃（SQLインジェクション、XSS（Cross-Site Scripting）など）をHTTP（Hypertext Transfer Protocol）の中身で検知**する。FWはアドレスとポートで止める（○）

## 2. フィルタリングルール（◎）

- 項目：**送信元アドレス、宛先アドレス、プロトコル、宛先ポート番号、動作（許可／拒否）**
- **上から順に評価し、最初に一致したルールを適用**する
- どのルールにも一致しない通信は**拒否**（最後に「すべて拒否」がある、暗黙の拒否）
- ◎の定番：構成図と通信の要件から、**ルール表の空欄（送信元・宛先・ポート）を埋める**
  - 例：外部 → DMZ（DeMilitarized Zone）のWebサーバ：TCP（Transmission Control Protocol） 443
  - 例：DMZのメールサーバ → 外部：TCP 25
  - 例：内部のキャッシュDNS（Domain Name System）サーバ → 外部：UDP（User Datagram Protocol）／TCP 53
- **ルールの順番**が問われる：狭い条件の許可・拒否を、広い条件のルールより上に置く

## 3. ゾーンとDMZ（◎）

| ゾーン | 置くもの | 基本方針 |
|---|---|---|
| 外部（インターネット） | − | 信頼しない |
| **DMZ** | **外部に公開するサーバ**（Web、メール、外部DNS、プロキシ） | 外部からは必要なポートだけ許可 |
| 内部（社内LAN（Local Area Network）） | 利用者の端末、社内サーバ | **外部から直接は入らせない** |

- DMZを分ける理由：公開サーバが乗っ取られても、**そこから内部へ直接入れない**ようにする
- **DMZ → 内部の通信は原則拒否**（必要な通信だけ例外で許可）
- 記述の型：「公開サーバが侵害された場合でも、内部ネットワークへの不正アクセスの被害を防ぐため」

## 4. ステートフルインスペクションの動き（◎）

- 行きの通信（TCPのSYN（Synchronize）など）を見て**セッション管理テーブル**に記録する → **戻りの通信はテーブルと一致すれば通す**
- 内→外の許可ルールだけ書けば、外からの応答は通る。**SYNなしで外から来たパケットは破棄**される
- UDP（DNSの応答など）も、送った問い合わせに対応する応答として一定時間通す
- **セッションには無通信タイマがある** → 長時間通信のないコネクションは削除される（WebSocketやSSH（Secure Shell）が切れる原因）→ [[TCP]]、[[WebSocket]]
- **行きと帰りが別のFWを通ると、帰りは破棄される**（非対称経路）→ [[ECMP]]、[[VRRP]]
- FTP（File Transfer Protocol）のようにデータコネクションを後から張るプロトコルは、中身を見て必要な通信を一時的に許可する（ALG（Application Level Gateway））→ [[FTP]]

## 5. 冗長化（○）

- **アクティブ／スタンバイ**：2台のうち1台で処理する。**セッション情報を同期**しておけば、切替後も通信が切れない
  - 同期していないと、切替時に通信中のセッションが全部切れる
- **アクティブ／アクティブ**：両方で処理するが、行きと帰りが別の機器を通らないように設計が必要
- 記述の型：「FW間でセッション情報を同期することで、切替後も既存の通信を継続できるため」

## 6. 午後で問われるテーマと記述の型

### ◎ ルール表を埋める・不足を見つける

- 通信の要件（誰が、どこへ、何で）を1つずつルールにする。DNS、メールの中継、OCSP（Online Certificate Status Protocol）、時刻同期などの**付随する通信を忘れない**
- 「通信できない原因」→ ルールの不足、順番の誤り、TCP／UDPの片方だけ許可

### ◎ 新しいサービスの導入による変更

- クラウド、SWG（Secure Web Gateway）、VPN（Virtual Private Network）を導入したときに、**追加・削除すべきルール**を問う
- 不要になったルールを**削除**する（残すと攻撃に使われる）

### ○ NAT（Network Address Translation）との組合せ

- FWでアドレス変換も行う場合、**ルールに書くアドレスが変換前か変換後か**（機器の仕様に従う）を問題文で確認する
- → [[NAT・NAPT]]

## 7. IDS・IPS（○）

- FWはアドレスとポートで通信を止めるが、**許可した通信の中に紛れた攻撃**は止められない → 通信の中身を見て攻撃を見つけるのがIDS（Intrusion Detection System）・IPS

| | IDS（侵入検知） | IPS（侵入防止） |
|---|---|---|
| 動き | 攻撃を**検知して通知**する（止めない） | 攻撃を**検知して遮断**する |
| 置き方 | **ミラーポート**やTAP（Test Access Point）で通信の**複製**を見る（経路の外） | **通信の経路の中**（インライン）に置く |
| 故障したとき | 業務の通信には影響しない | **通信が止まる**おそれ → 故障時は素通しにする機能（バイパス、フェイルオープン）や冗長化 |
| 誤検知したとき | 通知が出るだけ | **正規の通信まで遮断**してしまう |

- 検知の方式
  - **シグネチャ型**：既知の攻撃のパターンと照合する。**未知の攻撃は見つけにくい** → シグネチャを常に更新する
  - **アノマリ型**：普段と違う振る舞い（通信量、通信の種類）を検知する。未知の攻撃も見つけられるが、**誤検知が多い**
- 用語：**フォールスポジティブ（誤検知：正常を攻撃と判定）**、**フォールスネガティブ（検知漏れ：攻撃を見逃す）**
- **暗号化された通信の中身は見えない** → TLSインスペクションで復号してから検査する → [[TLS]]
- 置き場所の例：FWの内側（FWを通り抜けた通信を検査）、DMZの手前、サーバの手前
- 記述の型（IPSの注意点）：「インラインに設置するため、IPSの故障や誤検知によって正規の通信まで遮断されるおそれがあるから」
- 記述の型（IDSを選ぶ理由）：「ミラーポートで通信を監視するため、IDSが故障しても業務の通信に影響を与えないから」
- 次世代FW（NGFW）は、FWとIPSの機能を1台にまとめたもの

## 8. 攻撃者の観点：どこを突くか

| 狙う所 | 攻撃のしかた | 成り立つ条件 |
|---|---|---|
| **許可されているポート** | 443番（HTTPS：HTTP Secure）やDNSに**通信を偽装・トンネル**させ、外部と通信する（C&Cサーバとの通信、情報の持ち出し） | アドレスとポートだけで判断している。外向きの通信を広く許可している |
| **公開サーバ（DMZ）** | 脆弱性を突いて乗っ取り、**DMZから内部へ侵入**する（踏み台） | DMZ → 内部の通信を広く許可している |
| **送信元アドレスの詐称** | 外部から**内部のアドレスを送信元にした**パケットを送り、内部向けの許可ルールに一致させる | 外部から来た内部アドレスのパケットを破棄していない |
| **セッション管理テーブル** | SYNフラッドなどで**テーブルを埋め尽くし**、正規の通信を通らなくする | セッション数の上限、SYNの制限がない |
| **暗号化された通信** | TLS（Transport Layer Security）の中にマルウェアを隠し、検査をすり抜ける | 通信の中身を検査していない |
| **ルールの放置** | 使われなくなった許可ルール、広すぎる許可（any）を使う | ルールの定期的な見直しをしていない |

## 9. 防御側に必要な対策

| 対策 | 内容 | 防げる攻撃 |
|---|---|---|
| **必要最小限の許可** | 送信元・宛先・ポートを絞る。anyを使わない。**外向きの通信も制限**する（例：社内からのTCP 25は送信用メールサーバだけ） | トンネル、情報の持ち出し、マルウェアの拡散 |
| **DMZ → 内部の制限** | 必要な通信だけ許可する | 公開サーバを踏み台にした侵入 |
| **詐称パケットの破棄** | 外部インタフェースで**送信元が内部・プライベートアドレスのパケットを破棄**、内部から出る送信元が自組織以外のパケットも破棄（イングレス／エグレスフィルタリング） | 送信元の詐称、リフレクション攻撃への加担 |
| **NGFW・IPS** | アプリケーションの種類や攻撃パターンで判定する | 許可ポートを使った不正な通信 |
| **TLSインスペクション** | 暗号化された通信を復号して検査する → [[TLS]] | 暗号化に隠れたマルウェア |
| **DoS対策** | セッション数の上限、SYN Cookie、上流（ISP（Internet Service Provider））での対策 | セッション管理テーブルの枯渇 |
| **ログと見直し** | 拒否・許可のログを監視し、ルールを定期的に棚卸しする | 放置されたルールの悪用、攻撃の早期発見 |

- 記述の型（外向きの制限）：「マルウェアに感染した端末が外部の攻撃者のサーバと通信することを防ぐため」

## 10. 覚え方

- **FWは「関所」**：通行手形（ルール）にある者だけ通す。手形のない者は全員止める（暗黙の拒否）
- **ルールは「上から順に、最初に一致したもの」**
- **ステートフルは「行きを覚えて、帰りは顔パス」**：行きと帰りが別の関所だと、帰りは止められる
- **DMZは「外向けの応接室」**：客（外部）は応接室までは入れるが、執務室（内部）には入れない
- **攻撃者は「開いている門（許可ポート）」と「応接室（DMZ）」を狙う**

## 11. 勉強の優先順位

1. 構成図と要件からフィルタリングルールの表を埋められるようにする（付随する通信も含めて）
2. ステートフルインスペクションの仕組みと、非対称経路・無通信タイマの問題
3. DMZを設ける理由と、DMZ → 内部を制限する理由を30〜40字で書けるようにする
4. FWの冗長化とセッション同期
5. 攻撃者が狙う点と、外向きの通信の制限・詐称パケットの破棄
6. NGFW、WAF、UTMは違いを一言で言える程度でよい

> [!tip] 得点につながる覚え方
> FWは**ほぼすべての構成問題に登場する**。午後でルール表が出たら、通信の要件を「送信元 → 宛先：プロトコル／ポート」の形で1行ずつ書き出し、**戻りの通信はステートフルなら書かない**、**DNS・時刻同期・証明書の失効確認など付随する通信を忘れない**、の2点を確認する。
