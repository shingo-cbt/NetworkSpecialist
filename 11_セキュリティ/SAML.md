# SAML まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

令和5年春 午後Ⅱ 問2「ECサーバの増強」で、SAMLのリダイレクト、IdPの公開鍵証明書の登録、改ざんできない理由などが問われている。

## 1. SAMLの基本（○）

- **SAML（Security Assertion Markup Language）**：**異なる組織・サービスの間でシングルサインオン**（SSO（Single Sign-On））を実現する仕組み。認証の結果をXML（Extensible Markup Language）形式で受け渡す
- 登場人物

| 役割                         | 正体                         | 仕事                                       |
| -------------------------- | -------------------------- | ---------------------------------------- |
| **IdP（Identity Provider）** | 認証サーバ（社内の認証基盤、クラウドの認証サービス） | **利用者を認証し、「この人は認証済み」という証明（アサーション）を発行**する |
| **SP（Service Provider）**   | 利用したいクラウドサービス、Webアプリケーション  | アサーションを**検証**して、ログインさせる                  |
| 利用者                        | ブラウザ                       | IdPとSPの間を、**リダイレクト**で行き来する               |

- 利点
  - 利用者は**IdPで1回ログイン**すれば、複数のSPを使える
  - **SPにパスワードを渡さない・登録しない**（SPから漏れない）
  - IdPでアカウントを止めれば、**全SPの利用をまとめて止められる**（退職者の管理）
  - IdPで**多要素認証**をかければ、全SPに効く

## 2. 認証の流れ（SP起点）（◎）

```
利用者（ブラウザ）            SP（クラウドサービス）             IdP（認証サーバ）
   │── ① アクセス ─────────→│
   │←─ ② IdPへリダイレクト（認証要求）│
   │── ③ 認証要求 ──────────────────────────────→│
   │←─ ④ ログイン画面 → ID・パスワード、多要素認証 ─────│
   │←─ ⑤ 署名付きアサーションを持たせてSPへ送らせる ────│
   │── ⑥ アサーション ───────→│
   │                  ⑦ IdPの公開鍵で署名を検証 → ログイン成功
```

- **IdPとSPは直接通信しない**。**利用者のブラウザを経由**してやり取りする
  - → SPからIdPに直接届かない構成（IdPが社内にある）でも使える
- 事前の準備：**SPとIdPの間で信頼関係を結ぶ**
  - SPに**IdPの公開鍵証明書**（とIdPの識別子、URL（Uniform Resource Locator））を登録する
  - IdPにSPの情報（識別子、アサーションの送り先）を登録する
- ②でSPがリダイレクト先のIdPを決めるには、**利用者の所属組織**（どのIdPを使うか）の情報が必要（令和5年春 午後Ⅱ 問2の解答）
- **「リダイレクトで行き来する」の意味**：SPやIdPが「別の場所に行って」と返すと（HTTP（Hypertext Transfer Protocol）のリダイレクト）、**ブラウザが自動でその場所にアクセスし直す**。この仕組みで、**ブラウザに書類を運ばせる**
  - ②：SPが、**認証要求**を持たせて、ブラウザをIdPへ行かせる
  - ⑤：IdPが、**署名付きアサーション**を持たせて、ブラウザをSPへ戻らせる
  - たとえ：窓口（SP）で「身分証明が要ります」と言われ、**紹介状**（認証要求）を持って役所（IdP）へ行く。本人確認を受け、**印鑑付きの証明書**（アサーション）をもらって窓口に戻り提出する。窓口と役所は電話で話さず、**お客さん（ブラウザ）が書類を運ぶ**
- **FW（Firewall）で許可が必要な通信**：**端末（ブラウザ）→ IdP** と **端末 → SP** のHTTPS（HTTP Secure）。**SP → IdP の通信は不要**（直接通信しないため）
- 試験で問われる範囲：①〜⑦の流れの順番と、⑤で受け渡すもの（署名付きアサーション）の穴埋め（◎）、IdPとSPが直接通信しないこと（◎）、SPに登録するIdPの公開鍵証明書（◎）、どのIdPに送るかを決める所属組織（○）。リダイレクトの細かい方式（302、自動送信のPOSTフォームなど）は不要
- 覚え方：**「SAMLのリダイレクトは、ブラウザにお使いを頼むこと。紹介状を持って役所へ、証明書を持って窓口へ。窓口と役所は直接話さない」**

## 3. なぜ安全か（◎）

- アサーションには**IdPの秘密鍵でディジタル署名**が付いている
  - SPは**IdPの公開鍵**で署名を検証する → **信頼関係のあるIdPが発行したこと**と、**改ざんされていないこと**を確かめられる
  - 利用者がアサーションを書き換えると署名が合わなくなる。正しい署名を作るには**IdPの秘密鍵が必要**
- 記述の型（改ざんできない理由）：「アサーションはIdPの秘密鍵で署名されており、利用者はIdPの秘密鍵を持っていないため、改ざんすると署名の検証に失敗するから」
- 記述の型（SPに登録する情報）：「IdPの公開鍵証明書」
- アサーションには**有効期間**がある → IdPとSPの**時刻がずれると検証に失敗**する → [[NTP]]

## 4. 午後で問われるテーマ

### ◎ クラウドサービスのSSO

- 社内の認証基盤（IdP）とクラウドサービス（SP）をSAMLで連携し、社内のIDで使えるようにする
- **SP側のローカルログイン（ID・パスワード）を無効にする** → IdPを経由しないログインができないようにする

### ○ ゼロトラストとの関係

- IdPで、利用者・端末の状態・場所を確かめてからアサーションを発行する（条件付きアクセス）→ [[ゼロトラスト・SASE]]

### △ OAuth・OpenID Connectとの違い

- **OAuth**：**認可**（サービスに、利用者のデータへのアクセス権を渡す）の仕組み
- **OpenID Connect**：OAuthの上で**認証**を行う仕組み。スマートフォンのアプリなどで使う
- ネスペでは「SAMLは認証の結果（アサーション）をXMLで渡すSSO」と区別できればよい（詳細は情報処理安全確保支援士試験の範囲）

## 5. 攻撃者の観点：どこを突くか

| 狙う所              | 攻撃のしかた                                | 成り立つ条件                        |
| ---------------- | ------------------------------------- | ----------------------------- |
| **IdPのID・パスワード** | フィッシングで盗む → **全SPに一度に入れる**（SSOの裏返し）   | 多要素認証がない                      |
| **ログイン後のセッション**  | ブラウザのCookie（ログイン状態）を盗んで、認証を飛ばして使う     | セッションの有効期間が長い、端末がマルウェアに感染している |
| **IdPの署名用の秘密鍵**  | 盗めば、**任意の利用者のアサーションを偽造**できる           | 秘密鍵の保管が甘い                     |
| **SPの検証の不備**     | 署名を検証しない、宛先・有効期間を確かめないSPに、偽のアサーションを送る | SPの実装・設定の誤り                   |
| **IdPを経由しない入口**  | SPに残ったローカルアカウント（ID・パスワード）でログインする      | SPのローカルログインが有効のまま             |

- **補足：ログイン後のセッション（Cookie）は2か所にできる**
  - **SPのCookie**：⑦でログインに成功すると、SPが自分のセッションのCookieを発行する。ここから先は通常のログインと同じで、アサーションはもう使わない → 盗まれると**そのSPだけ**に入られる
  - **IdPのCookie**：④でIdPにログインすると、IdPもセッションのCookieを発行する（2つ目のSPでID・パスワードを聞かれないのはこのため）→ 盗まれると**全SP**に認証なしで入られる（SSOの裏返しで、被害が大きい）
- **補足：多要素認証でも防げない**
  - 多要素認証は**ログインの瞬間**に本人かを確かめる仕組み。Cookieを盗む攻撃は**ログインが終わった後**の状態を使うので、多要素認証を飛ばせてしまう
  - そのため、セッションの有効期間を短くする、重要な操作の前に再認証させる、端末の状態や接続元の変化を確かめる、といった対策が必要（下の表の「セッションの管理」）
- 覚え方：**「SSOが守るのは入口（ログインの瞬間）だけ。中に入った後の通行証（Cookie）は普通のログインと同じく盗まれうる。IdPの通行証は、全部の部屋の合鍵」**

## 6. 防御側に必要な対策

| 対策 | 内容 | 防げる攻撃 |
|---|---|---|
| **IdPで多要素認証** | すべてのSPに効く | 盗んだパスワードでのログイン |
| **秘密鍵の厳重な管理** | IdPの署名用の秘密鍵を守る（アクセス権の限定、専用の機器） | アサーションの偽造 |
| **SPでの検証の徹底** | 署名・発行者・宛先・有効期間を必ず検証する | 偽のアサーション |
| **ローカルログインの無効化** | IdPを経由しないログインを禁止する | IdPの迂回 |
| **セッションの管理** | セッションの有効期間を短くする、端末の状態を確かめる | セッションの乗っ取り |
| **時刻同期** | IdPとSPの時刻をNTP（Network Time Protocol）で合わせる | （正規の利用者が失敗する問題の防止） |

## 7. 覚え方

- **SAMLは「IdPが発行する、ハンコ付きの入館証（アサーション）」**：SPはハンコ（署名）をIdPの公開鍵で確かめるだけ
- **IdPとSPは直接話さない。利用者（ブラウザ）が入館証を運ぶ**
- **SPに登録するのは「IdPの公開鍵証明書」**
- **改ざんできないのは「IdPの秘密鍵がないから」**
- **SSOは便利な分、IdPのパスワードが漏れると全部やられる → 多要素認証**

## 8. 勉強の優先順位

1. SAMLの流れ（SP → IdP → SPのリダイレクト）と、IdP・SPの役割を説明できるようにする
2. 改ざんできない理由と、SPに登録する情報を30〜40字で書けるようにする
3. SSOの利点（パスワードをSPに渡さない、一元的な停止）
4. 攻撃者の観点と対策（多要素認証、ローカルログインの無効化）
5. OAuth・OpenID Connectとの違いは一言で言える程度でよい

> [!tip] 得点につながる覚え方
> SAMLの問題では、**利用者・SP・IdPの3者の間の矢印**を書き、**アサーションを誰が作り（IdP、秘密鍵で署名）、誰が確かめるか**（SP、公開鍵で検証）を押さえる。設問のほとんどはこの関係から答えが出る。
