## 3. 設問ごとの解説

### 設問1(1)(2)　a：ゾーン転送　b：SMTP　c：DNS1
- a：NOTIFYを受けたセカンダリは、それを契機に**ゾーン転送**を行う
- b：MGWとMSVの間はメールの転送 ＝ SMTP
- c：項番3「DNS3 → ［c］」：セカンダリのDNS3が、プライマリの**DNS1**にゾーン転送を要求する

### 設問1(3)　公開ゾーン情報の更新通知
| 項番 | 送信元 → 宛先 | 中身 |
|---|---|---|
| 3 | DNS3（セカンダリ）→ DNS1（プライマリ） | ゾーン転送の要求（データは戻りの通信で流れる） |
| 4 | DNS1（プライマリ）→ DNS3（セカンダリ） | **NOTIFY**：公開ゾーン情報が更新されたことの通知 |
- FWはステートフルなので、要求の戻り（ゾーンのデータ）は項番3で通る。プライマリから**始める**通信だけが、別の行に要る

### 設問1(4)　条件：送信元が少数の場合　理由：送信元は、DNSのキャッシュが生存している間、宛先を変えないから
- DNSラウンドロビンは、問い合わせのたびに返すアドレスの順番を変える
- でも送信元は、一度引いた答えを**キャッシュの生存時間**（TTL）の間使い続ける
- 送信元が多ければ、それぞれが違う答えをキャッシュするので、全体ではばらける（PC → MSVの通信）。**送信元が少ない**（MGW 2台だけ）と、ばらけずに偏り、TTLの間続く
- 採点講評：「PCからMSVへの通信では、DNSキャッシュが介在しても、それを理由とした負荷の偏りは生じない。この対比に気付いてほしい」

### 設問2(1)　d：新MSV1　e：新MSV2
- 新MSV1と新MSV2に、VRRPを2グループ設定する
  - VRRPg1（VIP1）：新MSV1が優先度高 → 普段は新MSV1がマスタ
  - VRRPg2（VIP2）：新MSV2が優先度高 → 普段は新MSV2がマスタ
- 両方とも働き（Act-Act）、片方が故障すると、もう一方が両方のVIPを持つ

### 設問2(2)　msvc：VIP1、msvc：VIP2
- PCはmsvcを引く → DNSラウンドロビンでVIP1とVIP2を交互に返す → アクセスが分散する
- 返すのが**仮想IPアドレス**なので、片方が故障してもVRRPで引き継がれ、どちらのアドレスでも届く（実IPアドレスを返すと、故障した方に送った通信は届かない）

### 設問3(1)　機器名：FW　設定変更内容：新MSVとMGWとの間のSMTP通信を、双方向とも許可する。
- MGWはDMZ、MSVは社内 → 間に**FW**がある。表1のルールは旧MSVのアドレスしか許可していない
- 移行中は、MGW → 新MSV（社外から社内へ）、新MSV → MGW（社内から社外へ）の両方が要る

### 設問3(2)　送信元：変更を実施済みの社員 又は 社外　宛先：未変更社員
- 移行中は、新MSVを使う社員（変更済み）と旧MSVを使う社員（未変更）が混在する
- 変更済みの社員や社外からのメールは新MSVに届く。宛先が**未変更社員**なら、MBOXは旧MSVにある → 新MSVもLDAPを見て、旧MSVに転送する必要がある（下線②）

### 設問3(3)　(A)：新MSV → 旧MSV　(B)：旧MSV
```
(ア) 社外 → 未変更社員：送信元のメールサーバ → MGW → 新MSV（VIP1） → 旧MSV
(イ) 未変更社員 → 社外：PC → 旧MSV → MGW → 宛先のメールサーバ
```

### 設問3(4)　申請者のメールアドレスに対応するメールサーバが、新MSVに変更される。
- LDAPには「メールアドレスと、そのMBOXを収容するMSV」の対応が登録されている（現行NWの仕様(2)）
- 社員が申告すると、その人の対応先が旧MSVから**新MSV**に変わる → 以後のメールは新MSVのMBOXに届く

| 設1(4) | 知識の取り違え | 偏りの理由はキャッシュ（TTL）。SOAのリフレッシュと混同。条件（送信元が少数）を考えていない |
| 設2(1) e | 当てはめ漏れ | VRRPを組むのは新MSV同士（図2） |

| 設3(1) | 当てはめ漏れ（表1） | 表1のFWのルールが旧MSVのアドレスだけになっていることを拾っていない |
| 設3(2)(3) | 読み方 | 三者（社外、変更済み、未変更）の転送経路を図3に書き込んでいない |

## 5. 確認するべき観点・知識

- **プライマリ → セカンダリはNOTIFY、セカンダリ → プライマリはゾーン転送の要求**（FWのルールの向き）
- **DNSラウンドロビンが偏る条件＝送信元が少数**。理由＝送信元はキャッシュ（TTL）の間、宛先を変えない
- **VRRPを2グループ組み、それぞれの仮想IPアドレスをDNSラウンドロビンで返す＝Act-Actの冗長構成**。DNSで返すのは仮想IPアドレス
- **サーバを入れ替えたら、FWのルールのアドレスも変える**（表の送信元・宛先を確かめる）
- **並行稼働の移行は、関係者ごと（社外、変更済み、未変更）の転送経路を図に書き込む**
