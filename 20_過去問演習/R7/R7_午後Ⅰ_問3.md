## 3. 設問ごとの解説

### 設問1(1)　複数機器のログを時系列で確認するため
- 根拠：下線①「社内のネットワーク機器，サーバ及びPCの時刻補正に利用」と、「syslogサーバに保存しているログは，…障害発生時の原因分析に利用」、設問の「ログ解析に着目して」
- 時刻がずれていると、機器ごとのログを並べたときに前後関係が分からない
- 「タイムスタンプの整合性」は、時刻をそろえる**手段**の言い換え。聞かれているのは**目的**なので、「時系列で確認するため」まで書く

### 設問1(2)　登録したFQDNやIPアドレス宛ての通信をブロックするため／Webサイトへのアクセス履歴の確認のため（又は、利用者認証を行うため）
- 指定は「**本文中の字句を用いて**」。本文の中から、プロキシサーバが担っている役割を探す
  - 「プロキシサーバは…登録したFQDNやIPアドレス宛ての通信をブロックする」
  - 「syslogサーバは，③プロキシサーバ…のアクセスログ…を保存」「業務用サーバやWebサイトへのアクセス履歴の確認…に利用」
  - 「認証サーバは，プロキシサーバ…の接続時にRADIUSプロトコルを用いて利用者認証を行っている」
- 「DMZに限定する」は一般論としては正しいが、本文に書かれていない

### 設問1(3)　L3SWのDHCPリースログ
- 根拠：「内部セグメントには，PCが設置されており，L3SWのもつDHCPサーバ機能でIPアドレスなどが割り当てられている」と、下線③のログの一覧（「L3SWのDHCPリースログ」）
- FWの通信ログには、送信元としてPCのIPアドレスが残る。でも、PCのIPアドレスはDHCPで割り当てられるので、日によって変わる
- だから、**その時刻にそのIPアドレスを使っていたPC**を、DHCPのリースログ（IPアドレスとMACアドレスの対応）で特定する
- 答えは「本文中の字句で」なので、一覧にある名前（L3SWのDHCPリースログ）をそのまま書く

### 設問1(4)　a：syslogサーバ　b：認証サーバ
- a：DMZ → ［a］のUDP/514 → syslog（DMZのプロキシ・NTPサーバのログを送る）
- b：プロキシサーバ → ［b］のUDP/1812 → RADIUSの認証 → 認証サーバ

### 設問1(5)　c：10080　d：443
- c：「プロキシサーバはTCP/10080で接続を待ち受ける」
- d：K社SaaSにはHTTPSで直接接続 → TCP/443

### 設問2(1)　SWGサービスのルート証明書
- 根拠：下線④「SWGサービスはHTTPS通信のコンテンツを調査する機能をもつ」
- HTTPSの中身を調べるには、SWGがいったん復号する（TLS（Transport Layer Security）インスペクション）。SWGはWebサイトの代わりに自分で証明書を作って端末に見せるので、その証明書を信頼させるために、**SWGサービスのルート証明書**を端末に入れておく（TLS.md の補足）

### 設問2(2)　C&Cサーバ
- 隔離環境（サンドボックス）でマルウェアを動かすと、攻撃者の指令サーバ（C&Cサーバ）へつなごうとする通信が観察される

### 設問3(1)　2、7
- 根拠：下線⑥「フォワードプロキシサーバの機能停止に伴ってFWの許可ルールを削除」
- フォワードプロキシとして使っていたルールを、表1から探す
  - 2：プロキシサーバ → インターネット（TCP/80、443）：PCの代わりに外へ出る通信 → **要らない**
  - 7：内部セグメント → プロキシサーバ（TCP/10080）：PCがプロキシに接続する通信 → **要らない**
  - 3：プロキシサーバ → 認証サーバ（UDP/1812）：利用者認証。リバースプロキシになっても、R-PCからの接続で利用者認証をするので**残す**
- ルールを1つずつ「この通信は、変更後も誰が使うか」で確かめる

### 設問3(2)　(B)，(A)，(H)，(I)，(E)，(I)，(K)
- 根拠：下線⑦の社内PCの経路「(G)，(F)，(I)，(H)，(J)」と、「ソフトEは…HTTP及びHTTPSの通信をSWGサービスのTCP/443ポート宛てに中継」、C主任「業務用サーバ…には，SWGサービスを経由して通信させる」
- R-PC（B）→ ソフトE（A）→ **SWGサービス（H）** → FW（I）→ リバースプロキシ（E）→ FW（I）→ 業務用サーバ（K）
- 下線⑦が、「PC → ソフトE → … → SWGサービス → 宛先」というお手本の形になっている。**お手本の経路の形をなぞる**と、(H)を落とさない

### 設問3(3)　送信元：内部セグメント 又は ソフトE　宛先：SWGサービス　TCP/443
- 根拠：下線⑧「PCがSWGサービスへ接続するための許可ルール」と、「ソフトEは…SWGサービスのTCP/443ポート宛てに中継」

### 設問3(4)　アクセスを許可する送信元をSWG-GIPに変更する。
- 根拠：「K社SaaSでは，アクセスを許可する送信元をJ社のグローバルIPアドレスだけに制限」と、「SWGサービスが中継する際，送信元アドレスをSWG-GIPに変換する」
- SWG経由になると、K社SaaSに届く送信元はSWG-GIPになる → 許可する送信元をSWG-GIPに変える

### 設問3(5)　FWの負荷軽減／RTTの短縮／可用性の向上
- 根拠：下線⑩「通信の経路を考慮すると業務用サーバのプライベートIPアドレスは直接接続リストに登録した方が良い」
- 社内のPCが社内の業務用サーバにつなぐのに、SWGサービス（インターネットの向こう）まで行って戻ってくると、遠回りになる
- 直接接続リストに入れると、社内で直接つながる → **経路が短くなる** → FWや回線を通らないので負荷が減る、往復時間（RTT）が短くなる、SWGやインターネットが止まっても使える
- 聞かれているのは「**利点**」。「SWGを経由しない」は、利点を生む**やり方**の方

| 設3(5) | 着地点のずれ | 「何をするか」を書き、「何が良くなるか」（利点）を書いていない |

## 5. 確認するべき観点・知識

- **「本文中の字句を用いて」は、本文から言葉を探して使う**：自分の知識で書かない
- **目的・利点を聞かれたら、一段上まで書く**：時刻をそろえる → 時系列で確認できる。経路が短くなる → 負荷が減る、遅延が減る
- **ログでPCを特定するときは、IPアドレスとPCの対応が変わることを考える** → DHCPのリースログ（認証ログ、プロキシのログと組み合わせることもある）
- **ルールを削除する設問は、1行ずつ「変更後もその通信を誰が使うか」で確かめる**
- **経路を答える設問は、本文にあるお手本の経路の形をなぞる**（3回続けて経路のたどり漏れ）
