## 3. 設問ごとの解説

### 設問1　a：共有鍵　b：ルータ　c：コスト　d：ダイクストラ　e：172.16.0.0
- a：IPsec VPNの認証用の「事前**共有鍵**」（今日IPsec.mdに整理した論点）
- b・c：Type1はルータLSA。エリア内のルータのリンクの情報で、メトリック（コスト）を含む
- d：OSPFはダイクストラ（SPF）アルゴリズムで最短経路を計算する
- e：表1のa〜g（172.16.0.0〜172.16.12.127）をまとめると **172.16.0.0/16**

### 設問2　OSPFへデフォルトルートを導入する。
- FWには静的デフォルト経路しかない → OSPFで全ルータに配らないと、本社以外のルータはインターネットへの経路を知らない
- FWで、静的デフォルト経路をOSPFに配布（再配布）する設定

### 設問3(1)　ルーティングテーブルサイズを小さくする。
- a〜gの7本の経路を、172.16.0.0/16の1本にまとめる → 本社側の**経路の数**（テーブルサイズ）が減る。支社の経路の変化が本社に伝わりにくくなる効果もある

### 設問3(2)　ルータ
- 本社のルータは、エリア0（本社）とエリア1（支社・広域イーサ網）の境界 → **ABR**。OSPFの集約はABRで行う

### 設問3(3)　ルータとFWの間
- ルータは、エリア0に172.16.0.0/16（集約経路）を広告している。FWは172.16.0.0/16宛てをルータへ送る
- 172.16.0.0/16の中で**使っていないアドレス**（例：172.16.200.1）宛てのパケットが来たとする
  1. FW → ルータ（集約経路に当たる）
  2. ルータには、そのアドレスの個別の経路がない → **デフォルトルート**（FW行き）に当たる → FWへ戻す
  3. FWはまたルータへ …… → **ルータとFWの間でループ**
- 対策（設3(4)）：ルータに「172.16.0.0/16 → **Null0**（捨てる）」の経路を入れる。個別の経路があればそちら（長い方）が優先され、ない宛先はNull0で捨てられる

### 設問3(4)　f：ルータ　g：172.16.0.0/16
- 表2の列は「設定機器」なので、機器名を入れる。集約をしているルータに、集約したアドレスのNull0経路を作る

### 設問4(1)　h、i、j、k、l
- 統合後、E社はエリア0。L3SW1〜L3SW6の新サブネットもエリア0 → L3SW1は、E社のエリア0と支社のエリア1の境界（ABR）になる
- OSPFでは、エリア間の経路は**必ずエリア0（バックボーン）を通って**伝わる。E社のエリア0とD社本社のエリア0は、エリア1で隔てられていて、つながっていない
- E社からは：エリア1（支社1〜3、広域イーサ網：**a〜g**）には届く。エリア1を越えたD社本社のエリア0（**h〜l**）と、インターネットには届かない

### 設問4(2)　ルータ、L3SW1／OSPF仮想リンクの接続設定を行う。
- **仮想リンク**：エリア0どうしが、別のエリアで隔てられているときに、その間のエリア（**通過エリア**）を通る論理的なリンクを張って、エリア0を1つにつなぐ機能
- 設定するのは、通過エリア（エリア1）の両端のABR：本社側の**ルータ**と、支社1側の**L3SW1**
- 採点講評：「初期構築段階では想定外だったネットワーク統合を後から行う場合などに役立つ」

### 設問4(3)　L3SW1／OSPFエリア1の支社個別経路を172.16.0.0/16に集約する。
- 仮想リンクで、L3SW1もエリア0とエリア1の**ABR**になる。これまで集約していたのは本社のルータだけ
- L3SW1からエリア0へ、支社の個別の経路（a〜g）がそのまま流れ、本社のエリア0に個別経路が現れてしまう → **L3SW1でも同じ集約**を設定する
- 採点講評：「ABRではないルータを誤って解答する例が多く見られた」

## 5. 確認するべき観点・知識

- **エリア間の経路は、必ずエリア0を経由する**。エリア0が分断されると、反対側のエリア0には届かない
- **仮想リンク**：分断されたエリア0を、通過エリアの両端のABRどうしでつなぐ
- **経路集約はABRで行う**。ABRが増えたら、新しいABRにも集約を設定する
- **集約経路とデフォルトルートの組合せでループする** → 集約したルータにNull0の経路
- **「機器と機器の間」「設定機器」には、機器名を答える**
- 関連するノート：[[OSPF]]、[[IPsec]]（事前共有鍵）、[[再配布]]

## 9. 問題の流れ（最初から通しの解説）

この問題は、**OSPFのエリアの仕組み**が分かると一本の話につながる。採点講評でも「全体として正答率は低かった」とされた、難しめの問題。

### ① D社の現行の構成（図1）

```
   支社1（a,b）  支社2（c,d）  支社3（e,f）
     L3SW1        L3SW2        L3SW3
        └───────広域イーサ網（g）───┘        ← ここまでが【エリア1】
                      │
                   ルータ                       ← エリア0とエリア1の境目（ABR）
                      │
   ───────────L2SW7（h）───────────── FW ─ インターネット ─ G社VPC
         L3SW4（i,j）     L3SW5（k,l）              ← ここが【エリア0】（本社）
```

- 本社のLANが**エリア0**、支社と広域イーサ網が**エリア1**
- 本社の**ルータ**は、広域イーサ網（エリア1）とL2SW7（エリア0）の両方につながる → 2つのエリアの境目にいる**ABR**
- アドレスは、支社側（a〜g）が**172.16.x.x**、本社側（h〜l）が**172.17.x.x**（表1）
- FWとG社のVPC GWの間はIPsec VPN。認証用に前もって設定する合言葉が**事前共有鍵**（a）

### ② OSPFの基本（設1 b〜d）

- OSPFのルータは、**LSA**（リンクの情報）を交換して、ネットワークの地図（LSDB）を作る
- **Type1のLSA**は**ルータLSA**（b）。各ルータが「自分のリンクと、その**コスト**（c）」を伝える
- 地図ができたら、各ルータが**ダイクストラ**（d）のアルゴリズムで最短経路を計算する

### ③ 経路集約（設1 e、設3(1)(2)）

```
a 172.16.0.0/23
b 172.16.2.0/23
  ……              → まとめて 172.16.0.0/16（e）の1本だけをエリア0へ
g 172.16.12.64/26
```

- 目的（設3(1)）：本社のL3SWが持つ経路が7本から1本になる → **ルーティングテーブルのサイズを小さく**する
- どこで集約するか（設3(2)）：OSPFで集約できるのは、エリアの境目にいる**ABR** → 本社の**ルータ**

### ④ 集約によるルーティングループと、Null0（設3(3)(4)）

172.16.0.0/16の中には、**使っていないアドレス**もある（例：172.16.200.1）。その宛先のパケットがインターネットから来ると、

```
① FW：172.16.200.1は？ → OSPFで「172.16.0.0/16はルータへ」と聞いている → ルータへ送る
② ルータ：172.16.200.1の個別の経路はない → デフォルトルート（FW行き）に当たる → FWへ戻す
③ FW：また①へ …… ルータとFWの間でぐるぐる回る
```

- ループが起きるのは**ルータとFWの間**（設3(3)）。「どの機器とどの機器の間か」なので、機器名で答える
- 対策は、集約したルータに「**172.16.0.0/16 → Null0**（捨てる）」を入れる（表2。fは「設定機器」の列なので**ルータ**）
- **Null0にしても、支社宛ての通信は捨てられない**：a〜gの個別の経路は/23や/26で、/16より**長い**ので、**ロンゲストマッチ**で個別の経路が優先される。個別の経路がない宛先だけがNull0に当たり、捨てられる（[[OSPF]]の表を参照）

### ⑤ デフォルトルートの配布（設2）

- FWには、インターネットへの**静的**デフォルト経路がある。ただ、これはFWの中だけの設定で、ほかのルータやL3SWはインターネットへの行き方を知らない
- FWの静的デフォルト経路を**OSPFに流し込んで**（再配布して）、全ルータに配る

### ⑥ E社との統合（設4）

E社は**全体がエリア0**。支社1のL3SW1とE社のL3SW6の間をフロアどうしでつなぎ、新しいサブネットを**エリア0**にする。

```
        【D社本社のエリア0】
              │
            ルータ（ABR）
              │
   ───広域イーサ網・支社1〜3【エリア1】───
              │
            L3SW1   ← 新しくエリア0ともつながる（ABRになる）
              │ フロア間接続（新サブネット＝エリア0）
            L3SW6
              │
        【E社のエリア0】
```

**問題：エリア0が二つに分断される（設4(1)）**

- OSPFでは「**エリア間の経路は、必ずエリア0を経由して伝わる**」。エリア0が背骨（バックボーン）で、ほかのエリアは背骨にぶら下がる形しか許されない
- E社のエリア0と、D社本社のエリア0は、間にエリア1が挟まっていて、**つながっていない**（背骨が2本に切れた状態）
- E社からは：すぐ隣のエリア1（支社1〜3、広域イーサ網：**a〜g**）の経路は、L3SW1から受け取れる。その先の本社のエリア0（**h〜l**）の経路は、エリア1を**通過して**伝わることができないので、届かない。インターネットへのデフォルトルートも届かない

**解決：仮想リンク（設4(2)）**

- **仮想リンク**は、エリア1の中に「エリア0の**トンネル**」を通す機能。通過するエリア1の両端のABRどうしを論理的につなぎ、切れた背骨を1本にする
- エリア1の両端は、本社側の**ルータ**と支社1側の**L3SW1**。本文の「フロア間OSPF追加設定を行う2台の機器は、**いずれもエリア境界ルータ**」がヒント

**副作用：集約が効かなくなる（設4(3)）**

- 仮想リンクで、L3SW1も「エリア0とエリア1の境目」、つまり**ABR**になる
- これまで支社の経路を集約していたのは本社のルータだけ。L3SW1は集約していないので、L3SW1から本社のエリア0へ、支社の**個別の経路（a〜g）が漏れる**（本文「本社のOSPFエリア0のネットワーク内に支社個別経路が現れてしまう」）
- 対策は、**L3SW1でも**、エリア1の支社個別経路を**172.16.0.0/16に集約**する（講評：「ABRではないルータを誤って解答する例が多かった」）

**最後の一文**：E社のアドレス（172.18.0.0/16）からも仮想サーバを使えるように、FWとVPC GWのIPsecの設定に**E社のアドレスを追加**する（設問にはなっていない）

### この問題の背骨

| 段階 | 起きること | 対応 |
|---|---|---|
| 集約 | 支社の経路を1本にまとめる | ABR（ルータ）で集約 |
| 集約の副作用 | 存在しない宛先がルータとFWの間でループ | ルータにNull0 |
| 統合 | エリア0が二つに分断され、本社に届かない | ルータとL3SW1の間に仮想リンク |
| 仮想リンクの副作用 | L3SW1がABRになり、個別の経路が漏れる | L3SW1でも集約 |

- 「手を打つと副作用が出て、また手を打つ」の繰り返し。午後Ⅰでよくある組み立て
