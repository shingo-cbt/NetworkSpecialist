## 3. 設問ごとの解説

### 設問1(1)　DNSラウンドロビン
- 案2の初期設定では、proxy.a-sha.co.jp に 192.168.1.145 と 192.168.2.145 の二つのAレコードがある → 問い合わせのたびに順番を変えて返し、負荷を分散する

### 設問1(2)　プロキシサーバのアプリケーションプロセスが停止した場合に検知できないから
- ping（ICMP）で分かるのは、OS（Operating System）とネットワークが応答するかまで。プロキシのプロセスが止まっていても、pingは返る
- 本文の直後に答えの言葉がある：「プロキシサーバの**アプリケーションプロセス**が動作するポート番号に**TCP接続可能か**監視」

### 設問1(3)　192.168.2.145
- 案1：平常時はB、障害時はCに切り替える。proxy.a-sha.co.jp のAを、プロキシサーバBの 192.168.1.145 から、プロキシサーバCの **192.168.2.145** に書き換える

### 設問1(4)　キャッシュDNSサーバがキャッシュを保持する時間を短くするため
- ゾーンファイルを書き換えても、キャッシュDNSサーバはTTLの間、古いアドレスを返し続ける → TTLを小さくして、切替を早く反映させる

### 設問1(5)　方法：プロキシ自動設定機能を利用する。　制限事項：対応するPCやサーバでしか利用できない。
- 読む場所：下線④「**自動で**プロキシサーバを切り替えるために…DNSとは異なる方法」「プロキシサーバを**利用する側の環境に依存**する」
  - 「利用する側」＝PCやサーバのブラウザ。端末側の機能でプロキシを選ぶ → **PAC**
- PACでは、戻り値に複数のプロキシを並べられる：`"PROXY proxyb:8080; PROXY proxyc:8080"` → 1台目に届かなければ自動で2台目を使う
- 制限：PACに対応していない端末やアプリケーションでは使えない → だからDNSでの切替と**併用**する
- 「送信元IPアドレスで振り分ける」は、LB（Load Balancer）やルータの機能。「利用する側の環境に依存」に合わない

### 設問2(1)　a：AS　b：ピア　c：UPDATE　d：KEEPALIVE　e：ルーティングテーブル　f：大きい
- BGPのメッセージ：1 OPEN（開始）、2 UPDATE（経路の追加・削除）、3 NOTIFICATION（エラー）、4 KEEPALIVE（接続の維持）
- LOCAL_PREFは、iBGPのピアにだけ伝える、AS内での出口の好み。**大きいほど優先**

### 設問2(2)　（自身の）IPアドレス
- iBGPは、eBGPで受けた経路のネクストホップを書き換えずに渡す → R13から見て、R11の先のR12のアドレスがネクストホップになり、R13は届かない
- **next-hop-self**：ネクストホップを、広告するルータ**自身のIPアドレス**に書き換える

### 設問2(3)　タイプ：4　動作：BGP接続を切断し，経路情報がクリアされる。
- KEEPALIVEは定期的に送る（初期値60秒）。**ホールドタイム**（初期値180秒）の間、何も届かなければ相手が落ちたと判断する
- BGP接続を切断し、**そのピアから受けた経路情報を消す** → ほかの経路（R13 → R14）が選ばれる。これが障害時の切替になる

### 設問2(4)　VRRPマスターになったR13が経路情報を保持していないと受信したパケットを転送できないから
- VRRPを先に入れると、R13がマスタになった瞬間に、FW10からのパケットがR13に来る
- BGPがまだなく、R13が宛先の経路を持っていなければ、パケットを転送できない → 先にBGPで経路を持たせてから、VRRPを入れる

### 設問2(5)　確認すべき内容：パケットロスが発生しないこと　組合せ：R13⇔R14、R13⇔FW10（又はR13⇔R11）
- 読む場所：表4の項番2で増設したのは「R13と増設の専用線」「R14と増設の専用線」「**R13とL2SW10**」の三つの接続
  - 専用線は R13⇔R14 で確かめる
  - L2SW10側の接続は、L2SW10の先の機器（FW10、R11）との間で確かめる
- 「二つ挙げ」は、**別々の機器・回線を確かめる組合せ**。同じ回線の行きと帰りは一つと数える
- 「故障がない」ことを確かめるpingで見るのは、応答が返ること＝パケットロスがないこと

### 設問2(6)　経路情報は，BGPと比較して静的経路制御の方が優先されるから
- 同じ宛先に複数のプロトコルの経路があれば、AD（Administrative Distance）が小さい方をルーティングテーブルに入れる
- 静的経路（1）はeBGP（20）より優先 → 静的経路を消さないと、BGPの経路は使われない

### 設問2(7)　R11、R13、R11とR12の回線、R13とR14の回線、R11とL2SW10の回線、R13とL2SW10の回線
- 読む場所：「設計どおりに**マルチホームによる可用性向上**が実現できたかどうかを確認するための障害試験」「R12とR14については**D社で障害試験実施済み**」
- 対象は、図3のマルチホームを構成する**A社側の機器と回線**だけ
  - 機器：R11、R13
  - 回線：R11⇔R12、R13⇔R14（D社閉域NWとの専用線）、R11⇔L2SW10、R13⇔L2SW10（本社側）
- IaaSのサーバ（プロキシサーバB・C、開発サーバCなど）は、マルチクラウドの話で、この試験の対象ではない

### 設問3(1)　ルーティングのループが発生する。
- 現在：営業所やD社閉域NWからインターネットへの通信は、**本社のR10経由**（図1）→ D社閉域NWは、インターネット宛てを**本社（R11・R13）に向けて**いる
- FW10のデフォルトルートを先にD社閉域NW側（R11・R13）に変えると：
  - FW10 → R11 → D社閉域NW → （インターネット宛ては本社へ）→ R11 → FW10 → R11 → … と**行ったり来たり**する
- だから下線⑩「FW10の設定変更は、D社閉域NWの設定変更とタイミングを合わせて実施する」
- 採点講評：「インターネットが利用不可になる」は結果。**技術的な原因**（ループ）を書く

### 設問3(2)　送信元IPアドレスが変わるから
- 読む場所：p.3「一部の部門では…SaaSを独自に契約…これらのSaaSでは**送信元IPアドレスによってアクセス制限**をしているものもある」
- FW40には新しいグローバルIPアドレスが割り当てられる → SaaSから見た送信元IPアドレスが、FW10のものからFW40のものに変わり、アクセスを拒否される

### 設問3(3)　送信元IPアドレスがプロキシサーバAで宛先IPアドレスがインターネットであった場合にネクストホップをR10とする設定
- 通常の経路（宛先だけで決める）は、全部FW40に向ける。プロキシサーバAからの通信だけ、**送信元で例外**を作る → ポリシーベースルーティング
- 「どのような設定か」は「条件（送信元・宛先）＋動作（ネクストホップ）」で書く

### 設問3(4)　SaaSの送信元IPアドレスによるアクセス制限の設定変更
- 恒久対応：SaaS側の許可リストに、FW40の新しいグローバルIPアドレスを追加する（設定変更を依頼する）

## 5. 確認するべき観点・知識

- **pingは機器の生存、TCP監視はプロセスの待ち受け、L7は正しく動くか**
- **DNSでの切替はTTLの間反映されない → TTLを小さくしておく**
- **PAC：端末側でプロキシを選ぶ。複数を並べれば自動で切り替わる。対応する端末でしか使えない**
- **BGPのメッセージ4種（OPEN、UPDATE、NOTIFICATION、KEEPALIVE）。ホールドタイム切れで切断し、そのピアの経路を消す**
- **next-hop-self ＝ ネクストホップを自身のIPアドレスに書き換える**
- **BGPを先、VRRPを後**（マスタになったルータが経路を持っていないと転送できない）
- **静的経路はBGPより優先（AD）→ BGPに切り替えるなら静的経路を消す**
- **障害試験の対象は「確かめたい冗長化」を構成する機器と回線**
- **デフォルトルートの切替は、上流（D社閉域NW）とタイミングを合わせる。片方だけ変えるとループ**
- **出口を変えると送信元のグローバルIPアドレスが変わる → 送信元IPで制限しているSaaSに影響。一時対応はポリシーベースルーティング、恒久対応は許可リストの変更**
- 関連するノート：[[BGP]]、[[VRRP]]、[[プロキシ]]、[[ネットワーク監視]]、[[DNS]]、[[移行・切替手順]]、[[クラウド接続]]

- [[移行・切替手順]]：デフォルトルートの切替でループが起きる理由、出口の変更と送信元IPアドレスの制限
- [[VRRP]]：BGPとの導入の順番
