## 3. 設問ごとの解説

### 設問1　a：NS　b：MX　c：100.α.β.1　d：100.α.β.3　e：192.168.1.1　f：192.168.1.3
- 1台のDNSサーバが、2つのゾーンを持つ
  - **example.jp**（インターネット向け）：会員企業がインターネットから引く → 返すのは**インターネットから届くアドレス** ＝ FWzの静的NATの**変換前**（グローバル）
  - **y-sha.example.lan**（社内向け）：運用PCが広域イーサ網から引く → NATを通らないので**プライベート**のまま
- 表1：100.α.β.1 ⇔ 192.168.1.1（TCP/53・UDP/53 → ns）、100.α.β.3 ⇔ 192.168.1.3（TCP/25 → mail）
- **ポート番号でどのサーバか分かる**：53はDNS、443はWeb、25はメール

### 設問2(1)　コモン名とURLのドメインとが異なるから
- 証明書は1つ、マルチドメイン非対応 → コモン名は ecsv.example.jp。運用PCの URL は ecsv.y-sha.example.lan → 一致せずエラー

### 設問2(2)　L3SW，FWz，L2SW
- 運用PC → L3SW →（広域イーサ網）→ FWz → L2SW → ECサーバ
- 本文「運用PCは…**広域イーサ網経由で**ECサーバにアクセス」。FWyはインターネット側なので通らない。広域イーサ網は「機器」ではないので書かない

### 設問3(1)　g：アップ　h：アウト
- スケールアップ（1台を高性能に）は**サーバを止める**必要がある。スケールアウト（台数を増やす）は止めずに増やせる

### 設問3(2)　1台故障時にも，ECサイトの応答速度の低下を発生させないため
- 2台で十分な処理能力 → 3台なら1台故障しても2台残る（**N+1**）
- 発端は「応答が遅い」というクレーム → 目的は**応答速度の低下を起こさない**

### 設問3(3)　i：100.α.β.2　j：192.168.1.2　k：192.168.1.4
- PCは ecsv.example.jp を引いて、**100.α.β.2**（グローバル）宛てに送る（i）
- **FWzの静的NATは変えない** → FWzは 100.α.β.2 を **192.168.1.2** に変換する（j）
- 192.168.1.2 宛てをLBが受ける必要がある → **LBの仮想IPアドレスは 192.168.1.2**（既設ECサーバのアドレスを引き継ぐ）。既設ECサーバは 192.168.1.5（ecsv1）に変わる
- (iii) LBが 192.168.1.5 に振り分ける。ソースNATをすると、送信元はLBの物理IPアドレス **192.168.1.4**（k）
- 解き方：**図の矢印1本ずつ、そこにいる装置がアドレスを書き換えるか**を追う。書き換えるのは FWz（NAT）と LB（宛先を振り分け先へ、ソースNATなら送信元も）だけ

### 設問4(1)　LB／仮想IPアドレス
- 項番5（ecsv、インターネット向け）と項番11（ecsv、社内向け）は、増強後は LB の**仮想IPアドレス**を示す（ゾーンの変更は不要）

### 設問4(2)　（自身の）IPアドレス
- 図4：既設ECサーバは ecsv1・192.168.1.5 → **ホスト名とIPアドレス**を変える
- 元の 192.168.1.2 は LB の仮想IPアドレスになるので、既設ECサーバは明け渡す

### 設問4(3)　FWz から LB に変更
- ソースNATをしないと、ECサーバの応答の宛先は PC（200.a.b.c）。デフォルトゲートウェイが FWz のままだと、**応答がLBを通らず FWz へ直接**行ってしまう（LBが宛先・送信元を戻せない）
- → 既設ECサーバのデフォルトゲートウェイを **FWz から LB** に変える

### 設問4(4)　ECサーバに，アクセス元PCのIPアドレスを通知するため
- 運用PCから保守するためにソースNATをすると、ECサーバに届く送信元は全部 LB（192.168.1.4）になる
- 本文「ECサーバは、**アクセス元のIPアドレスなどをログとして管理**」→ そのままだと PC のアドレスが分からない → X-Forwarded-For で通知する
- 応答は LB に返り、LB が自分のセッションの情報で PC へ戻す。XFF は戻りには使わない

### 設問4(5)　既設ECサーバにインストールされているサーバ証明書と秘密鍵のペアを，LBに移す
- LBがCookieを見るには、**LBでTLSを終端**する → **サーバ証明書と秘密鍵のペア**が LB に必要
- 下線⑦「既設ECサーバ内のサーバ証明書の**流用**」→ 新しく取るのではなく、既設のものを LB に移す
- 採点講評：秘密鍵とサーバ証明書は**一緒に**管理されてはじめて、サーバ認証と共通鍵の安全な配送ができる

### 設問5(1)　TCPコネクションが再設定されるたびに，ポート番号が変わる可能性があるから
- 会員企業の出口で NAPT される → TCPコネクションを張り直すと送信元ポートが変わる → IPアドレスとポートの組では同じ利用者と分からない

### 設問5(2)　サーバからの応答に含まれるCookie中のセッションIDが，セッション管理テーブルに存在しない場合
- 本文の3つの条件をつなぐ（採点講評）
  1. ECサーバは**最初のアクセス**でセッションIDを生成する
  2. ECサーバは**応答**のCookie（Set-Cookie）にセッションIDを書き込む
  3. LBは、Cookie中のセッションIDと振分け先のサーバでテーブルを作る
- → LBが新しいレコードを作るのは、**サーバの応答に、テーブルにないセッションIDが入っていたとき**
- 「新しい端末」「ブラウザを起動」は利用者側の出来事で、**LBが判定できる条件**ではない

### 設問5(3)　サービスが稼働しているかどうか検査しないから
- L3（ping）は機器が生きているか、L4（TCPのポート）は待ち受けているかまで。ECのサービス（アプリケーション）が正しく応答するかは L7 でしか分からない

### 設問6(1)　アクセス元の購買担当者が所属している会員企業の情報
- IdPは会員企業ごとに違う → ECサーバ（SP）は、**この購買担当者がどの会員企業の人か**を知らないと、リダイレクト先のIdPを決められない

### 設問6(2)　IdPの公開鍵証明書
- 下線⑫「IdPが作成するデジタル署名の検証に必要な情報」→ **IdPの公開鍵証明書**

### 設問6(3)　IdPの鍵を所有していないから
- (vi)「KDCは…**IdPの鍵で**STを暗号化」。Kerberosのチケットは**共通鍵で暗号化**されている（署名ではない）
- PCが持っているのは自分の鍵だけ。STは IdP の鍵で暗号化されているので、PCは中身を読めず、書き換えると IdP で復号・検証できなくなる

### 設問6(4)　① 信頼関係のあるIdPが生成したものであること　② SAMLアサーションが改ざんされていないこと
- デジタル署名の検証で分かるのは、いつも**2つ**：**誰が作ったか**（真正性）と**改ざんされていないか**（完全性）
- 「公開鍵で復号できる」は検証の手段。設問は「検証できる**内容**」

## 5. 確認するべき観点・知識

- **インターネット向けのゾーンのAレコードは、FWの静的NATの変換前**（グローバル）。社内向け（NATを通らない）はプライベート
- **LBを後から入れるとき、FWのNATを変えないなら、LBの仮想IPアドレスは既設サーバのアドレスを引き継ぐ** → 既設サーバはホスト名とIPアドレスを変える
- **ソースNATをしないLBでは、サーバのデフォルトゲートウェイをLBにする**（戻りをLBに通す）。ソースNATをすれば変えなくてよいが、送信元が全部LBになる → **X-Forwarded-For でサーバに元のIPを知らせる**
- **LBでTLSを終端するなら、既設サーバの証明書と秘密鍵のペアをLBに移す**
- **IPアドレス＋ポートのセッション維持は、NAPTでポートが変わると切れる** → Cookie
- **LBのテーブルに登録するのは、サーバの応答のCookieに未登録のセッションIDがあったとき**
- **L3・L4のヘルスチェックはサービスの稼働を見ない** → L7
- **SAMLの署名の検証で分かるのは「信頼するIdPが作った」「改ざんされていない」の2つ**。SPに登録するのは**IdPの公開鍵証明書**
- **KerberosのSTは、サーバ（ここではIdP）の鍵で暗号化**。利用者は鍵を持たないので改ざんできない
- 関連するノート：[[負荷分散装置]]、[[SAML]]、[[Kerberos]]、[[DNS]]、[[TLS]]、[[NAT・NAPT]]

## 7. ノートに追記した内容

- [[負荷分散装置]]：LBを後から入れるときのアドレスの引継ぎ（VIPは既設サーバのアドレス、デフォルトゲートウェイ、ソースNATとXFF、テーブルの登録条件）

- [[SAML]]：R5午後Ⅱ問2の内容はすでにノートにあった（リダイレクト先を決める所属組織、IdPの公開鍵証明書、改ざんできない理由）
