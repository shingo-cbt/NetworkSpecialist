# HTTP まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

令和7年春 午後Ⅰ 問2は、学校ネットワークのトラブルシューティングを題材に、**HTTP（Hypertext Transfer Protocol）の知識と、問題の切り分け・仮説検証の進め方**を問う問題だった（IPA（情報処理推進機構）の出題趣旨より）。

## 1. HTTPの基本（○）

- Webブラウザ（クライアント）とWebサーバが、**リクエストとレスポンス**をやり取りするプロトコル
- 下位はTCP（Transmission Control Protocol）（HTTP/1.1、HTTP/2）。ポートは **80**、TLS（Transport Layer Security）で暗号化した **HTTPS（HTTP Secure）は443**
- **ステートレス**：1回のやり取りごとに完結し、前のやり取りを覚えていない → ログイン状態などは **Cookie** で管理する

### リクエストとレスポンスの形

```
GET /index.html HTTP/1.1          ← リクエスト行（メソッド、パス、バージョン）
Host: www.example.jp              ← ヘッダ（1行に1つ。何行でも並べられる）
User-Agent: Mozilla/5.0 ...
Cookie: session=abc123
Accept-Language: ja
X-Forwarded-For: 203.0.113.5
                                  ← 空行：ヘッダはここまで
（ボディ：POSTで送るデータなど。GETでは通常なし）

HTTP/1.1 200 OK                    ← ステータス行
Content-Type: text/html
Set-Cookie: session=abc123
Set-Cookie: lang=ja                ← 同じヘッダを複数行に分けて書くこともある
                                   ← 空行
（ボディ：HTMLなどの本文）
```

- **ヘッダは1行に1つ**書き、**改行で追加**していく。**空行**で「ヘッダの終わり」を示し、その後ろに**ボディ**（本文）が続く
- 同じヘッダを2回以上使う場合
  - **複数行に分けて書く**：サーバがCookieを2つ渡すときは、`Set-Cookie` を2行書く
  - **1行にカンマで並べる**：`Accept-Language: ja, en`
  - **1つだけ**：`Host` は、HTTP/1.1のリクエストに**ちょうど1つ**必須。2つあるとエラーになる

### 主なメソッド（○）

| メソッド | 内容 |
|---|---|
| **GET** | 情報を取得する |
| **POST** | データを送る（フォームの送信など） |
| PUT／DELETE | 置き換え／削除（API（Application Programming Interface）で使う） |
| HEAD | ヘッダだけ取得する（ヘルスチェックなど） |
| **CONNECT** | **プロキシにトンネルを張らせる**（HTTPS、wss をプロキシ経由で通す） |

### GETとPOSTの違い（△）

| | GET | POST |
|---|---|---|
| データの場所 | **URL（Uniform Resource Locator）の後ろ（クエリ文字列）**：`/search?q=abc` | **メッセージボディ** |
| メリット | ブックマーク・共有ができる。**キャッシュできる** | URLに出ないので、ログや履歴に残りにくい。大きなデータも送れる |
| デメリット | **ログ・閲覧履歴・Refererに残る**ので、パスワードなどには使わない。URLの長さに上限がある | キャッシュ・ブックマークができない |

- POSTでもデータは**暗号化されない**。盗聴を防ぐにはHTTPS（TLS）が必要

## 2. ステータスコード（◎：トラブルシューティングの手がかり）

| コード | 意味 | 切り分けのヒント |
|---|---|---|
| **200** OK | 成功 | − |
| **301／302** | **リダイレクト**（別のURLへ移動） | Locationヘッダの移動先にアクセスし直す。HTTPからHTTPSへの誘導など |
| 304 Not Modified | キャッシュをそのまま使ってよい | − |
| **401** Unauthorized | **認証が必要**（サーバの認証） | ID・パスワードの問題 |
| **403** Forbidden | **アクセス禁止** | サーバ側のアクセス制御で拒否 |
| **404** Not Found | ページがない | URLの誤り、ファイルがない |
| **407** Proxy Authentication Required | **プロキシの認証が必要** | プロキシの認証設定の問題 |
| **500** Internal Server Error | サーバ内部のエラー | アプリケーションの不具合 |
| **502** Bad Gateway | **プロキシ・LB（Load Balancer）が、その先のサーバから正しい応答を得られない** | 中継装置の先のサーバの問題 |
| **503** Service Unavailable | サーバが一時的に使えない（過負荷、保守中） | − |
| **504** Gateway Timeout | **プロキシ・LBが、その先のサーバからの応答を待ちきれない** | 中継装置の先のサーバの遅延・経路の問題 |

- **4xxはクライアント側（要求の内容）の問題、5xxはサーバ側の問題**
- **502・504は**「中継装置（プロキシ、LB、SWG（Secure Web Gateway））の先」に問題があることを示す → どこで止まっているかの切り分けに使う

### 401・407・403の違い（◎、11/10に整理）

- **401と407は「認証情報をください」**。認証情報なしの初回でも、ID・パスワードが違ったときも、同じコードが返る（「失敗」ではなく「必要」）
- **403は「誰であっても通さない」**。認証し直しても変わらない

| | 401（サーバの認証） | 407（プロキシの認証） |
|---|---|---|
| 求める側 | Webサーバ | プロキシサーバ |
| 求めるときのヘッダ（レスポンス） | **WWW-Authenticate** | **Proxy-Authenticate** |
| 認証情報を入れるヘッダ（リクエスト） | **Authorization** | **Proxy-Authorization** |

```
PC → プロキシ   GET http://www.example.jp/  （認証情報なし）
PC ← プロキシ   407 + Proxy-Authenticate: Basic
PC → プロキシ   GET ... + Proxy-Authorization: Basic xxxx
PC ← プロキシ   200 OK（通った） / 407（違った）
```

- 「Authenticate」はサーバ側からの要求、「Authorization」はクライアントからの答え。頭に「Proxy-」が付けばプロキシ用
- **ログに407があっても、それだけでは異常ではない**：認証情報なしの最初の要求には毎回407が返る。407が繰り返し返って200にならないときに問題がある
- **407で止まる典型**：OS（Operating System）の更新やアプリなど、プロキシ認証に対応していないソフトの通信 → その宛先をプロキシの認証の対象から外す、またはプロキシを通さない設定にする
- 407が返ったなら、少なくとも**プロキシまでは届いている**
- 覚え方：401と407は「関所で通行手形を見せて」（401は目的地の門、407は途中の関所）。403は「手形があっても通さない」

## 3. 主なヘッダ（◎）

| ヘッダ | 役割 | 関連 |
|---|---|---|
| **Host** | アクセスしたいホスト名。**1つのIP（Internet Protocol）アドレスで複数のWebサイトを運用**（バーチャルホスト）するのに必要 | − |
| **Cookie／Set-Cookie** | セッション管理。LBの**セッション維持**にも使う | [[負荷分散装置]] |
| **Location** | リダイレクト先のURL | − |
| **X-Forwarded-For** | プロキシ・LBが、**元のクライアントのIPアドレス**を書き込む | [[負荷分散装置]] |
| Authorization／**Proxy-Authorization** | サーバ／プロキシへの認証情報 | − |
| Cache-Control | キャッシュしてよいか、期間 | − |
| **Upgrade** | 別のプロトコル（WebSocketなど）への切替 | [[WebSocket]] |
| Strict-Transport-Security | **HSTS（HTTP Strict Transport Security）**：ブラウザに「一定期間このサイトにはHTTPSでしか接続しない」と指示する（max-age：期間、includeSubDomains：サブドメインも対象） | [[TLS]] |

- **X-Forwarded-For が複数並ぶ場合**（△〜○）：プロキシやLBを**何段も経由**すると、それぞれの装置が、**受け取った通信の送信元を後ろに追加**していく

```
X-Forwarded-For: 203.0.113.5, 198.51.100.7
                 └─利用者──┘  └─途中のプロキシ─┘
```

  - **一番左が、元の利用者のIPアドレス**。Webサーバのログで利用者を確認するときは、ここを見る
  - LBでSNAT（Source NAT、NAT：Network Address Translation）すると、サーバからは送信元がLBに見えるので、このヘッダで利用者のアドレスを渡す → [[負荷分散装置]]

### URLの分解と、HTTPの中での置き場所（○、11/10に整理）

```
https://www.example.jp/shop/cart.html
└─┬─┘   └─────┬─────┘└──────┬──────┘
スキーム    FQDN           パス
```

| 入るもの | HTTP/1.1での場所 | HTTP/2の疑似ヘッダー | 役割 |
|---|---|---|---|
| パス `/shop/cart.html` | リクエスト行（メソッドの後ろ） | **:path** | サーバの中の、どのページか |
| FQDN（Fully Qualified Domain Name） `www.example.jp` | **Hostヘッダ**（HTTPSならSNIにも） | **:authority** | どのサイトか |
| メソッド | リクエスト行の先頭 | **:method** | |
| スキーム（https） | − | **:scheme** | |

- フォワードプロキシに送るときだけ、リクエスト行に**URL全体**を書く（`GET http://www.example.jp/shop/cart.html HTTP/1.1`）。PCがつないでいる相手はプロキシなので、どのサーバのどのページかを伝える
- **SNIに入るのはFQDNだけ**（ポート、パスは入らない）。IPアドレスでアクセスするとSNIは送られない → [[TLS]]
- **パスが見えるのは復号したときだけ**：SNIだけを見るFW・SWG・LBはFQDNまで。URLのパスで振り分ける・フィルタリングするなら、TLSインスペクションかSSLオフロードが要る
- 覚え方：「FQDNは建物の住所、パスは建物の中の部屋番号」

## 4. HTTPのバージョン（○）

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 下位 | TCP | TCP（実質TLS必須） | **QUIC（UDP（User Datagram Protocol）上）** |
| 同時に複数の要求 | 1つのコネクションでは順番に（複数のコネクションを張る） | **1つのコネクションで並行して（多重化）** | 多重化。1つのパケットロスが他の要求を止めない |
| ヘッダ | テキスト | バイナリ、**圧縮** | 圧縮 |

- **キープアライブ（持続的接続）**：HTTP/1.1では1つのTCPコネクションで複数の要求を送れる（毎回TCPを張り直さない）
- **HoL（Head of Line）ブロッキング**（○）：列の先頭の処理が詰まると、後ろの処理が全部待たされること（レジの先頭の会計が長引くと、後ろの人が全員待つ）
  - HTTP層：HTTP/1.1は、1つのコネクションでリクエストとレスポンスを1組ずつ順番に処理する → 前のレスポンスが遅いと、後ろのリクエストが待たされる。対策としてブラウザは複数のTCPコネクションを張る
  - TCP層：HTTP/2は1つのTCPコネクションで多重化するが、TCPは順番どおりに渡すので、1つのパケットが失われると全部のストリームが待たされる → HTTP/3はQUIC（UDP）でこれを避ける
  - 記述の型：「先行の処理が終わるまで後続の処理が待たされるから」
- **ストリームとストリームID**（○）：HTTP/2は、1つのTCPコネクションの中に仮想的な通信の単位（ストリーム）を複数作り、それぞれを**ストリームID**で区別する → 多重化と並列処理ができる
- **HTTP/2の特徴の4点セット**（○、令和5年春 午後Ⅰ 問1）

| 特徴 | 中身 |
|---|---|
| 多重化 | 1つのTCPコネクションの中に**ストリーム**（仮想的な通信路）を複数作る。HTTP/1.1のパイプラインは「**リクエストを受けたのと同じ順序でレスポンスを返す**」制約があるが、HTTP/2にはない |
| ヘッダー圧縮 | **HPACK**でバイナリに圧縮する。コロンで始まる**疑似ヘッダーフィールド**（**:method**、:scheme、:path、:authority）が必須 |
| フロー制御 | **ストリームごと**に行い、1つのストリームが資源を占有するのを防ぐ |
| 互換性 | HTTP/1.1と同じ「https://」と443番を使う → どちらで話すかを、TLSの拡張の**ALPN**（Application-Layer Protocol Negotiation）で決める |

- **h2とALPN**：h2は、TLS（1.2以上）の上でHTTP/2を使う方式
  - クライアントが**ClientHello**で「使えるアプリケーション層のプロトコル」の候補（h2、http/1.1）を送り、サーバが**ServerHello**で1つ選んで返す
  - 目的の記述の型：「通信開始時にTCPの上位のプロトコルを決定するため」
  - 問われ方：「ネゴシエーションが含まれるのはシーケンスのどこか」→ TCPの3ウェイハンドシェイクでもHTTPのやり取りでもなく、**ClientHelloとServerHello**
- **LBでのバージョンの変換**：ブラウザとLBの間はHTTP/2、LBとサーバの間はHTTP/1.1 → LBはHTTPを終端して**HTTP/2をHTTP/1.1に変換**する → レイヤー7で動くモードが必要（URLで振り分けるときも同じ）→ [[負荷分散装置]]
  - 記述の型：「HTTP/2リクエストをHTTP/1.1に変換して負荷分散するから」
- **HTTPのバージョンとNAPT（Network Address Port Translation）の変換エントリー**（○）：HTTP/1.1は複数のTCPコネクションを張るので、エントリーを多く使う。HTTP/2は1つのTCPコネクションにまとまる。HTTP/3はUDPなので、UDPの保持時間で消える（→ [[NAT・NAPT]]）
- **HTTP/3はUDP 443**を使う → FWでUDP 443を止めていると、ブラウザはTCP（HTTP/2）に切り替えて通信する（△〜○）

## 5. プロキシとの関係（◎）

- **フォワードプロキシ**：社内の端末の代わりにWebサーバへアクセスする
  - 端末はプロキシに **URL全体（http://www.example.jp/...）** を書いたリクエストを送る
  - **HTTPSはCONNECTメソッド**でプロキシにトンネルを張らせ、その中でTLSを通す（プロキシは中身を見ない。見るならTLSインスペクション）
  - **プロキシの例外設定**：社内のサーバなど、プロキシを通さず直接アクセスする宛先を指定する（令和4年春 午後Ⅰ 問3でも問われた）
- **リバースプロキシ**：Webサーバの手前に置き、外部からの要求を受けてサーバに中継する（LB、WAF（Web Application Firewall）、キャッシュ）
- → [[プロキシ]]

## 6. 午後で問われるテーマと記述の型

### ◎ トラブルシューティングの切り分け

- 「Webページが見られない」を、**下の層から順に**確かめる
  1. **名前解決**：DNS（Domain Name System）でIPアドレスが引けるか → [[DNS]]
  2. **TCP接続**：宛先の80／443番につながるか（FW（Firewall）、経路） → [[FW]]
  3. **TLS**：証明書のエラーがないか（ホスト名の不一致、ルート証明書） → [[TLS]]
  4. **HTTP**：**ステータスコード**は何か（401／403／407／502／504など）
- どこまで成功し、どこで失敗したかで原因の場所を絞り込む
- **仮説を立てて検証する**：「プロキシの認証で止まっている」→ 407が返るか確認する、など
- 記述の型：「ステータスコード502が返っていることから、プロキシは応答しており、プロキシから先のWebサーバとの通信に問題があると判断できる」

**どこまで成功したかの見分け方**（11/10に整理）

| 症状 | 正常と言えるところ | 疑うところ |
|---|---|---|
| IPアドレスを直接打つと見られる | TCP・TLS・HTTP | ①名前解決 |
| pingは通るがページが出ない | 名前解決と経路 | ②ポート（FW）から上 |
| 証明書の警告が出る | ①② | ③TLS（名前の不一致、ルート証明書、中間CA（Certificate Authority）証明書） |
| ステータスコードが返る | ①②③ | ④コードの示す場所（407はプロキシの認証、502・504は中継装置の先、401・403・404はWebサーバ） |

**プロキシを使うときの注意**（試験で狙われる）

- ①：PCが名前解決するのは**プロキシの名前**だけ。Webサイトの名前解決は**プロキシがする**。PCでnslookupが失敗しても、原因とは限らない
- ②：PCがTCPでつなぐ相手は**プロキシ**（8080番など）
- ③：HTTPSはCONNECTでトンネルを張ってから、その中でTLSを通す
- ④：502・504・407が返るのは、**プロキシが応答している証拠**
- たとえ：①番号を調べる、②相手が受話器を取る、③本人か確かめる、④用件への返事

### ◎ Cookieとセッション維持

- LBで振り分けるとき、Cookieを見て同じサーバに送る → HTTPSならLBでTLSを終端する必要がある
- **Set-CookieとCookieの向き**（11/14に追記）：**Set-Cookie**はレスポンスのヘッダ（サーバ → ブラウザ、「これを覚えて」）、**Cookie**はリクエストのヘッダ（ブラウザ → サーバ、「前にもらった値です」）。属性はSet-Cookieにだけ付き、Cookieでは名前＝値だけを送る
- **Cookieの主な属性**（平成27年秋 午後Ⅰ 問1）

| 属性 | 意味 | 問われ方 |
|---|---|---|
| **Domain** | どのドメイン（とサブドメイン）に送るか | SSO（Single Sign-On）で複数のサーバ（eigyo.a-sha.example.jp、kokoku.a-sha.example.jp）にCookieを送らせるには、共通の上位ドメイン（a-sha.example.jp）を指定する |
| **Secure** | **HTTPSのときだけ**送る | 全ページをHTTPSにしても、HTTPで接続されたときにCookieが平文で流れる → **Secure属性を付ける**（採点講評で正答率が低かった） |
| **HttpOnly** | JavaScriptから読めない | XSS（Cross-Site Scripting）でCookieを盗まれるのを防ぐ |
| SameSite（△） | 別サイトからのリクエストには送らない | CSRFを防ぐ |

  - 覚え方：**「Set-Cookieは番号札を渡すこと、Cookieは番号札を見せること。札の注意書き（Secure、HttpOnly、Domain）は渡すときだけ付ける」**
- → [[負荷分散装置]]

### ○ リダイレクト

- HTTPでアクセスしてきた利用者を、301／302でHTTPSに誘導する
  - ただし、**最初のHTTPのアクセスとリダイレクトは平文**なので、中間者に横取りされるとHTTPのまま偽の経路で通信させられる（**SSL（Secure Sockets Layer）ストリッピング**）
  - 対策：**HSTS**。一度指示を受けたブラウザは、`http://` と入力されても自分でHTTPSに置き換えて接続する。証明書にエラーがあれば、警告を無視して進むことも許さない
  - HSTSの弱点：**初回のアクセス**はまだ指示を受けていないので守られない → ブラウザに組み込まれた**HSTSプリロードリスト**にドメインを登録する（△）
  - 午前で用語として出る程度。午後で出るなら「HTTPのリダイレクトだけでは不十分な理由」
- SWGやクラウドの認証画面へリダイレクトして利用者を認証する

### ○ バーチャルホストとHostヘッダ

- 1台のサーバ・1つのIPアドレスで複数のサイトを運用する → Hostヘッダ（HTTPSならSNI（Server Name Indication））でサイトを区別する

## 7. 覚え方

- **ステータスは「2成功、3移動、4客のせい、5店のせい」**
- **401はサーバの認証、407はプロキシの認証**（7は「プロキシの関所」）
- **502は「先の店から変な返事」、504は「先の店から返事がない」**：どちらも中継装置の先が怪しい
- **HTTPSをプロキシに通すのは「CONNECTでトンネル」**
- **切り分けは「名前 → つながる → 暗号 → 応答コード」の順**
- **HTTP/3は「UDP 443」**：止められたらTCPに戻る

## 8. 勉強の優先順位

1. ステータスコード（特に301／302、401、403、407、502、504）の意味と、切り分けでの使い方
2. トラブルシューティングの切り分けの順番（DNS → TCP → TLS → HTTP）
3. 主なヘッダ（Host、Cookie、X-Forwarded-For、Upgrade）
4. プロキシとの関係（CONNECT、例外設定）
5. HTTP/2・HTTP/3の違い（多重化、QUICとUDP 443）
6. メソッドの種類は午前で確認する程度でよい

> [!tip] 得点につながる覚え方
> HTTPは直近の午後Ⅰでトラブルシューティングの題材になった。**ステータスコードを「どこで止まっているかの証拠」として読む**練習をする。502・504・407が出たら、利用者とWebサーバの間にある**中継装置**（プロキシ、LB、SWG）を疑う。
