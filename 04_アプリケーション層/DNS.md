# DNS まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

## 1. DNSの基本（○）

- ドメイン名（FQDN：Fully Qualified Domain Name）とIP（Internet Protocol）アドレスなどの対応を、**木構造に分散したサーバ**で管理・検索する仕組み
- ポート：**UDP（User Datagram Protocol） 53**（通常の問い合わせ）と **TCP（Transmission Control Protocol） 53**

| TCPを使う場面 | 理由 |
|---|---|
| **ゾーン転送** | 大量のデータを確実に送る |
| 応答が大きいとき | UDPの応答に収まらないと**TCビット**が立ち、TCPで問い合わせ直す（EDNS0（Extension Mechanisms for DNS version 0）を使えばUDPでも大きな応答を送れる） |

- **正引き**：名前 → IPアドレス／**逆引き**：IPアドレス → 名前（PTR（Pointer）レコード）
- 午前の誤り選択肢の定番：「DNS（Domain Name System）はUDPしか使わない」→ 誤り（ゾーン転送などでTCPも使う）。**FW（Firewall）でTCP 53を許可し忘れる**と午後で問われる

## 2. サーバの種類と問い合わせの流れ（◎）

| 役割 | 別名 | 仕事 |
|---|---|---|
| **権威DNSサーバ** | コンテンツサーバ | **自分が管理するゾーン**の情報を答える |
| **キャッシュDNSサーバ** | フルサービスリゾルバ | 端末の代わりに権威DNSへ順に問い合わせ、結果を**キャッシュ**する |
| スタブリゾルバ | − | 端末（OS：Operating System）側の問い合わせ機能 |
| フォワーダ | − | 受けた問い合わせを、別のキャッシュDNSサーバへ転送する |

- **再帰問い合わせ**：端末 → キャッシュDNS。「最終的な答えをください」
- **反復問い合わせ**：キャッシュDNS → ルート → .jp → example.jp と順にたどる。「知っている範囲で教えて（次の行き先でもよい）」
- 記述の型（キャッシュDNSの役割）：「端末からの再帰問い合わせを受け、権威DNSサーバへ反復問い合わせを行い、結果をキャッシュする」

## 3. リソースレコード（◎）

| レコード | 内容 | ポイント | 出題度 |
|---|---|---|---|
| **SOA**（Start of Authority） | ゾーンの管理情報 | **シリアル番号**、リフレッシュ間隔など。ゾーン転送で重要 | ◎ |
| **NS**（Name Server） | ゾーンの権威DNSサーバ名 | 上位ゾーンにも書いて委任する | ◎ |
| **A** | 名前 → IPv4アドレス | | ◎ |
| **AAAA** | 名前 → IPv6アドレス | | ○ |
| **CNAME**（Canonical Name） | 別名 → 正式名 | 同じ名前に他のレコードを置けない、**ゾーンの頂点（example.jp自体）には使えない** | ◎ |
| **MX**（Mail Exchanger） | メールの配送先サーバ名 | **優先度（値が小さいほど優先）**。値はホスト名（IPアドレスは書けない） | ◎ |
| **PTR** | IPアドレス → 名前（逆引き） | メールサーバの正当性確認で使う | ○ |
| **TXT** | 任意の文字列 | **SPF**（Sender Policy Framework）、DKIM（DomainKeys Identified Mail）の公開鍵、DMARC（Domain-based Message Authentication, Reporting and Conformance）のポリシーを書く | ◎ |
| SRV（Service） | サービスのホスト名とポート | SIP（Session Initiation Protocol）などで使う | △ |
| CAA | 証明書を発行してよい認証局 | | △ |

### 記載例（ゾーンファイル）

午後の問題では、次のような**ゾーンファイルの一部が表で示され、空欄を埋める**形が多い。

```
$ORIGIN example.jp.
$TTL 3600                         ; 既定のTTL（秒）

@       IN  SOA  ns1.example.jp. admin.example.jp. (
                 2026101001  ; シリアル番号（更新のたびに増やす。日付＋連番が定番）
                 3600        ; リフレッシュ：セカンダリがSOAを確認する間隔
                 900         ; リトライ：確認に失敗したときの再試行間隔
                 604800      ; 期限切れ：プライマリと通信できないまま、この時間を過ぎたら応答をやめる
                 300 )       ; ネガティブキャッシュのTTL

@       IN  NS     ns1.example.jp.
@       IN  NS     ns2.example.jp.

ns1     IN  A      192.0.2.1
ns2     IN  A      192.0.2.2
www     IN  A      192.0.2.10
www     IN  A      192.0.2.11      ; 同じ名前に複数のA → DNSラウンドロビン
www     IN  AAAA   2001:db8::10
web     IN  CNAME  www.example.jp. ; web.example.jp は www.example.jp の別名

@       IN  MX  10 mail1.example.jp. ; 優先度10（先に使う）
@       IN  MX  20 mail2.example.jp. ; 優先度20（mail1に届かないとき）
mail1   IN  A      192.0.2.25
mail2   IN  A      192.0.2.26

@       IN  TXT    "v=spf1 ip4:192.0.2.25 ip4:192.0.2.26 -all"   ; SPF
_dmarc  IN  TXT    "v=DMARC1; p=reject; rua=mailto:dmarc@example.jp" ; DMARC
```

逆引きは別のゾーン（`in-addr.arpa`）に、**IPアドレスを逆順にした名前**で書く。

```
$ORIGIN 2.0.192.in-addr.arpa.
25      IN  PTR    mail1.example.jp.   ; 192.0.2.25 → mail1.example.jp
```

上位ゾーン（jp）側での委任とグルーレコードの例。

```
example.jp.      IN  NS  ns1.example.jp.
example.jp.      IN  NS  ns2.example.jp.
ns1.example.jp.  IN  A   192.0.2.1      ; グルーレコード
ns2.example.jp.  IN  A   192.0.2.2      ; グルーレコード
```

**読み方のポイント（穴埋めで狙われる）**

- **末尾のドット「.」**：付いていれば完全な名前（FQDN）。付いていなければ `$ORIGIN` が後ろに補われる
  - 「.」は**ルート**（DNSの木の一番上）を表す。名前は右に行くほど上の階層で、`www.example.jp.` は「ルート → jp → example → www」とたどる住所。末尾の「.」は「ルートから始まる完全な住所（ここで終わり）」の印
  - `www` → `www.example.jp.`
  - `www.example.jp`（ドットなし）→ `www.example.jp.example.jp.` になってしまう → **よくある設定ミス**
- **`@`**：`$ORIGIN` そのもの（ここでは `example.jp.`）＝ゾーンの頂点
  - 頂点に何行も書くレコード（SOA、NS、MX、TXT）を短く書くための記号。`$ORIGIN` を変えれば、同じファイルを別のドメインに使い回せる
  - 読み方：`@ IN MX` は「xxx@example.jp 宛てのメールの配送先」、`@ IN TXT "v=spf1 ..."` は「example.jp から送るメールのSPF」
  - メールアドレスの `@` とは無関係。ゾーンファイルの中では `@` が頂点の意味になるので、SOAの管理者のメールアドレスは `@` の代わりに「.」で書く（`admin.example.jp.` → admin@example.jp）
- **頂点（Zone Apex）**：ゾーンの名前そのもの（`example.jp.`）。`www.` などが付かない名前で、ブラウザで `https://example.jp` と打ったときにアクセスする名前
  - 頂点には、ゾーン自体の情報（**SOA、NS**、MX、TXT）を書く
  - 「ルートドメイン」と呼ばれることもあるが、DNSの木の一番上（末尾の「.」）のルートと紛らわしいので、試験では「頂点」で覚える
- **ゾーンと権威DNSサーバは別物**：`example.jp.` は名前（ゾーン）で、サーバではない
  - ゾーン：管理する名前の範囲。権威DNSサーバ：そのゾーンのゾーンファイル（原本）を持ち、正式な答えを返す機械（例：ns1.example.jp、192.0.2.1）
  - 「権威」＝原本を持っているという意味。キャッシュDNSは、聞いた答えをTTLの間覚えているだけ（写し）
  - どのサーバが権威かは、**NSレコード**で決まる。上位ゾーン（jp）にも同じNSを登録して委任する。権威DNSサーバの名前は、ゾーンの外（DNS事業者のサーバなど）でもよい
  - 覚え方：「ゾーンは町、頂点は町の名前、権威DNSサーバは台帳を持つ町役場」
- **名前を省略した行**：直前の行と同じ名前になる
- **MXの値はホスト名**で、そのホスト名のAレコードが別に必要。IPアドレスやCNAMEの名前は書かない
- **CNAMEの左側**（`web`）には、ほかのレコード（A、MXなど）を置けない。`@` にもCNAMEは置けない
  - CNAMEは「名前 → 別の名前」。「この名前は、**丸ごと**あの名前の別名」という意味なので、自分の情報を持てない。頂点には必ずSOAとNSがあるので、CNAMEを置けない
  - 名前解決の流れ：`web` を聞くと「wwwの別名」と返り、キャッシュDNSが続けて `www` のAレコードを引いて、IPアドレスを端末に返す（問い合わせが1段増える）
  - 使う理由（◎）：**CDN（Content Delivery Network）・クラウドの負荷分散装置・SaaS（Software as a Service）は、事業者の都合でIPアドレスが変わる** → Aで固定せず、CNAMEで事業者のFQDNを指す。記述の型：「IPアドレスが変わっても、自社のDNSの設定を変更せずに済むため」
  - もう1つの理由：1台のサーバに複数の名前を付けるとき、正式名に寄せておけば、IPアドレスの変更は1か所で済む
  - 頂点をCDNに向けたいときは、DNS事業者独自のALIASレコードを使うか、`www` をCNAMEにして、頂点からwwwへHTTPでリダイレクトする（△）
  - NSの値にも、CNAMEの名前は書かない（MXと同じ）
  - 覚え方：「CNAMEは転送届。届けを出した名前には、もう何も置けない」
- シリアル番号を**増やさずに**ファイルを変更すると、セカンダリに反映されない（→ 4. ゾーン転送）
- **SOAの項目**：1つのゾーンに1つだけ、頂点に書く。多くはセカンダリへの指示
  - 並び順：プライマリDNSサーバ名 → 管理者のメールアドレス → **シリアル番号（◎）** → **リフレッシュ（◎）** → リトライ → 期限切れ → ネガティブキャッシュのTTL
  - セカンダリの動き：リフレッシュの間隔でプライマリのシリアル番号を確認 → 大きければゾーン転送 → 失敗したらリトライの間隔で再試行 → 期限切れを過ぎたら、古い情報を答えないように応答をやめる
  - 覚え方：「SOAはゾーンの奥付。版数（シリアル）が上がらないと、セカンダリは新しい版を取りに来ない」
- 逆引きの名前は**オクテットが逆順**：192.0.2.25 → `25.2.0.192.in-addr.arpa.`

- **グルーレコード**：委任先のNSのホスト名が、そのゾーンの中にある場合、上位ゾーンに**NSのAレコードも一緒に登録**する。ないと名前解決が堂々巡りになる（○）
- 穴埋めで「MXの優先度」「CNAMEの書き方」「TXTにSPFを書く」が問われやすい → [[SPF・DKIM・DMARC]]

## 4. ゾーン転送（◎）

- **プライマリ**（マスタ）のゾーン情報を**セカンダリ**（スレーブ）にコピーして冗長化する
- 流れ
  1. セカンダリが一定間隔（SOAのリフレッシュ値）でプライマリの**SOAのシリアル番号**を確認する
  2. **シリアル番号が増えていたら**ゾーン転送（AXFR（Full Zone Transfer）：全体、IXFR（Incremental Zone Transfer）：差分）を行う
  3. プライマリから **NOTIFY** で更新を知らせることもできる
- ◎の定番：**プライマリでレコードを変更したのに、シリアル番号を増やし忘れた → セカンダリに反映されない**
  - 記述の型：「SOAレコードのシリアル番号が更新されていないため、セカンダリDNSサーバがゾーン転送を行わないから」
- ゾーン転送は**TCP 53**。転送を許可する相手（セカンダリ）をACL（Access Control List）で制限する → 誰にでも転送するとゾーン情報が漏れる

## 5. TTLとキャッシュ（◎）

- 各レコードの **TTL**（Time To Live） の間、キャッシュDNSサーバは結果を保持し、権威DNSに問い合わせ直さない
- ◎の定番：**サーバ移転（IPアドレスの変更）**
  - TTLが長いと、変更後も**古いIPアドレスがキャッシュに残り**、旧サーバへアクセスされ続ける
  - 対策：**移転の前にTTLを短くしておき**（古いTTL分の時間が過ぎるのを待つ）、切り替えた後で元に戻す
  - 記述の型：「キャッシュDNSサーバに古い情報が残る時間を短くし、切替後すぐに新しいIPアドレスが参照されるようにするため」
  - **なぜ「移転の数日前」に変えるのか（○）**：キャッシュDNSは、**受け取った時点のTTL**で期限を数える。権威DNSでTTLを変えても、すでにキャッシュされている情報には効かない
    - 直前に変えた場合：前日に「TTL＝1日」でキャッシュした情報は、Aレコードを書き換えた後も、最大1日使われ続ける
    - 数日前に変えた場合：古いTTL（1日）の情報は遅くとも1日後に期限が切れ、次の問い合わせから短いTTLで覚え直す → 切替当日は、短いTTLの時間で新しいアドレスが使われる
    - つまり、TTLを変えてから**元のTTL以上待つ**必要がある（「2日前」は1日に余裕を持たせた値）
    - 記述の型：「TTLの変更前に取得されたキャッシュは、元のTTLが経過するまで古い情報を保持し続けるから」
    - 覚え方：「TTLは、受け取った時点の消費期限。あとから期限を変えても、すでに配られた分には効かない」
- TTLを短くしすぎると、権威DNSへの問い合わせが増えて負荷が上がる
- 存在しない名前の応答もキャッシュされる（ネガティブキャッシュ、△）

## 6. 午後で問われるテーマと記述の型

### ◎ 権威DNSとキャッシュDNSの分離・配置

- **権威DNS（外部公開）**：DMZ（DeMilitarized Zone）に置く。インターネットからの問い合わせを受け付け、**再帰問い合わせは拒否**する
- **キャッシュDNS（社内用）**：内部LAN（Local Area Network）に置く。**社内からの再帰問い合わせだけ**受け付ける
- 兼用すると、オープンリゾルバとして攻撃の踏み台になる、キャッシュポイズニングの対象になる → [[DNSリフレクタ攻撃]]
- FWのルール
  - 外 → DMZの権威DNS：**UDP／TCP 53**
  - 内部のキャッシュDNS → 外：UDP／TCP 53（反復問い合わせ）
  - プライマリ → セカンダリ：TCP 53（ゾーン転送）

### ◎ DNSによる負荷分散

- **DNSラウンドロビン**：1つの名前に複数のAレコードを登録し、問い合わせごとに順番を変えて返す
- 欠点
  - **サーバの故障を検知しない** → 停止したサーバのアドレスも返し続ける
  - **キャッシュ**されるので、同じキャッシュDNSを使う多数の端末が同じサーバに集中し、偏る
- 記述の型：「DNSサーバはWebサーバの稼働状況を確認しないため、停止中のサーバのIPアドレスも応答してしまうから」
- 改善：負荷分散装置を使う、**GSLB**（Global Server Load Balancing、ヘルスチェックをして、稼働中・近いサイトのアドレスを返すDNS）を使う → [[負荷分散装置]]

### ○ スプリットDNS（内外で別の応答）

- 同じ名前に対して、**社内からは内部のアドレス、社外からはグローバルアドレス**を返す
- 方法：内部用と外部用で別々の権威DNSを持つ、または送信元で応答を切り替える
- 問われ方：「社内から公開サーバに、NAT（Network Address Translation）を経由せず直接アクセスさせる方法」
- **なぜ必要なのか**
  - 社内の端末が公開サーバの名前（`www.example.jp`）を引くと、普通は外部向けの権威DNSが答える**グローバルアドレス**が返る → 社内の端末なのに、わざわざ外側（FW・NAT）を回ってアクセスすることになる。構成によっては、そもそも届かない
  - かといって、社内から**IPアドレス**（`https://10.1.1.10/`）や内部用の別名でアクセスすると、**サーバ証明書の名前と一致せず、証明書エラー**になる → [[TLS]]
  - そこで、**名前は社外と同じ（証明書と一致）のまま、社内のDNSだけ内部のアドレスを答える**ようにする

```
社外の端末 → 外部向けの権威DNS（DMZ）
              「www.example.jp は 203.0.113.10（グローバル）」

社内の端末 → 社内のDNSサーバ
              「www.example.jp は 10.1.1.10（内部）」 ← 社内用に登録しておく
```

- 効果：社内からも `https://www.example.jp/` でアクセスする → 名前が証明書と一致するのでエラーにならず、名前解決の結果は内部のアドレスなので、社内から直接サーバに届く
- 記述の型：「社内の端末が参照するDNSサーバに、公開サーバのホスト名の内部IPアドレスを登録し、社内からも同じホスト名でアクセスさせる」
  - ポイントは2つ：**社内用のDNSに内部アドレスを登録する**こと、**アクセスする名前を証明書と同じホスト名にする**こと（後者が抜けると、IPアドレスでのアクセスのままでエラーは消えない）
- 覚え方：**「名前は証明書に合わせ、行き先はDNSで社内に向ける」**

### ○ キャッシュポイズニング

- 偽の応答を、正規の応答より先にキャッシュDNSに受け取らせ、**偽のIPアドレスをキャッシュさせる** → 利用者を偽サイトに誘導
- 偽の応答が受け入れられる条件：問い合わせの**ID（16ビット）と送信元ポート番号が一致**していること
- カミンスキー攻撃：存在しないサブドメインを次々に問い合わせ、何度も偽の応答を送り込む機会を作る
- 対策
  - **送信元ポート番号のランダム化**（当てるべき値を増やす）
  - **DNSSEC**（DNS Security Extensions）
  - キャッシュDNSを外部からの問い合わせに答えないようにする

### ○ DNSSEC

- 権威DNSの応答に**ディジタル署名**を付け、キャッシュDNSが検証する → **改ざんと、なりすましを検知**できる
- 上位ゾーンが下位ゾーンの鍵を保証する**信頼の連鎖**（DS（Delegation Signer）レコード）で、ルートまでたどる
- レコード：DNSKEY（公開鍵）、RRSIG（署名）、DS（下位ゾーンの鍵のハッシュ）
- **暗号化はしない**（中身は見える）→ 盗聴対策ではない
- 応答が大きくなる → EDNS0、TCPが必要になり、リフレクタ攻撃での増幅にも使われる
- 記述の型：「応答に付与された署名を検証することで、応答が改ざんされていないことを確認できるから」

### ○ メールとDNS

- 送信側のメールサーバは、宛先ドメインの **MXレコード**を引いて配送先を決める
- MXを複数登録し、優先度を変えて**メールサーバを冗長化**する（優先度の値が小さい方が先）
- 受信側は、接続してきたサーバのIPアドレスを**逆引き**（PTR）し、さらに正引きして一致するか確かめる → なりすまし対策
- SPF：送信元ドメインのTXTレコードに、送信してよいサーバのIPアドレスを書く
- → [[SPF・DKIM・DMARC]]

### △ DNSの暗号化

- **DoT**（DNS over TLS（Transport Layer Security））：TCP 853
- **DoH**（DNS over HTTPS、HTTPS：Hypertext Transfer Protocol Secure）：TCP 443 → 通常のWeb通信と区別しにくく、社内のDNSフィルタリングを迂回される問題がある

## 7. 覚え方

- **「権威は答える人、キャッシュは聞いて回る人」**：権威は自分のゾーンだけ、キャッシュは代わりに聞いて覚えておく
- **再帰は「全部調べて」、反復は「知ってる所まで」**
- **ゾーン転送は「シリアルが増えないと、セカンダリは動かない」**
- **移転の前に「TTLを先に短く」**：引っ越しの前に、転送届（キャッシュ）の有効期限を短くしておく
- **ラウンドロビンは「生きているか見ないで、順番に配るだけ」**
- **MXは「小さい数字が先」**：1番目の候補
- **DNSSECは「ハンコは押すが、封筒には入れない」**：改ざんは分かる、中身は見える
- **UDPで足りなければTCP**：ゾーン転送と大きい応答はTCP 53

## 8. 勉強の優先順位

1. 権威DNSとキャッシュDNSの役割、配置（DMZ／内部）とFWのルールを構成図で説明できるようにする
2. ゾーン転送とSOAのシリアル番号、反映されない理由を30〜40字で書けるようにする
3. サーバ移転の前にTTLを短くする理由
4. DNSラウンドロビンの欠点と改善策
5. リソースレコード（SOA、NS、A、AAAA、CNAME、MX、PTR、TXT）の書き方を穴埋めで答えられるようにする
6. キャッシュポイズニングとDNSSECの仕組み
7. DoH／DoTは名前とポート番号だけ押さえればよい

> [!tip] 得点につながる覚え方
> DNSは単独の大問になることも、**サーバ移転、メール、負荷分散、セキュリティの問題の一部**として出ることもある。午後で構成図にDNSサーバが出てきたら、「権威かキャッシュか」「どこに置くか」「誰からの問い合わせに答えるか」「TTLとキャッシュの影響は」の4点を確認する。
