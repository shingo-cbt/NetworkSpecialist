# プロキシ まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

プロキシの機能をクラウドで提供するSWG（Secure Web Gateway）や、ゼロトラストの考え方は [[ゼロトラスト・SASE]] を参照。

## 1. プロキシの基本（◎）

- **プロキシ（プロキシサーバ）**：クライアントの代わりにサーバへアクセスし、通信を**中継**する
- 2種類

| | フォワードプロキシ | リバースプロキシ |
|---|---|---|
| 置き場所 | **社内（利用者側）** | **サーバ側**（Webサーバの手前） |
| 代わりをする相手 | **社内の利用者**の代わりにインターネットへ | **Webサーバ**の代わりに外部からの要求を受ける |
| 主な目的 | アクセス制御、URL（Uniform Resource Locator）フィルタリング、ログ、キャッシュ、**利用者の認証** | 負荷分散、TLS（Transport Layer Security）終端、キャッシュ、WAF（Web Application Firewall） |

- フォワードプロキシを使うと、**インターネットへのWebアクセスをプロキシ経由に限定**できる（FW（Firewall）で端末からの直接の80／443を拒否し、プロキシだけ許可）→ [[FW]]

## 2. フォワードプロキシの動き（◎）

- 端末はプロキシに、**URL全体を書いたリクエスト**を送る（`GET http://www.example.jp/ HTTP/1.1`）
- **HTTPS（HTTP Secure）**は、**CONNECTメソッド**でプロキシにトンネルを張らせ、その中でTLSを通す
  - プロキシは**通信先のホスト名とポート**しか分からない（中身は見えない）
  - 中身を検査するには**TLSインスペクション**（プロキシが復号する。端末にプロキシのルート証明書が必要）→ [[TLS]]
- **プロキシ認証**：プロキシが利用者を認証し、誰がどこにアクセスしたかを記録する
  - 未認証だと **407 Proxy Authentication Required** が返る → [[HTTP]]
  - Windowsのドメインに参加したPCは、ログオン時の認証情報（Kerberos（ケルベロス）など）で自動的に認証できる（統合認証）

### 明示的プロキシと透過型プロキシ（○）

| | 明示的プロキシ | 透過型プロキシ |
|---|---|---|
| 端末の設定 | **ブラウザにプロキシを設定**する（手動、PAC、WPAD） | **不要**（ネットワーク側で通信をプロキシに転送する） |
| HTTPSの扱い | CONNECTで扱える | 宛先のホスト名はSNI（Server Name Indication）などで判断する |

## 3. プロキシの設定の配り方（◎）

- **PAC（Proxy Auto-Config）ファイル**：宛先ごとに**プロキシを使うか、直接接続するか**を決めるスクリプト（JavaScriptの関数 `FindProxyForURL`）
  - 例：社内のサーバ（`*.corp.example.jp`）は直接（DIRECT）、それ以外はプロキシへ
- **WPAD（Web Proxy Auto-Discovery）**：端末がPACファイルの場所を**自動で見つける**仕組み（DHCP（Dynamic Host Configuration Protocol）のオプション、またはDNS（Domain Name System）で `wpad.ドメイン` を探す）
  - 攻撃者が偽のWPADを用意すると、通信を自分のプロキシに向けさせられる（△）
- **プロキシの例外設定**：プロキシを通さず**直接アクセスする宛先**を指定する
  - 社内のサーバ（プロキシを経由すると遠回り、プロキシからは社内に届かない）
  - **大量の通信をするクラウドサービス**（Web会議など）→ プロキシの負荷・遅延を避ける（ローカルブレイクアウトと同じ考え方）→ [[SD-WAN]]
  - 令和4年春 午後Ⅰ 問3では、プロキシの例外に**業務サーバと営業支援サーバのFQDN（Fully Qualified Domain Name）**を登録する、が解答になった
- 記述の型：「社内のサーバ宛ての通信をプロキシを経由せず直接送るため、PACファイルで当該FQDNをDIRECTに指定する」

## 4. 午後で問われるテーマと記述の型

### ◎ プロキシ経由で通信できない原因

- プロキシの例外に入っていない社内サーバに、プロキシ経由でアクセスしようとして失敗する
- プロキシが通さないプロトコル（WebSocketを解釈できない、HTTPS以外のポートへのCONNECTを禁止している）→ [[WebSocket]]
- プロキシ認証に失敗する（407）、TLSインスペクションの証明書エラー
- プロキシの先のサーバの問題（502／504）→ [[HTTP]]

### ◎ プロキシからSWGへの移行

- 社内のプロキシの代わりに**クラウドのSWG**を使う（テレワークの端末も同じ制御を受けられる、社内のプロキシの負荷・回線の混雑を解消する）
- PACファイルの転送先をSWGに変える、端末にSWGのルート証明書を配る、SWGの送信元IP（Internet Protocol）アドレスでクラウドサービスへのアクセスを制限する
- 令和7年春 午後Ⅰ 問3、令和4年春 午後Ⅰ 問2で出題されている
- → [[ゼロトラスト・SASE]]

### ○ プロキシの冗長化と負荷

- プロキシが止まると、全員がインターネットを使えなくなる → 2台以上にし、PACファイルで両方を指定する（1台目に届かなければ2台目）、負荷分散装置で振り分ける
- → [[負荷分散装置]]

### ○ ログと追跡

- プロキシのログには**利用者（認証した場合）・アクセス先のURL・時刻**が残る → 不正なアクセスや情報漏えいの調査に使う
- リバースプロキシ・LB（Load Balancer）の先のサーバでは、元のクライアントのIPアドレスを **X-Forwarded-For** で知る

## 5. 覚え方

- **フォワードプロキシは「社員の代わりに外へ行く使い走り」、リバースプロキシは「サーバの代わりに客を受ける受付」**
- **HTTPSは「CONNECTで素通しのトンネル」**：中身を見るならTLSインスペクション（ルート証明書を配る）
- **PACは「宛先ごとの行き方の地図」、WPADは「地図の置き場所を自動で探す」**
- **社内サーバとWeb会議は「例外（DIRECT）」**
- **407はプロキシの認証**

## 6. 勉強の優先順位

1. PACファイル・プロキシの例外設定の目的を30〜40字で書けるようにする
2. フォワードプロキシとリバースプロキシの違い
3. HTTPSとCONNECTメソッド、TLSインスペクション
4. プロキシ経由で通信できない原因（例外、認証、プロトコル）
5. SWGへの移行で必要な作業
6. 透過型プロキシ、WPADは概要を知っている程度でよい

> [!tip] 得点につながる覚え方
> プロキシの問題では、**どの宛先がプロキシを通り、どの宛先が直接か**を構成図に色分けして書き込む。PACファイル・例外設定・FWのルールの3つが一致しているかを確認する。
