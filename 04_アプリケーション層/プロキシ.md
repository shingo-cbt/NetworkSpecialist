# プロキシ まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

プロキシの機能をクラウドで提供するSWG（Secure Web Gateway）や、ゼロトラストの考え方は [[ゼロトラスト・SASE]] を参照。

## 1. プロキシの基本（◎）

- **プロキシ（プロキシサーバ）**：クライアントの代わりにサーバへアクセスし、通信を**中継**する
- 2種類

| | フォワードプロキシ | リバースプロキシ |
|---|---|---|
| 置き場所 | **社内（利用者側）** | **サーバ側**（Webサーバの手前） |
| 代わりをする相手 | **社内の利用者**の代わりにインターネットへ | **Webサーバ**の代わりに外部からの要求を受ける |
| 主な目的 | アクセス制御、URL（Uniform Resource Locator）フィルタリング、ログ、キャッシュ、**利用者の認証** | 負荷分散、TLS（Transport Layer Security）終端、キャッシュ、WAF（Web Application Firewall） |

- フォワードプロキシを使うと、**インターネットへのWebアクセスをプロキシ経由に限定**できる（FW（Firewall）で端末からの直接の80／443を拒否し、プロキシだけ許可）→ [[FW]]

## 2. フォワードプロキシの動き（◎）

- 端末はプロキシに、**URL全体を書いたリクエスト**を送る（`GET http://www.example.jp/ HTTP/1.1`）

**GETメソッドで、直接アクセスする場合とプロキシ経由の場合のリクエストの違い**

① Webサーバに直接送る場合

```
GET /search?q=network&page=2 HTTP/1.1   ← リクエスト行：メソッド、パス（＋クエリ）、バージョン
Host: www.example.jp                     ← 必須。どのサイトか（パスにはホスト名がないため）
User-Agent: Mozilla/5.0 ...
Accept-Language: ja
Cookie: session=abc123
                                         ← 空行：ヘッダの終わり（GETは通常ボディなし）
```

- 1行目には**パスだけ**を書く。接続先のサーバは決まっているので、どのサイト宛てかは**Hostヘッダ**で伝える（バーチャルホスト）
- 送りたいデータは**クエリ**（`?q=network&page=2`）としてURLに付ける。`&` で複数並べる

② プロキシ経由で送る場合（HTTP：Hypertext Transfer Protocol）

```
GET http://www.example.jp/search?q=network&page=2 HTTP/1.1   ← URL全体を書く
Host: www.example.jp
Proxy-Authorization: Basic dXNlcjpwYXNz                      ← プロキシの認証情報（必要なとき）
User-Agent: Mozilla/5.0 ...
Cookie: session=abc123
                                                             ← 空行
```

- 1行目に**URL全体**（`http://` から）を書く。端末がTCP（Transmission Control Protocol）で接続している相手はプロキシなので、「どこのサーバの、どのページか」を全部伝える必要がある
- プロキシの認証が必要なら**Proxy-Authorization**ヘッダを付ける。ないか誤っていると**407**が返る
- HTTPなので、プロキシはパス・クエリ・Cookie・中身まで**すべて見える**（パス単位のフィルタリングやウイルス検査ができる）

③ プロキシ経由で送る場合（HTTPS）

```
CONNECT www.example.jp:443 HTTP/1.1     ← ここだけ平文。プロキシに見えるのはホスト名とポート
Host: www.example.jp:443

（以降、端末とWebサーバの間でTLSのハンドシェイク → GETなどはトンネルの中で暗号化）
```

- 覚え方：**「直接ならパスだけ、プロキシ経由なら住所を全部書く」**

- **HTTPS**（HTTP Secure）は、**CONNECTメソッド**でプロキシにトンネルを張らせ、その中でTLSを通す
  - プロキシは**通信先のホスト名とポート**しか分からない（中身は見えない）
  - 中身を検査するには**TLSインスペクション**（プロキシが復号する。端末にプロキシのルート証明書が必要）→ [[TLS]]
- **プロキシ認証**：プロキシが利用者を認証し、誰がどこにアクセスしたかを記録する
  - 未認証だと **407 Proxy Authentication Required** が返る → [[HTTP]]
  - Windowsのドメインに参加したPCは、ログオン時の認証情報（Kerberos（ケルベロス）など）で自動的に認証できる（統合認証）

### 明示的プロキシと透過型プロキシ（○）

- 違いの出発点：**端末が「プロキシを使っている」と知っているかどうか**

**明示的プロキシ**：端末は、プロキシと話していると知っている

```
端末（ブラウザにプロキシ 10.0.0.8:8080 を設定済み）
  │ ① TCPで、プロキシ（10.0.0.8:8080）に接続
  │ ② 「CONNECT www.example.jp:443」と、行き先をプロキシに伝える ← 平文
  ↓
プロキシ ──→ www.example.jp:443 に接続し、トンネルを中継
```

- 端末は**最初からプロキシ宛て**に接続し、行き先を**CONNECTの行**（HTTPならGETのURL全体）で教える
- 名前解決（DNS（Domain Name System））も、普通はプロキシが行う

**透過型プロキシ**：端末は、Webサーバと直接話しているつもり

```
端末（プロキシの設定なし）
  │ ① 自分でDNSを引く → www.example.jp ＝ 203.0.113.10
  │ ② TCPで、203.0.113.10:443 に接続しようとする（宛先はWebサーバ）
  ↓
ルータ・FW・L4スイッチが、この通信を横取りしてプロキシへ回す
  ↓
プロキシ：「宛先 203.0.113.10:443 の通信が来た。でも、どのサイトか教えてもらっていない」
```

- 端末はプロキシの存在を知らないので、**CONNECTの行を送らない** → プロキシは、横取りした通信の中から**自分で行き先を探す**

**透過型でのホスト名の手がかり（ここでSNI（Server Name Indication）が出てくる）**

| 通信 | 手がかり | 理由 |
|---|---|---|
| HTTP | **Hostヘッダ** | 平文なので、そのまま読める |
| HTTPS | **SNI**（TLSのClientHelloの中） | 暗号化される前の最初のメッセージに、**ホスト名が平文で入っている**。ここしか読めない |
| （どちらも） | 宛先のIPアドレス | 1つのIPアドレスに多数のサイトがある（CDN（Content Delivery Network）など）と、どのサイトかわからない |

- HTTPSで、**明示的プロキシのCONNECTの行の代わり**をするのがSNI。どちらも「封筒の宛名」で、ホスト名単位のフィルタリングやログに使える → [[TLS]]

**違いのまとめ**

| | 明示的プロキシ | 透過型プロキシ |
|---|---|---|
| 端末の設定 | **必要**（手動、PAC、WPAD） | **不要** |
| 端末の接続先 | プロキシ（例：8080番） | Webサーバ（443番）。ネットワーク機器が横取りする |
| ホスト名の知り方（HTTPS） | **CONNECTの行**で、端末が教える | **SNIを読む**（自分で探す） |
| 名前解決 | 普通はプロキシが行う | **端末が自分で行う**（端末からのDNSを許可する必要がある） |
| **利用者の認証**（407） | **できる** | **難しい**。端末はプロキシと話しているつもりがないので、認証を要求されても応えられない → IPアドレスなどで識別する |
| 向いている場面 | 社員のPC（認証して、誰がアクセスしたかを記録する） | プロキシを設定できない機器（ゲストの端末、IoT（Internet of Things）機器、プロキシ非対応のアプリ） |

- 試験でのポイント（○）
  - 「**端末の設定を変えずに**プロキシを導入したい」→ 透過型
  - 「**利用者ごとに認証して、ログを残したい**」→ 明示的（透過型では難しい）
  - 透過型でHTTPSの中身まで検査するなら、やはり**TLSインスペクション**と端末へのルート証明書の配布が必要
  - SNIを暗号化する**ECH**（Encrypted Client Hello）が使われると、透過型ではホスト名が読めなくなる（△）
- 覚え方：**「明示的は、行き先を自分で言う客。透過型は、黙って来る客の封筒（SNI）を見て、行き先を知る」**

## 3. プロキシの設定の配り方（◎）

- **PAC（Proxy Auto-Config）ファイル**：宛先ごとに**プロキシを使うか、直接接続するか**を決めるスクリプト（JavaScriptの関数 `FindProxyForURL`）
  - 例：社内のサーバ（`*.corp.example.jp`）は直接（DIRECT）、それ以外はプロキシへ
- **WPAD（Web Proxy Auto-Discovery）**：端末がPACファイルの場所を**自動で見つける**仕組み（DHCP（Dynamic Host Configuration Protocol）のオプション、またはDNSで `wpad.ドメイン` を探す）
  - 攻撃者が偽のWPADを用意すると、通信を自分のプロキシに向けさせられる（△）
- **プロキシの例外設定**：プロキシを通さず**直接アクセスする宛先**を指定する
  - 社内のサーバ（プロキシを経由すると遠回り、プロキシからは社内に届かない）
  - **大量の通信をするクラウドサービス**（Web会議など）→ プロキシの負荷・遅延を避ける（ローカルブレイクアウトと同じ考え方）→ [[SD-WAN]]
  - 令和4年春 午後Ⅰ 問3では、プロキシの例外に**業務サーバと営業支援サーバのFQDN**（Fully Qualified Domain Name）を登録する、が解答になった
- 記述の型：「社内のサーバ宛ての通信をプロキシを経由せず直接送るため、PACファイルで当該FQDNをDIRECTに指定する」

## 4. 午後で問われるテーマと記述の型

### ◎ プロキシ経由で通信できない原因

- プロキシの例外に入っていない社内サーバに、プロキシ経由でアクセスしようとして失敗する
- プロキシが通さないプロトコル（WebSocketを解釈できない、HTTPS以外のポートへのCONNECTを禁止している）→ [[WebSocket]]
- プロキシ認証に失敗する（407）、TLSインスペクションの証明書エラー
- プロキシの先のサーバの問題（502／504）→ [[HTTP]]

### ◎ プロキシからSWGへの移行

- 社内のプロキシの代わりに**クラウドのSWG**を使う（テレワークの端末も同じ制御を受けられる、社内のプロキシの負荷・回線の混雑を解消する）
- PACファイルの転送先をSWGに変える、端末にSWGのルート証明書を配る、SWGの送信元IP（Internet Protocol）アドレスでクラウドサービスへのアクセスを制限する
- 令和7年春 午後Ⅰ 問3、令和4年春 午後Ⅰ 問2で出題されている
- → [[ゼロトラスト・SASE]]

### ○ プロキシの冗長化と負荷

- プロキシが止まると、全員がインターネットを使えなくなる → 2台以上にし、PACファイルで両方を指定する（1台目に届かなければ2台目）、負荷分散装置で振り分ける
- → [[負荷分散装置]]

### ○ ログと追跡

- プロキシのログには**利用者（認証した場合）・アクセス先のURL・時刻**が残る → 不正なアクセスや情報漏えいの調査に使う
- リバースプロキシ・LB（Load Balancer）の先のサーバでは、元のクライアントのIPアドレスを **X-Forwarded-For** で知る

## 5. 覚え方

- **フォワードプロキシは「社員の代わりに外へ行く使い走り」、リバースプロキシは「サーバの代わりに客を受ける受付」**
- **HTTPSは「CONNECTで素通しのトンネル」**：中身を見るならTLSインスペクション（ルート証明書を配る）
- **PACは「宛先ごとの行き方の地図」、WPADは「地図の置き場所を自動で探す」**
- **社内サーバとWeb会議は「例外（DIRECT）」**
- **407はプロキシの認証**

## 6. 勉強の優先順位

1. PACファイル・プロキシの例外設定の目的を30〜40字で書けるようにする
2. フォワードプロキシとリバースプロキシの違い
3. HTTPSとCONNECTメソッド、TLSインスペクション
4. プロキシ経由で通信できない原因（例外、認証、プロトコル）
5. SWGへの移行で必要な作業
6. 透過型プロキシ、WPADは概要を知っている程度でよい

> [!tip] 得点につながる覚え方
> プロキシの問題では、**どの宛先がプロキシを通り、どの宛先が直接か**を構成図に色分けして書き込む。PACファイル・例外設定・FWのルールの3つが一致しているかを確認する。
