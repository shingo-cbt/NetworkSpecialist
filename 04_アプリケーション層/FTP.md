# FTP まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

## 1. FTPの基本（○）

- TCP（Transmission Control Protocol）でファイルを転送するプロトコル
- **制御用とデータ用の2本のTCPコネクション**を使うのが最大の特徴 → FW（Firewall）・NAPT（Network Address Port Translation）の問題の原因になる

| コネクション | ポート | 役割 | 張っている期間 |
|---|---|---|---|
| **制御コネクション** | サーバの**TCP 21** | コマンドと応答（ログイン、ディレクトリ移動など） | ログイン中ずっと |
| **データコネクション** | アクティブ：サーバの**TCP 20**から／パッシブ：サーバの任意のポートへ | ファイル本体、ファイル一覧 | 転送のたびに張って切る |

- ユーザ名・パスワード・データがすべて**平文**で流れる
- 午前の誤り選択肢の定番：「FTP（File Transfer Protocol）はUDP（User Datagram Protocol）を使う」→ 誤り（UDPを使うのはTFTP（Trivial File Transfer Protocol））

## 2. アクティブモードとパッシブモード（◎）

### アクティブモード

1. クライアントがサーバのTCP 21に制御コネクションを張る
2. クライアントが **PORTコマンド** で「自分のIP（Internet Protocol）アドレスとポート番号」を伝える
3. **サーバ（TCP 20）からクライアントへ**データコネクションを張る

### パッシブモード

1. クライアントがサーバのTCP 21に制御コネクションを張る
2. クライアントが **PASVコマンド** を送る
3. サーバが **227応答** で「サーバのIPアドレスとポート番号（1024以上の任意の番号）」を返す
4. **クライアントからサーバへ**データコネクションを張る

| | アクティブ | パッシブ |
|---|---|---|
| データコネクションを張る向き | **サーバ → クライアント** | **クライアント → サーバ** |
| アドレスを通知するコマンド | PORT（クライアントが通知） | PASV → 227応答（サーバが通知） |
| サーバ側のデータ用ポート | 20 | 任意（1024以上） |
| 困る場所 | **クライアント側のFW・NAPT** | **サーバ側のFW**（任意ポートの許可） |

- IPv6でも使えるよう拡張したのが **EPRT（Extended PORT、PORTの拡張）／EPSV（Extended Passive Mode、PASVの拡張）**（△）

## 3. 午後で問われるテーマと記述の型

### ◎ パッシブモードを使う理由

- 社内の端末がFW・NAPTの内側にいる構成が普通
- アクティブモードだと、**外のサーバから内側の端末に向けて新しいコネクションが来る** → FWは外→内を通さない／NAPTはどの端末に転送すべきか分からない
- パッシブモードなら、データコネクションも**内側から張る**ので、内→外の許可だけで通る
- 記述の型：「データコネクションをクライアント側から確立するので、FWで外部からの接続を許可する必要がないから」
- 記述の型（アクティブが失敗する理由）：「サーバからクライアントへのデータコネクションが、FWで遮断される（NAPTで変換できない）から」

### ◎ FWの許可ルール（サーバを公開する場合）

- パッシブモード
  - 外 → サーバ TCP 21（制御）
  - 外 → サーバ **パッシブ用のポート範囲**（データ）→ サーバ側で範囲を狭く設定して、FWではその範囲だけ許可する
- アクティブモード
  - 外 → サーバ TCP 21（制御）
  - サーバ TCP 20 → 外（データ）
- 問われ方：「FWのフィルタリングルール表の空欄を埋める」

### ◎ NAPT・FWとALG

- PORTコマンドと227応答は、**IPアドレスとポート番号をデータの中（アプリケーション層）に書いている**
- NAPTはIPヘッダとTCPヘッダしか書き換えない → データの中のアドレスは**プライベートIPのまま**相手に届き、そのアドレスには接続できない
  - 例：サーバがNAPT（静的NAT（Network Address Translation））の内側にあると、227応答でプライベートIPを返してしまう
- 対策
  - FW・ルータの **ALG（Application Level Gateway、アプリケーションレベルゲートウェイ）** 機能：制御コネクションの中身を見て、**PORT／227のアドレスを書き換え**、必要なデータコネクションを**一時的に許可**する
  - サーバ側で「通知するIPアドレス」をグローバルIPに設定する
- 記述の型：「制御コネクションで通知されるIPアドレスがNAPTで変換されず、プライベートIPアドレスのまま相手に届くから」
- **制御コネクションを暗号化（FTPS：FTP over SSL/TLS）するとALGが中身を読めず、書き換えも許可もできない** → 次の項目とつながる
- → [[NAT・NAPT]]

### ○ 暗号化（FTPS と SFTP）

| | FTPS | SFTP（SSH File Transfer Protocol） |
|---|---|---|
| 正体 | **FTP＋TLS**（Transport Layer Security） | **SSH（Secure Shell）のサブシステム**（FTPとは別物） |
| ポート | 明示的：21で開始し**AUTH TLS**で暗号化／暗黙的：990 | **TCP 22** |
| コネクション | 制御とデータの**2本のまま** | **1本だけ** |
| FW | ALGが効かないので、データ用ポート範囲の固定と許可が必要 | 22番を許可するだけ |

- 問われ方：「FTPの代わりにSFTPを使う利点」
- 記述の型：「通信が暗号化され、1本のTCPコネクションで済むためFWの設定が簡単になるから」
- → [[TLS]]

### △ その他

- **匿名FTP（anonymous）**：ユーザ名 anonymous で誰でもログインできる公開用FTP
- 主な応答コード：220（接続準備完了）、331（パスワード要求）、230（ログイン成功）、**227（パッシブモード開始）**、150（データ転送開始）、226（転送完了）
- 転送モード：テキスト（ASCII（American Standard Code for Information Interchange）、改行コードを変換する）／バイナリ（そのまま送る）。画像などをASCIIで送ると壊れる

### ○ TFTP（ついでに押さえる）

- **UDP 69**、**認証なし**、機能は送受信だけ
- ネットワーク機器の**設定ファイル・ファームウェアの転送**、PXE（Preboot eXecution Environment）ブートで使う
- 問われ方：「機器の設定ファイルを取得するのに使うプロトコル」

## 4. 覚え方

- **「21で話して、20で運ぶ」**：制御は21、アクティブのデータは20
- **アクティブは「サーバが攻めてくる（Active）」、パッシブは「サーバは待つだけ（Passive）」**
  - 内側の端末にとって、外から攻めてくる＝FW・NAPTで止まる → だからパッシブ
- **PORTは「私の番号はここ」、PASVは「あなたの番号を教えて」**
- **「アドレスがデータの中にある」からNAPTを越えられない → ALGが中身を書き換える**（SIP（Session Initiation Protocol）と同じ構造）
- **FTPSはFTPに鎧を着せたもの、SFTPは別人（SSH）**
- **TFTPは「Trivial（ささいな）」**：UDP、認証なし、機器の設定用

## 5. 勉強の優先順位

1. アクティブとパッシブで、データコネクションを張る向きを図で描けるようにする
2. パッシブモードを使う理由（FW・NAPTの内側の端末）を30〜40字で書けるようにする
3. FWの許可ルール（21番、パッシブ用ポート範囲、20番）を表で埋められるようにする
4. NAPTで失敗する理由と ALG の役割
5. FTPSとSFTPの違い（ポート、コネクション数）
6. 応答コードは 227 だけ覚えればよい

> [!tip] 得点につながる覚え方
> FTPは「**アドレスとポート番号をデータの中で通知し、別のコネクションを後から張る**」プロトコルの代表。この構造がFW・NAPTと相性が悪い、という理由づけは **SIP／RTP（Real-time Transport Protocol、VoIP：Voice over IP）** でもそのまま使える。
