# SMTP まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

## 1. メールの全体像（○）

```
[送信者のPC] ─SMTP（587）→ [送信側メールサーバ] ─SMTP（25）→ [受信側メールサーバ] ─POP3／IMAP→ [受信者のPC]
   メールソフト                  （MX（Mail Exchanger）を引いて配送）       メールボックスに保存
```

- **SMTP（Simple Mail Transfer Protocol）**：メールを**送る**（転送する）プロトコル
  - PC → 送信側メールサーバ、メールサーバ → メールサーバの両方で使う
- **POP3（Post Office Protocol version 3）／IMAP（Internet Message Access Protocol）**：受信者がメールボックスから**受け取る**プロトコル → [[POP・IMAP]]
- 送信側メールサーバは、宛先ドメインの**MXレコード**をDNS（Domain Name System）で引いて、配送先のメールサーバを決める → [[DNS]]

### SMTPのやり取りと配送の仕組み（○）

- **コマンドの流れ**（送信側＝クライアント、受信側＝サーバ）

```
受信側：220 mail.example.jp ready         ← 接続できた
送信側：EHLO sender.example.com           ← あいさつ（古い形はHELO）
受信側：250 OK
送信側：MAIL FROM:<taro@example.com>      ← エンベロープFrom
受信側：250 OK
送信側：RCPT TO:<hanako@example.jp>       ← エンベロープの宛先（宛先が複数なら繰り返す）
受信側：250 OK
送信側：DATA                              ← 本文を送る合図
受信側：354 本文をどうぞ
送信側：（ヘッダと本文）
送信側：.                                 ← 「.」だけの行で本文の終わり
受信側：250 OK（受け付けた）
送信側：QUIT
```

- **応答コード**：先頭の数字で意味が決まる

| コード | 意味 | 送信側の動き |
|---|---|---|
| 2xx（220、250など） | 成功 | 次へ進む |
| 3xx（354） | 続きを送ってよい | 本文を送る |
| **4xx**（421、450など） | **一時的なエラー**（混んでいる、少し待って） | キューにためて、あとで**再送する** |
| **5xx**（550など） | **恒久的なエラー**（宛先がない、拒否） | 再送せず、すぐに**エラーメール**を返す |

- **蓄積転送（ストアアンドフォワード）**：メールサーバは、受け取ったメールをいったん保存してから次へ送る
  - 受信側のサーバが止まっている・4xxが返る → 送信側のサーバはメールを**キュー**にため、間隔を空けて再送する（何日続けるかはサーバの設定による）
  - それでも届かなければ、エンベロープFromの宛先に**エラーメール**（バウンスメール）を返す
  - だから、受信側のサーバが短時間止まっても、メールはすぐには失われない（移行・切替の問題で問われる）
- **Receivedヘッダ**：メールサーバを1つ通るたびに、ヘッダの先頭に追加される → 下から上へたどると、**どのサーバを経由したか**が分かる（迷惑メールの送信元の調査、配送の遅れの原因の切り分け）
- 問われ方：「コマンドの順番」「受信側のメールサーバを停止しても、メールが失われない理由」「4xxと5xxで送信側の動作がどう違うか」
- 覚え方：**「4は『あとでまた』、5は『もう来るな』」**

## 2. ポート番号（◎）

| ポート | 用途 | 認証 |
|---|---|---|
| **TCP（Transmission Control Protocol） 25** | **メールサーバ同士の転送** | なし（相手を問わず受け付ける） |
| **TCP 587（サブミッションポート）** | **PC → 送信側メールサーバ**（メールの投稿） | **SMTP-AUTH**（SMTP認証）でユーザを確認する |
| TCP 465（SMTPS（SMTP over SSL/TLS）） | PC → 送信側メールサーバ（最初からTLS（Transport Layer Security）で暗号化） | SMTP-AUTH |

- **STARTTLS**：25番や587番で接続した後、途中からTLSに切り替える
- 午前の定番：「サブミッションポートの番号と目的」

### 587（STARTTLS）と465（SMTPS）の違い：暗号化を始めるタイミング

| | TCP 587（サブミッションポート） | TCP 465（SMTPS） |
|---|---|---|
| 用途・認証 | PC → 送信用メールサーバ、SMTP-AUTH | **同じ** |
| 暗号化 | **平文で接続してから**、STARTTLSでTLSに切り替える | **最初からTLS**で接続する |

```
587：PC ──（平文）── 接続 →「STARTTLS」→ ここからTLS → 認証・送信
465：PC ══（TLS）══ 接続した瞬間からTLS → 認証・送信
```

- [[LDAP]]（Lightweight Directory Access Protocol）のStartTLS（389番のまま途中で暗号化）とLDAPS（LDAP over SSL/TLS、636番で最初から暗号化）と同じ関係。POP3・IMAP、FTP（AUTH TLS）にも同じ2つの方式がある → [[TLS]]
- STARTTLSは平文と**同じポート番号**、○○Sは**専用のポート番号** → FWで許可するポートが変わる
- 覚え方：**「587は入ってから鍵をかける（STARTTLS）、465は最初から鍵のかかった通路（SMTPS）」**

### SMTP-AUTHとSMTPSの違い：認証と暗号化（混同しやすい）

| | SMTP-AUTH | SMTPS |
|---|---|---|
| 目的 | **送信者の認証**（ID・パスワードで正規の利用者か確かめる） | **通信の暗号化**（中身やパスワードの盗聴を防ぐ） |
| 防ぐもの | 第三者が自社のメールサーバで勝手に送る（踏み台） | 通信の盗聴 |
| たとえ | 受付で**社員証を確かめる** | 受付までの道を**トンネルにする** |

- 2つは**組み合わせて**使う：SMTP-AUTHだけで暗号化しないと、ID・パスワードが平文で流れる → **TLSの中（SMTPS、またはSTARTTLSの後）でSMTP-AUTHを行う**
- LDAPの「シンプル認証（認証）は平文だと危ないので、LDAPS・StartTLS（暗号化）で守る」と同じ関係
- 試験の主役は**587＋SMTP-AUTH**（OP25Bの対象外で、認証してから送れる）。465は「最初からTLS」と区別できればよい
- 覚え方：**「SMTP-AUTHは社員証の確認（誰か）、SMTPSは通路のトンネル（盗聴防止）。社員証はトンネルの中で見せる」**

## 3. エンベロープとヘッダ（◎）

| | エンベロープ（封筒） | ヘッダ（便箋に書いた差出人） |
|---|---|---|
| 送信元 | **MAIL FROM**（エンベロープFrom） | **From:**（メールソフトに表示される差出人） |
| 宛先 | **RCPT TO** | To:、Cc: |
| 誰が使う | **メールサーバが配送に使う** | 利用者が見る |

- エンベロープとヘッダの送信元は**別々に、自由に書ける** → ヘッダのFromを偽った**なりすましメール**が送れる
- BCC（Blind Carbon Copy）は、エンベロープの宛先（RCPT TO）にだけ入れ、ヘッダには書かない（△）
- 配送できないときのエラーメール（バウンスメール）は、**エンベロープFromの宛先**に返る
- → [[SPF・DKIM・DMARC]]（送信元の正しさの確認）

## 4. 午後で問われるテーマと記述の型

### ◎ OP25B（Outbound Port 25 Blocking）

- ISP（Internet Service Provider）が、自社の利用者（動的なIP（Internet Protocol）アドレス）から**外部のメールサーバのTCP 25番への通信を遮断**する
  - 目的：**ウイルスに感染したPCが、直接ほかのメールサーバへ迷惑メールを大量送信する**のを防ぐ
  - 利用者は、ISPのメールサーバ、または**サブミッションポート（587）でSMTP-AUTHを使って**自分のメールサーバに送る
- 企業でも同じ考え方：**社内のPCから外部へのTCP 25はFW（Firewall）で拒否し、社内のメールサーバだけに許可**する
- 記述の型：「マルウェアに感染した端末から外部のメールサーバへ直接迷惑メールが送信されることを防ぐため」
- 記述の型（587を使う理由）：「OP25Bの対象外となり、SMTP-AUTHで利用者を認証してから送信できるため」
- **補足：587と25は別々の通信**（587は送信元ではなく、メールサーバが待ち受ける**宛先**のポート）

```
【区間1】PC → 自社のメールサーバ（投稿）
  送信元ポート：52345（PCが適当に選ぶ）／宛先ポート：587（SMTP-AUTHで認証）
【区間2】自社のメールサーバ → 相手のメールサーバ（転送）
  送信元ポート：40123（サーバが適当に選ぶ）／宛先ポート：25
```

- **補足：どこで止めるか・何を止めるか**

| 通信 | 止めるか | 止める場所 |
|---|---|---|
| **PC** → 外部のメールサーバの25番 | **止める** | 家庭：**ISPのネットワーク**（本来のOP25B）／会社：**会社のFW** |
| PC → 自社のメールサーバの587番 | 止めない（認証付きの正規の投稿） | − |
| **メールサーバ** → 相手のメールサーバの25番 | 止めない（サーバ同士の転送） | − |

  - テレワークの社員が自宅から会社のメールサーバに送るときも、ISPのOP25Bで25番は止められる → 587を使う
  - 問題文が「ISPのOP25B」なら家庭・テレワーク、「FWのルール」なら会社の話
  - 覚え方：**「587は自社のメールサーバの投稿口。PCは投稿口（587）に出し、サーバが相手の受付（25）に届ける。外へ25番で出られるのはメールサーバだけ」**

### ◎ 第三者中継（オープンリレー）の禁止

- **第三者中継**：自社と関係のない送信者から、自社と関係のない宛先へのメールまで中継してしまうこと → 迷惑メールの踏み台になる
- 対策：**自社のドメイン宛て**のメールと、**認証した利用者（SMTP-AUTH）・社内のアドレス**から送るメールだけを受け付ける
- 記述の型：「外部から外部宛てのメールの中継を拒否し、迷惑メール送信の踏み台にされることを防ぐため」

### ◎ メールサーバの配置

- **DMZ（DeMilitarized Zone）にメール中継サーバ**（外部とのやり取り、迷惑メール・ウイルスの検査）を置き、**内部にメールボックスのあるメールサーバ**を置く
- FWのルール
  - 外部 → DMZのメール中継サーバ：TCP 25
  - DMZのメール中継サーバ → 外部：TCP 25（送信）、DNS（MXの問い合わせ）
  - DMZのメール中継サーバ ⇔ 内部のメールサーバ：TCP 25
  - 内部のPC → 内部のメールサーバ：587、POP3／IMAP
- → [[FW]]

### ○ MXレコードによる冗長化

- MXを複数登録し、優先度の値が小さいサーバに先に配送、止まっていれば次のサーバへ
- バックアップのメールサーバでも、迷惑メール対策を同じようにかける（バックアップ側を狙う迷惑メールがある）

### ○ クラウドのメールサービスへの移行

- MXレコードをクラウド側に向ける、SPF（Sender Policy Framework）にクラウドの送信元を追加する
- 送信元のIPアドレスが変わるので、受信側の判定（SPF）に影響する → [[SPF・DKIM・DMARC]]

## 5. 覚え方

- **SMTPは「郵便局どうしの配達」、POP・IMAPは「自分の郵便受けから取り出す」**
- **25は「局どうし」、587は「窓口に出す（本人確認あり）」**
- **エンベロープは「封筒の宛名」、ヘッダは「便箋に書いた差出人」**：どちらも自由に書ける → なりすましができる
- **OP25Bは「各家庭から直接よその局に投げ込ませない」**
- **第三者中継は「よそ者の手紙をよそへ運ばない」**

## 6. 勉強の優先順位

1. OP25Bの目的と、サブミッションポートを使う理由を30〜40字で書けるようにする
2. 第三者中継を禁止する理由と方法
3. メールサーバの配置（DMZと内部）と、FWのルール
4. エンベロープとヘッダの違い（なりすましの原因）
5. MXによる冗長化、ポート番号（25、587、465）

> [!tip] 得点につながる覚え方
> メールの問題では、**メールが通る経路（PC → 送信サーバ → 受信サーバ → PC）を矢印で描き、区間ごとにプロトコルとポート番号**を書き込む。そのうえで「外部へ直接25番で出させない」「外部から外部への中継を断る」の2点を確認する。
