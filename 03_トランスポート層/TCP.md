# TCP まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋め・計算として頻出／○ 午前・午後小問で出る／△ 深追い不要

## 1. TCPの基本（○）

- **コネクション型で、信頼性のある通信**を提供するトランスポート層のプロトコル
- TCP（Transmission Control Protocol）が行うこと（UDP（User Datagram Protocol）は行わない）
  - **コネクションの確立と切断**（3ウェイハンドシェイク）
  - **到達確認と再送**（シーケンス番号とACK（Acknowledgement））
  - **順序制御**（届いた順番がばらばらでも並べ直す）
  - **フロー制御**（受信側が処理しきれない量を送らない）
  - **輻輳制御**（ネットワークが混んだら送信量を減らす）

| | TCP | UDP |
|---|---|---|
| コネクション | あり | なし |
| 信頼性（再送・順序） | あり | なし（必要ならアプリが行う） |
| ヘッダ長 | **20バイト**（オプションで増える） | **8バイト** |
| 速さ・遅延 | 確立と再送の分だけ遅い | 速い、遅延が小さい |
| 向く用途 | Web、メール、ファイル転送、LDAP（Lightweight Directory Access Protocol） | **音声・映像（RTP：Real-time Transport Protocol）**、DNS（Domain Name System）の通常の問い合わせ、DHCP（Dynamic Host Configuration Protocol）、NTP（Network Time Protocol）、SNMP（Simple Network Management Protocol） |
| 送信元の詐称 | ハンドシェイクがあるので**しにくい** | **しやすい**（リフレクション攻撃に悪用） |

- **ポート番号**：0〜1023がウェルノウン、49152〜65535が動的・プライベート（クライアントの送信元ポートに使う）
- 午前の定番：「TCPとUDPの比較」「音声にUDPを使う理由」

## 2. ヘッダの主な項目（○）

| 項目 | 内容 |
|---|---|
| 送信元／宛先ポート番号 | どのアプリケーションの通信か |
| **シーケンス番号** | 送るデータの先頭が、全体の何バイト目か |
| **確認応答番号（ACK番号）** | **次に受け取りたいバイトの番号**（＝ここまで受け取った） |
| **フラグ** | SYN（Synchronize、接続要求）、ACK（確認応答）、FIN（Finish、切断要求）、**RST（Reset、強制切断）**、PSH（Push）、URG（Urgent） |
| **ウィンドウサイズ** | 受信側が、今受け取れる量（フロー制御に使う） |
| オプション | **MSS**（Maximum Segment Size）、ウィンドウスケール、SACK（Selective ACK）、タイムスタンプ |

## 3. コネクションの確立と切断（◎）

### 3ウェイハンドシェイク（確立）

```
クライアント                                    サーバ
    │── SYN（seq=100, MSS=1460）             ──→│
    │←─ SYN+ACK（seq=500, ack=101, MSS=1460） ──│
    │── ACK（ack=501）               ──────────→│
```

- **SYNのときに、MSSなどのオプションを互いに伝える**
- ACK番号は「相手のシーケンス番号＋1」（SYNは1バイト分として数える）

### 切断

- **FIN → ACK → FIN → ACK**（片方ずつ閉じる4回のやり取り）
- 最後にACKを送った側は、しばらく **TIME_WAIT** 状態で待つ（遅れて届くパケットへの対応、△）
- **RST**：その場で強制的に切断する。**待ち受けていないポートへのSYN**には、RSTが返る（UDPの場合はICMP（Internet Control Message Protocol）のポート到達不能が返る）

## 4. 信頼性：再送（○）

- 受信側は、受け取った分を**ACK番号**で知らせる。送信側はACKが来るまでデータを保持する
- 再送のきっかけ
  - **タイムアウト**：一定時間（RTO：Retransmission Timeout）ACKが来ない
  - **高速再送**：同じACK番号が**3回重複**して届く（＝途中の1つだけ抜けている）→ タイムアウトを待たずに再送
- **SACK**：抜けた部分だけを知らせて、必要な分だけ再送させる（△）

## 5. フロー制御とスループット（◎）

- **スライディングウィンドウ**：ACKを待たずに、**ウィンドウサイズ分まで連続して送る**
- 受信側は、ACKのたびにウィンドウサイズを通知する。処理が追いつかなければ小さくし、0にすれば送信が止まる
- **ウィンドウスケール**：ヘッダのウィンドウ欄は16ビット（最大65,535バイト）なので、オプションで最大約1GBまで拡張する

### ◎ スループットの計算

- **1コネクションの最大スループット ＝ ウィンドウサイズ ÷ RTT（Round Trip Time、往復遅延時間）**
  - 1往復の間に、ウィンドウサイズ分しか送れないため
- 例：ウィンドウ 64Kバイト、RTT 10ms
  - 64 × 1,000 × 8 ビット ÷ 0.01 秒 ＝ **約51Mbps**（1K＝1,024で計算すると約52Mbps）
  - 回線が1Gbpsあっても、1コネクションでは約51Mbpsしか出ない
- **帯域遅延積（BDP：Bandwidth-Delay Product） ＝ 帯域 × RTT**：回線を使い切るのに必要なウィンドウサイズ
  - 例：1Gbps × 100ms ＝ 100Mビット ＝ **12.5Mバイト**
- ◎の定番：**海外拠点や遠距離のWAN（Wide Area Network）で、回線は太いのに転送が遅い**
  - 原因：RTTが大きく、ウィンドウサイズで速度の上限が決まる
  - 対策：ウィンドウサイズを大きくする（ウィンドウスケール）、複数コネクションで並行して送る、WAN高速化装置を使う
  - 記述の型：「RTTが大きいため、ACKを待つ時間が長くなり、ウィンドウサイズで決まる上限までしか転送速度が出ないから」

## 6. 輻輳制御（○）

- 送信側は、ネットワークの混み具合に応じた**輻輳ウィンドウ（cwnd）**を自分で持つ
- **実際に送れる量 ＝ 受信ウィンドウ（rwnd）と輻輳ウィンドウ（cwnd）の小さい方**

| 段階 | 動き |
|---|---|
| **スロースタート** | 小さく始め、ACKが返るたびに**倍々（指数関数的）**に増やす |
| **輻輳回避** | しきい値を超えたら、**1ずつ（直線的）**に増やす |
| パケットロス（重複ACK） | cwndを**半分**にする（高速リカバリ） |
| パケットロス（タイムアウト） | cwndを**最小に戻し**、スロースタートからやり直す |

- **TCPグローバル同期**：ルータのキューがあふれて多数のTCPが同時にロス → 全員が同時に減速・増速して回線の利用率が波打つ → 対策は **RED（Random Early Detection）／WRED**（Weighted RED） → [[QoS]]
- アルゴリズム名（Reno、CUBIC、BBRなど）は△

## 7. MSS（◎）

- **MSS（最大セグメントサイズ）**：TCPが1回で運ぶ**データ部分**の最大サイズ
- **MSS ＝ MTU（Maximum Transmission Unit） − IP（Internet Protocol）ヘッダ（20） − TCPヘッダ（20）**
  - Ethernet：1500 − 40 ＝ **1460**
  - フレッツのPPPoE（PPP over Ethernet）：1454 − 40 ＝ **1414**
  - IPv6ではIPヘッダが40バイトなので、MTU − 60
- **SYNで互いのMSSを伝え、小さい方に合わせる**
- **MSSクランプ**：ルータが通過するSYNのMSS値を小さく書き換える → 端末が最初から小さいサイズで送る → **PMTUD（Path MTU Discovery）に頼らずに済む**
- 記述の型：「ルータでSYNパケットのMSS値を、経路のMTUに合わせた値に書き換える」

## 8. 午後で問われるテーマと記述の型

### ◎ スループットが出ない原因

- 「回線帯域を増やしたのに速くならない」→ **ウィンドウサイズ ÷ RTT** を計算して上限を確かめる
- 「無線LAN（Local Area Network）や回線品質が悪い区間で遅い」→ ロスのたびにcwndが小さくなり、再送も増える
- → 5章の計算と記述の型

### ◎ MTU・MSSとPMTUD

- PPPoE、IPsec（Security Architecture for Internet Protocol）、GRE（Generic Routing Encapsulation）などでヘッダが増える区間 → 1500バイトのパケットが通らない
- ICMPが遮断されていると**PMTUDブラックホール**（大きいデータだけ失敗）
- 対策：**MSSクランプ**（7章）
- → [[ICMP]]、[[PPP]]

### ○ FWのステートフルインスペクション

- FW（Firewall）は**SYNから始まるコネクションの状態を記録**し、その戻りの通信を自動で許可する
  - 内→外の許可ルールだけで、外からの応答は通る
  - **SYNなしで外から来たパケット**は、記録がないので破棄される
- コネクションの記録には**無通信タイマ**がある → 長時間通信のないコネクションは記録を消され、通信できなくなる
  - 対策：**TCPキープアライブ**やアプリのPing／Pongで定期的に通信する
- → [[WebSocket]]

### ○ SYNフラッド攻撃

- 送信元を詐称したSYNを大量に送り、サーバに**ハーフオープン（SYN+ACKを返してACKを待つ状態）のコネクション**を溜めさせて、資源を使い果たさせる
- 対策：**SYN Cookie**（ACKが返るまで記録を持たない）、FW・IPS（Intrusion Prevention System）でのSYNの数の制限
- 記述の型：「3ウェイハンドシェイクを完了させず、サーバに接続待ちの状態を大量に保持させるから」

### ○ 負荷分散装置とTCP

- **L4負荷分散**：IPアドレスとポート番号で振り分ける。コネクション単位
- **L7負荷分散**：HTTP（Hypertext Transfer Protocol）の中身（URL（Uniform Resource Locator）、Cookie）で振り分ける。装置がTCPコネクションを**いったん終端**し、サーバとは別のコネクションを張る
- **セッション維持（パーシステンス）**：同じ利用者を同じサーバに振り分け続ける
- → [[負荷分散装置]]

### ○ TCPかUDPかの選択

- 音声・映像：**遅れて届いたデータは使えない**ので、再送するTCPより**UDP（RTP）**が向く → [[QoS]]
- DNS：普段はUDP、ゾーン転送や大きい応答は**TCP** → [[DNS]]
- 送信元詐称を使う攻撃は、ハンドシェイクのない**UDP**で起きやすい → [[DNSリフレクタ攻撃]]

## 9. 覚え方

- **TCPは「書留郵便」、UDPは「普通郵便」**：書留は受領確認と再配達がある分、遅い
- **3ウェイは「もしもし（SYN）→ はい、もしもし（SYN+ACK）→ では話します（ACK）」**
- **ACK番号は「次はこれをください」**：ここまで受け取った、の次の番号
- **スループットの上限は「ウィンドウ ÷ RTT」**：1往復でトラック1台分しか運べない。道路（帯域）を広げても、トラックの荷台（ウィンドウ）が小さいと運べる量は増えない
- **輻輳制御は「倍々で増やし、ロスで半分」**
- **MSSは「MTUから40引く」**：1500 → 1460、1454 → 1414
- **重複ACKが3回で高速再送**

## 10. 勉強の優先順位

1. **スループットの計算（ウィンドウ ÷ RTT、帯域遅延積）**を自分で1回解いておく
2. 遠距離WANで遅い理由を30〜40字で書けるようにする
3. MSSの計算とMSSクランプ（PPP（Point-to-Point Protocol）、ICMPのノートとセットで）
4. 3ウェイハンドシェイクの流れとフラグ、ステートフルインスペクションとの関係
5. 輻輳制御（スロースタート、輻輳回避）とグローバル同期
6. SYNフラッド、負荷分散装置との関係
7. TIME_WAIT、SACK、アルゴリズム名は名前を知っている程度でよい

> [!tip] 得点につながる覚え方
> TCPは単独の大問より、**ほかの技術の「理由づけ」として何度も出る土台**。午後で「なぜ遅いか」「なぜ通らないか」「なぜ切れるか」と問われたら、**ウィンドウとRTT／MSSとMTU／FW・NAPT（Network Address Port Translation）のコネクション管理**の3つを疑う。

## 11. これまでのノートとの関係

| ノート | TCPのどの機能と関係するか | 内容 |
|---|---|---|
| [[ICMP]] | **MSS**、PMTUD | ICMPが遮断されるとPMTUDが働かず、大きいTCPセグメントが届かない。MSSクランプが対策 |
| [[PPP]] | **MSS** | PPPoEはヘッダ8バイト分MTUが小さい（1492／1454）→ MSSは1414。ルータでMSSクランプ |
| [[QoS]] | **輻輳制御**、UDPとの比較 | テールドロップでTCPグローバル同期 → RED／WRED。音声はTCPではなくUDP（RTP）を使う |
| [[WebSocket]] | **コネクション（長時間の接続）** | 1本のTCPを張りっぱなしにする → FW・NAPTの無通信タイマで切られる。Ping／Pongで維持 |
| [[FTP]] | **コネクション（2本）**、ポート番号 | 制御（21）とデータの2本のTCPを使う。データコネクションを張る向きでFW・NAPTの可否が変わる |
| [[DNS]] | **UDPとの使い分け** | 通常はUDP 53、ゾーン転送と大きい応答はTCP 53 → FWで両方を許可 |
| [[DNSリフレクタ攻撃]] | **3ウェイハンドシェイク**（UDPとの比較） | UDPはハンドシェイクがないので送信元を詐称できる。TCPでは詐称した相手とは接続が完了しない |
| [[LDAP]] | ポート番号 | TCP 389（LDAPS（LDAP over SSL/TLS）は636）。FWのルールで許可する |
| [[IEEE802.11]] | 再送、輻輳制御（直接のリンクはない） | 無線区間のロスや再送で、TCPのスループットが下がる |
| [[Gratuitous ARP]] | − | 直接の関係はない（L2／L3の仕組み） |
