# WebSocket まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

## 1. WebSocketの基本（○）

- **1本のTCPコネクション上で、サーバとクライアントが双方向に通信する**ためのプロトコル（RFC 6455）
- 最初は **HTTPで接続し、Upgradeでプロトコルを切り替える**。以降はHTTPではなくWebSocketのフレームでやり取りする
- サーバから**任意のタイミングでプッシュ**できる（HTTPはクライアントの要求に応答するだけ）
- **全二重**で、1回接続すればコネクションを張りっぱなしにする
- フレームのヘッダは2〜14バイトと小さい → HTTPのように毎回ヘッダを送らないので**オーバヘッドが小さい**
- URIスキームとポート

| スキーム | 下位 | ポート |
|---|---|---|
| `ws://` | TCP | 80 |
| `wss://` | TLS（TCP） | 443 |

- 用途：チャット、株価・ダッシュボードのリアルタイム更新、オンラインゲーム、IoTの監視、Web会議のシグナリング
- 午前の誤り選択肢の定番：「WebSocketはUDPで通信する」→ 誤り（TCP）

## 2. ハンドシェイク（◎）

### クライアント → サーバ（HTTP/1.1 GET）

```
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: https://example.com
```

### サーバ → クライアント

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

| 項目 | 役割 | 出題度 |
|---|---|---|
| `Upgrade: websocket` / `Connection: Upgrade` | プロトコルの切替を要求 | ◎ |
| **101 Switching Protocols** | 切替に同意したことを示すステータス | ◎ |
| `Sec-WebSocket-Key` | クライアントが生成するランダム値 | ○ |
| `Sec-WebSocket-Accept` | Keyに固定の文字列を連結しSHA-1→Base64した値。**WebSocket対応サーバが応答したことの確認** | ○ |
| `Origin` | 接続元ページのオリジン。サーバが不正なサイトからの接続を拒否するのに使う | △ |

- 穴埋めで「101」「Upgrade」が問われやすい

## 3. フレーム（△〜○）

| opcode | 種類 |
|---|---|
| 0x0 | 継続フレーム |
| 0x1 | テキスト |
| 0x2 | バイナリ |
| 0x8 | クローズ |
| 0x9 | **Ping** |
| 0xA | **Pong** |

- **Ping／Pong**：生存確認と、無通信によるタイムアウト防止（キープアライブ）に使う → 午後で重要
- クライアント→サーバのフレームは**マスク必須**（中間装置のキャッシュ汚染を防ぐため）。サーバ→クライアントはマスクしない

## 4. 他の方式との比較（○）

| 方式 | 仕組み | 欠点 |
|---|---|---|
| ポーリング | クライアントが定期的にHTTP要求する | 更新がなくても通信する。間隔の分だけ遅れる |
| ロングポーリング | 要求をサーバが保留し、更新があったら応答する | 応答のたびに要求をやり直す。ヘッダのオーバヘッド |
| SSE（Server-Sent Events） | HTTP応答を開いたままサーバから流し続ける | **サーバ→クライアントの片方向のみ** |
| **WebSocket** | 1本のTCPで全二重 | プロキシ・LB・FWでの考慮が必要 |

- 問われ方：「ポーリングと比べた利点」→ **通信量（ヘッダ）とサーバ負荷の削減、遅延の短縮**
- 記述の型：「サーバから任意のタイミングで送信でき、HTTPのように要求ごとにヘッダを送る必要がないから」

## 5. 午後で問われるテーマと記述の型

### ◎ 無通信タイムアウトによる切断

- WebSocketは**コネクションを長時間張りっぱなし**にする
- 経路上のFW、NAPT、プロキシ、負荷分散装置には**無通信タイマ**がある → 無通信が続くとセッション情報を消され、コネクションが切れる
- 対策
  - アプリで **Ping／Pong を定期的に送る**（タイマより短い間隔）
  - 機器側の無通信タイマを長くする
  - 切れたときにクライアントが自動で再接続する
- 記述の型：「一定時間通信がないと、FW（NAPT）のセッション情報が削除され通信できなくなるから」

### ◎ プロキシ経由の通信

- `ws://`（平文）：HTTPの**Upgradeに対応していないプロキシ**だと、ヘッダを書き換えたり101を中継できず失敗する
- `wss://`（TLS）：ブラウザはプロキシに **CONNECTメソッド** でトンネルを張らせる → プロキシは中身を解釈せず中継するだけなので**通りやすい**
- 問われ方：「wssを使う理由（暗号化以外）」「プロキシで許可すべき設定」
- 記述の型：「CONNECTメソッドでトンネルを確立するため、プロキシがWebSocketに対応していなくても中継できるから」
- TLSインスペクション（復号）を行うプロキシでは、WebSocketに対応していないと通信できない点にも注意 → [[プロキシ]]

### ◎ 負荷分散装置（LB）

- L7で処理するLBは、**Upgradeヘッダを解釈して中継できる**必要がある（非対応ならL4で中継する）
- 1本のコネクションが長く続く → **リクエスト単位ではなくコネクション単位で振り分けが固定される**
  - サーバを追加しても、既存の接続は移らないので**負荷が偏りやすい**
  - サーバを止めると、その配下の全クライアントが一斉に再接続する
- 振り分け方式は**最小コネクション数**方式が向く（ラウンドロビンだと偏る）
- 複数サーバ間で同じメッセージを配る（チャット等）には、サーバ間で情報を共有する仕組みが必要
- → [[負荷分散装置]]

### ○ FWの設定

- 宛先ポートは **80／443** で、HTTP／HTTPSと区別しにくい
- 通信開始は**クライアントから**のTCP接続なので、FWは内→外の許可（戻りはステートフルで通る）で足りる。サーバからのプッシュでも、外から新しく接続しに来るわけではない
- 問われ方：「サーバからプッシュするのに、外→内の許可ルールが要らない理由」
- 記述の型：「クライアントが確立したTCPコネクション上でサーバが送信するため、新たな着信は発生しないから」

### △ セキュリティ

- ブラウザの同一オリジンポリシーはWebSocketにはそのままは効かない → サーバが **Originヘッダを検証**する（CSWSH：クロスサイトWebSocketハイジャック対策）
- 認証はハンドシェイク時（Cookie、トークン）に行う

## 6. 覚え方

- **「HTTPで入って、101で着替える」**：GET + Upgrade → 101 Switching Protocols で以降はWebSocket
- **「張りっぱなしは、タイマに切られる」**：長時間接続 × 無通信タイマ → Ping／Pongで生かし続ける
- **wssは「CONNECTで素通り」**：プロキシは暗号化された中身を見ずにトンネルで中継する
- **SSEは片道、WebSocketは往復**
- **プッシュでも始めたのはクライアント**：だからFWは内→外だけでよい

## 7. 勉強の優先順位

1. ハンドシェイク（Upgrade、101）を穴埋めで答えられるようにする
2. 無通信タイムアウトによる切断と Ping／Pong 対策を、自分の言葉で30〜40字で書けるようにする
3. プロキシ経由での `wss://`（CONNECT）の理由を説明できるようにする
4. LBで負荷が偏る理由と、最小コネクション数方式
5. フレームのopcodeは Ping／Pong があることだけ押さえればよい

> [!tip] 得点につながる覚え方
> WebSocketは単独で深く問われるより、**Webシステムの構成問題の中で「長時間接続をFW・NAPT・プロキシ・LBがどう扱うか」**として出る。プロトコルの細部より「張りっぱなしのTCP」が経路上の機器に与える影響で考える。
