# 負荷分散装置 まとめ（ネスペ出題観点）

出題度：◎ 午後で記述・穴埋めとして頻出／○ 午前・午後小問で出る／△ 深追い不要

## 1. 負荷分散装置の基本（◎）

- **負荷分散装置（LB（Load Balancer）：ロードバランサ）**：利用者からの通信を、**複数のサーバに振り分ける**装置
- 利用者は**LBの仮想IP（Internet Protocol）アドレス**（VIP（Virtual IP））にアクセスし、LBが実際のサーバを選んで転送する
- 目的
  - **負荷の分散**：1台では処理しきれない量を複数台でさばく
  - **可用性の向上**：故障したサーバを自動で外し、残りで処理を続ける
  - **保守のしやすさ**：1台ずつ外して作業できる
- 振り分ける層

| | L4負荷分散 | L7負荷分散 |
|---|---|---|
| 判断に使う情報 | IPアドレス、ポート番号 | **HTTP（Hypertext Transfer Protocol）の中身**（URL（Uniform Resource Locator）、Cookie、ヘッダ） |
| TCP（Transmission Control Protocol）の扱い | そのまま中継 | LBで**いったん終端**し、サーバとは別のコネクションを張る |
| HTTPS（HTTP Secure） | 中身は見えない | LBで**TLS（Transport Layer Security）を終端**すれば中身を見られる |

## 2. 振り分け方式（○）

| 方式 | 内容 | 向く場面 |
|---|---|---|
| **ラウンドロビン** | 順番に振り分ける | サーバの性能が同じ、処理時間が短い |
| **重み付けラウンドロビン** | 性能に応じた比率で振り分ける | サーバの性能が違う |
| **最小コネクション数** | 現在のコネクションが最も少ないサーバへ | **接続時間がばらつく**、長時間の接続（WebSocketなど） |
| 最小応答時間 | 応答が最も速いサーバへ | − |

- 問われ方：「長時間の接続が多い場合に適した方式」→ 最小コネクション数 → [[WebSocket]]

## 3. ヘルスチェック（◎）

- LBがサーバの状態を定期的に確認し、**異常なサーバを振り分け先から外す**

| レベル | 確認方法 | 分かること |
|---|---|---|
| L3 | **ping（ICMP（Internet Control Message Protocol））** | サーバ（OS（Operating System））が動いているか |
| L4 | **TCPで接続**できるか（ポートが開いているか） | サービスのプロセスが待ち受けているか |
| **L7** | **HTTPで特定のページを要求**し、応答コードや内容を確認する | **アプリケーションが正常に動いているか** |

- ◎の定番：**L3・L4のヘルスチェックでは、アプリケーションの異常（データベースにつながらない、エラーページを返す）を検知できない**
- 記述の型：「L4のヘルスチェックではポートが応答していれば正常と判断するため、アプリケーションの異常を検知できないから。L7で応答内容まで確認する」

## 4. セッション維持（パーシステンス）（◎）

- ログイン状態やショッピングカートなど、**サーバが利用者ごとの情報を持つ**アプリケーションでは、同じ利用者を**ずっと同じサーバ**に振り分ける必要がある

| 方式 | 内容 | 注意点 |
|---|---|---|
| **送信元IPアドレス** | 同じ送信元IPは同じサーバへ | **プロキシやNAPT（Network Address Port Translation）の先の多数の利用者が同じIPに見える** → 1台に集中する |
| **Cookie** | LBがCookieにサーバの情報を入れる（または既存のCookieを見る） | **HTTPの中身を見る必要がある** → HTTPSならLBでTLSを終端する |
| TLSのセッションID | TLSのセッションIDで判別 | 再接続でIDが変わることがある（△） |

- 記述の型（送信元IPの問題）：「多数の利用者がプロキシ経由で同じ送信元IPアドレスになり、特定のサーバに負荷が集中するから」
- 記述の型（TLS終端が必要な理由）：「Cookieを参照してセッションを維持するには、LBでHTTPSを復号する必要があるから」
- → [[TLS]]

## 5. 構成（○）

- **インライン構成**：LBをクライアントとサーバの間に置く。行きも帰りもLBを通る
- **ワンアーム構成**：LBを経路の脇に置く。戻りの通信がLBを通らないとうまく動かない → LBで**送信元アドレスもLBのアドレスに変換**（SNAT（Source NAT））して、戻りをLBに戻す
  - **なぜSNATしないと動かないのか**（利用者 203.0.113.5 → VIP 192.0.2.100 の例）
    ```
    【送信元をそのままにした場合】
    ① 利用者 → LB         送信元 203.0.113.5 → 宛先 192.0.2.100（VIP）  ← 利用者は「VIPと話している」つもり
    ② LB → Webサーバ      送信元 203.0.113.5 → 宛先 10.1.1.11（サーバ）  ← 宛先だけ変換
    ③ Webサーバ → 利用者  送信元 10.1.1.11  → 宛先 203.0.113.5
                          ↑ 宛先が利用者なので、LBを通らずにルータへ直接返す → 送信元がVIPでない ✕
    
    【SNATした場合】
    ② LB → Webサーバ      送信元 10.1.1.2（LB）   → 宛先 10.1.1.11
    ③ Webサーバ → LB      送信元 10.1.1.11        → 宛先 10.1.1.2（LB）  ← 返事がLBに戻る
    ④ LB → 利用者         送信元 192.0.2.100（VIP）→ 宛先 203.0.113.5   ← LBが送信元をVIPに戻して返す ✓
    ```
    - 送信元をそのままにすると、サーバの応答はLBを通らずに利用者へ直接返り、**送信元がVIPではなくサーバのアドレス**になる。利用者は「VIPに接続を申し込んだのに、知らない相手から返事が来た」と判断して捨てる → TCPの接続が成立しない
    - たとえ：会社の代表番号（VIP）に電話したのに、担当者の携帯から折り返しが来た。知らない番号なので出ない
    - SNATすると、サーバから見た相手はLBになるので、応答が必ずLBに戻る
    - インライン構成では、行きも帰りも必ずLBを通るので、この問題は起きない
    - 記述の型：「サーバからの応答がLBを経由せず利用者に直接返り、送信元がVIPではないため、利用者側で受け付けられないから」
  - SNATすると、サーバから**本当の利用者のIPアドレスが見えない** → LBがHTTPヘッダ **X-Forwarded-For** に元のアドレスを入れて渡す
    - 記述の型：「LBでHTTPヘッダのX-Forwarded-Forに利用者のIPアドレスを付与し、Webサーバでその値をログに記録する」
    - X-Forwarded-ForはHTTPのヘッダなので、HTTPSなら**LBでTLSを終端している**ことが前提 → [[TLS]]
- **DSR（Direct Server Return）**：戻りの通信をLBを通さずサーバから直接返す。LBの負荷が減る（△）
- **LB自体の冗長化**：2台でアクティブ／スタンバイにし、VIPを引き継ぐ。セッション維持の情報も同期する
- **GSLB（Global Server Load Balancing）**：DNS（Domain Name System）の応答で**複数のデータセンター・クラウド**に振り分ける → [[DNS]]

## 6. 午後で問われるテーマと記述の型

### ◎ サーバの増設・保守

- 新しいサーバを振り分け先に追加する、保守のために1台を**振り分け先から外す**
- 外すときは、**新規の接続だけ止めて、既存のセッションが終わるのを待ってから**停止する
- 記述の型：「新規の振り分けを停止し、既存のセッションが終了してからサーバを停止することで、利用者の通信が切断されないようにする」

### ◎ TLS終端と証明書

- LBでTLSを終端する場合、**サーバ証明書と秘密鍵をLBに導入**する（令和5年春 午後Ⅱ 問2でも問われた）
- LBとサーバの間は平文にするか、再び暗号化する
- → [[TLS]]

### ○ DNSラウンドロビンとの違い

- DNSラウンドロビンは**サーバの故障を検知しない**、キャッシュで偏る。LBは**ヘルスチェック**で故障したサーバを外せる

### ○ LBの冗長化と切替

- LBが1台だと単一障害点 → 2台で冗長化し、VIPを引き継ぐ（VRRP（Virtual Router Redundancy Protocol）と同様の仕組み）
- 切替時にGratuitous ARP（Address Resolution Protocol）で周りの機器を更新する → [[Gratuitous ARP]]

## 7. 覚え方

- **LBは「受付係」**：客（利用者）は代表窓口（VIP）に来て、受付係が空いている担当者（サーバ）に案内する
- **ヘルスチェックは「L3は生きているか、L4は席にいるか、L7はちゃんと仕事ができるか」**
- **セッション維持は「同じ客は同じ担当者へ」**：送信元IPだとプロキシの客がまとめて1人に見える。Cookieなら中身（HTTPS）を開ける必要がある
- **長い接続は「最小コネクション数」**
- **SNATすると客の顔が見えない → X-Forwarded-Forに名札を付ける**

## 8. 勉強の優先順位

1. ヘルスチェックのレベルの違いと、L7が必要な理由を30〜40字で書けるようにする
2. セッション維持の方式（送信元IP、Cookie）と、それぞれの注意点
3. LBでのTLS終端（証明書と秘密鍵の導入、Cookieを見るため）
4. 振り分け方式の使い分け
5. サーバの切り離しの手順、LBの冗長化
6. SNATとX-Forwarded-For、DSR、GSLBは概要を押さえればよい

> [!tip] 得点につながる覚え方
> LBは**Webシステムの増強・更改の問題で頻出**。構成図にLBがあったら、**ヘルスチェックのレベル**、**セッション維持の方法（HTTPSならTLS終端が必要）**、**LBの冗長化**の3点を確認する。
